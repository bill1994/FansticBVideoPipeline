## 上午（续）：YOLO26 vs YuNet 选型对比（深度研究团队 · 单章模式）

用户问：换成 YOLO26 性能会更好吗？系统压力会不会更小？调研文档因开源许可不采用，但自己自用+无偿分享、不商用。

**交付**：`docs/reviews/2026-10-17-YOLO26与YuNet检测后端对比-单章研究.md`（约 200 行 / 21 条可点击来源）
执行：建团队 `research-yolo26-vs-yunet` → topic-researcher 初稿 → draft-reviewer 审稿（**2 轮 REVISE**，共 7 条必改）→ draft-reviser 修订 2 轮 → 第 3 轮 PASS。

### 三条硬结论

1. **YOLO26 结构上不能替代 YuNet 做人脸**：COCO 80 类**没有 face 类**（官方文档 80 类清单逐条核对），只能输出 `person` 人体框。要出人脸框必须 WIDER FACE 级标注**重训单类头**。⚠️ 关键澄清：**运行时纯 Node 不是阻碍**（训练是一次性离线步骤，ONNX 导出后照常在 onnxruntime-node 跑），真正阻碍是重训工程量 + 重训产物的 AGPL 归属。
2. **系统压力是变大不是变小**：模型体积 20–35×、参数 32–38×、单帧耗时 3.3–5.4×；但 1fps 下 1 小时素材 3600 帧，总耗时 43s → 140–235s，离线批处理**不构成障碍**。`onnxruntime-node` 的 100MB 级固定成本两者共用。
3. **许可：用户只对了一半**。自用（不 convey）= 零义务 ✅；但**无偿分享给他人 = convey，一样触发 §4–§6**（AGPL §4 原文 "any price or no price" 与收费无关；FSF FAQ 组织内复制不算、转给外部个体才算）。报告 v1.1 已把 YOLO 改为"自用场景备选"，原"硬排除"已过期。

### 与项目代码对上的三条事实（本次实测核对）

- `OCCLUSION_BUDGET = { face: 0, handheld: 0.2, broll: 0.3 }` —— **face 额度 0，任何相交即 error**；唯一 `occludesSubject: true` 的 `center-emphasis` 落画面中部 ⇒ face 框精度 = 误报率。
- `shot.safeArea` 至今**零消费**（仅 perceive.ts 形状校验 + 1 个测试夹具）；`subjectBox` 仅出现在告警文案。
- **M-4 定案的 fail-closed 在 `src/` 里一行实现都没有**（只存在于报告/文档）。

### 术语雷区（本次抓到研究生误读，务必记牢）

`handheld` = **主持人手持的讲解用物品**（D5：小物品、形状变化不大），是**物体检测**，不是"手持拍摄/运动镜头"；
`broll` = B-roll 空镜里的**主体**（产品特写），不是"无主体的空镜"。二者都不是镜头/场景分类，**不能用光流/相机抖动替代**。

## 上午（续 4）：🔴 唯一硬阻断已拆除 —— perceive 内置后端上线

### 阶段 B 的取舍结论：走「第三条路」，跳过对比实验

原计划是 `@napi-rs/canvas` vs 纯 Buffer 手写二选一。实际结论是**两个都不选**：

> **让 ffmpeg 一次做完「抽帧 + 等比缩放 + 补边」，直吐 `rgb24` 原始字节；Node 只做通道重排（RGB 交错 → BGR planar）。**

理由：ffmpeg 本来就是本阶段必需依赖（抽音轨/抽帧/镜头切分都用），再引原生插件（`@napi-rs/canvas`）
或图片解码库（生产路径根本不需要解码器）都是纯增风险；1fps 量级下性能不是瓶颈（单帧推理 11.4ms）。
补边用 ffmpeg `pad` 补 0，与 OpenCV `BORDER_CONSTANT 0` 语义一致。

⚠️ **与报告 §5.4 阶段 B 判据的差异已如实记录在代码注释里**：未做像素一致性对比（不存在第二个实现）。

## 下午：三素材实测 —— 揪出两个真 bug

### 🔴 Bug 1（严重）：fps 滤镜抽帧的时间映射不可靠 → 检测结果归属错位

**现象**：`3月22日` 的 s1 被判成 face，抽图看是**纯鞋子特写**；
生产 debug 却说 `t=4.50s f=270 score=0.930 box=[0.433,0.097,…]`，
而同一时刻用 `-ss 4.5` 抽帧跑检测只有 **0.39**。

**根因**：原实现用 `-vf fps=1/interval` 抽帧，并假设「第 i 个输出帧 = i × interval 秒」。
实测证伪 —— **标称 4.5s 的那一帧，画面实际是 4.87s 之后的人物镜头**
（`fps` 滤镜按时间桶采样，桶内取哪一帧不受控）⇒ 「帧 → shot」归属整体错位，
产品特写镜头里塞进了对侧人物镜头的检测结果。

**修法**：改用 `select='not(mod(n,step))'` 按**帧号**抽帧，`frameNo = framesScanned × step` 精确成立，
与镜头切分（同基于帧号）处于同一坐标系。

**连带第二个坑**：加了 `select` 后仍读到 7649 帧（=总帧数）。
原因是 **ffmpeg 默认 cfr 同步会把稀疏帧按输入帧率补回去**
（20 秒素材实测：14 帧 → 1259 帧）。必须加 **`-fps_mode passthrough`**。
⚠️ ffmpeg 9 已移除 `-vsync`，只能用它。

**另一处转义坑**：`select='not(mod(n,90))'` 在 Node `spawn` 传参时**不要**写 `\,`
（多写的反斜杠会让 select 失效、输出全部帧）。单引号本身已足够保护逗号。

### 🔴 Bug 2：handheld 外扩高度不够，漏掉手和鞋

`s2`（人物中景、双手扶鞋）实测：face 框 `[0.427,0.062,0.135,0.298]`，
`heightRatio=2` 时框底只到 **0.658**，而手与鞋在 **0.75–0.85** ⇒ **手和鞋下半部分露在框外**（抽帧目视确认）。
按「头顶 0.062 → 上半身底 0.75」反推需 ≈2.3，取 **2.5** 留余量。
⚠️ 不宜再大：handheld 预算只有 20%，框越大 overlay 占比越小，保护形同虚设。

## 下午（续）：低置信镜头查出第三个 bug —— **假阴性**

用户要看 `3月22日` 的 s4（唯一低置信 shot，75 帧 / 1.25s）。

### 🔴 根因：短镜头被抽帧间隔整段跳过

`planSampleFrames(spans, step)`：每段内均匀取 `ceil(duration/step)` 帧、**至少 1 帧**、取段中点避开转场边界。
抽成纯函数 + **6 项单测**（`tests/perceive-sampling.test.ts`，含 s4 场景回归用例）。
ffmpeg 用完整 `eq(n,…)` 列表 select（而非 mod），配合 `-fps_mode passthrough`。

### 🔴 用户的关键改进：裁切窗口**围着主体画**

我原来的方案是「固定切左/右或中间」，用户指出应该**切主体两侧**。
技术化后叫 **主体锚定裁切**：

```
窗口中心 = 该 shot 的 safeArea 中心
窗口宽度 = ratio × 画面宽（ratio 钳制 0.3–0.7）
左边界  = clamp(中心 − 窗口宽/2, 0, 1 − 窗口宽)
```

- **主体几乎恒完整** —— 窗口是照着它画的，被切的永远是两侧空白
- `side` 参数只决定「视频显示在画面哪一侧」，**与裁哪里无关**
- 裁切窗口在**校验期算好**写入 `params.window`（归一化），渲染期直接消费

### 派生判据（W-D2-02 的正确形式）

```ts
visibleRegion(params) => params.window
|safeArea ∩ window| / |safeArea| >= MIN_VISIBLE_RATIO   // 默认 0.5（占位，待校准）
```

只用于兜底**「主体比窗口还宽」**的极端情形 —— 正常构图下恒为 1.0。
