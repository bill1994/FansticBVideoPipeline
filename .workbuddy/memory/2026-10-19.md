## 🔴 抓到 `placeholders --check` 的假红（换机必犯，且报错指错方向）

拉取后首次跑 `npm run placeholders -- --check` → **FAIL**，而 `git diff` 显示文件**零差异**。

### 定位过程

1. 重跑生成器再 `diff` ⇒ **141 行全部标记不同，但内容逐字一致** —— 典型的行尾符差异。
2. Node 读字节：committed blob `crlf:0 / lf:141`，重新生成 `crlf:0 / lf:141`，**byteEqual true**。
   ⇒ 不是 git blob 的问题，是**工作区文件**。
3. `git status` 报 M 但 `git diff --stat` 为空 + warning 提示
   `LF will be replaced by CRLF the next time Git touches it` ⇒ **`core.autocrlf=true`，仓库无 `.gitattributes`**。
4. 直接验证：`git checkout --` 该文件后统计 → **CRLF 141 / LF 141**，
   此时 `--check` **FAIL**；再 `npm run placeholders` 写成 LF 后 → **OK**。

**根因**：`tools/list-placeholders.mts:150` 的 `cur !== md` 是**逐字节**比对，
而 `writeFileSync` 在 Windows 上不转换行尾、`git checkout` 却按 autocrlf 写出 CRLF。
⇒ **每次拉取后必红，且内容完全正确**。

**为什么这条特别值得记**：错误信息是「与 `placeholders.ts` 不一致，跑 `npm run placeholders` 重新生成后提交」——
把人指向**改代码**，而代码完全没问题。照着做只会写出一个 LF 文件、再被下次 checkout 打回 CRLF，**无限循环**。
这与项目记的「假绿」系列互补：**假绿是本该红却绿，这个是该红却红且原因在工具自身**。

### 修法

比对前 `normalizeEol()`（`\r\n → \n`）；失败时额外判断是否**仅**行尾差异，是则追加提示，
不再让人去改代码。

**反向验证**（防修成「永远通过」）：手动篡改一个单元格 → `--check` **FAIL** 且未误报行尾原因；
恢复 → **OK**。

## M-1g：无字幕模式（`--no-subtitle`）—— 用户选「走3，先不看 karaoke」

### 为什么需要它（不是「造假绕过门控」）

用户两条素材**字幕烧在画面里**（实测：无字幕轨，只有 video+audio），
而字幕模板外的 motion 模板**完全不依赖词级时间** —— 只用 `abs:` 锚点。
原先门控一刀切「无词级时间 ⇒ 拒绝起草」，于是「只想验证 motion 表现」也做不了。

### 设计：给「本来就不需要对齐」一条正路

| 做法 | 说明 |
|---|---|
| `--no-subtitle` | align 阶段产出**显式标记的空产物** |
| `AlignReport.mode` | `'aligned'`（默认）/ `'no-subtitle'` —— **新字段，落盘** |
| `words`/`cues` | **空数组**，不是编造的词 |
| `silentWordRatio` | `null`（真·未测量） |
| storyboard 侧拦截 | `mode==='no-subtitle'` 时**主动报错**：`word:`/`cue:` 锚点与字幕模板都不可用 |

🔴 **与 P0「绝不伪造结果」不冲突**：伪造是「把没测的说成测了」，
这里是「明说没测（`mode` + `null`），并把该禁的都禁掉」。
⚠️ `meanConfidence` 仍记 0（类型是 `number` 且下游有算术，不能null），
「没测」由 `mode` 与 `silentWordRatio: null` 承担。

### 关键：拦截器必须精确，且错误信息要指向真实原因

不拦的话 `word:0` 会取到 `undefined`，报错说「锚点序号非法」——
看起来像 draft 写错，真实原因是「这条 job 没做对齐」。实测拦截输出：

```
✗ 本 job 是**无字幕模式**（mode = no-subtitle）—— 没有词级时间戳也没有 cue，下列写法不可用：
  · 轨「t1」的 word:8
  · 轨「t2」的字幕模板 caption/karaoke-word
  ↳ 改用 `abs:<帧>` 或 `abs:<秒>s` 锚点（不依赖对齐数据）。
  ↳ 若本片其实有 SRT，请去掉 --no-subtitle 重跑align。
```

### 🔴 顺手修一个「报错信息自己打自己脸」的问题

写 draft 时踩到：注册表存的是 `typography/kinetic-line@1.0`（**带版本**），
而 motion 字段**必须带 `@1.0`**。我漏了 ⇒ 报「未注册」，
但错误信息列出的已注册清单里**明明有它** ⇒ 自己打自己的脸，绕了一圈才定位。

修法：`getTemplate()` 检测「去掉 `@版本` 后能匹配」时，直接提示正确写法：
`↳ 你大概想写 typography/kinetic-line@1.0 —— motion 的规范写法是 family/subtype@version`
（对真正不存在的 motion 不误报，实测 `false`）。

### 🔴 真渲抓到的问题：split-frame 单独用会半屏纯黑 —— 是 draft 用法问题，不是代码 bug

两条素材的 `carrier/split-frame` 都出现「一半画面正常、一半纯黑」。
像素级量测（`t=106s`，1920×1080）：左半屏均色 `172.2,167.1,147.8` / 右半屏 `0.0,0.0,0.0`。

🔴 **查证结论：不是 10-18 那个 bug 复发**，而是 **draft 用法错误**：
`split-frame` 的语义是「视频缩进一侧，**另一侧留给 overlay**」；
我两条 draft 都**单独**放了它，同区间无任何 overlay ⇒ 另一半自然没人填。
（证据：storyboard 里该区间只有它自己一个 item；`splitFrameGeometry({side:'left'})`
算出的 `display=[0,0,0.5,1]` 是**正确的**——视频确实该在左半。）

修法：给同区间补一个 overlay 填另一半（0322 补右半 `kinetic-line`，
0528 补左半 `stat-card`），两条均 0 error 通过。

⚠️ 这条值得记：**「半屏黑」有两种可能**（载体轨失效 / 用法缺配套 overlay），
判据是查该区间**有没有 overlay item** —— 有则是前者，无则是后者。
别看到黑屏就以为撞上老bug。
