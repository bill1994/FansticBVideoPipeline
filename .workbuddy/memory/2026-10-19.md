## 🔴 抓到 `placeholders --check` 的假红（换机必犯，且报错指错方向）

拉取后首次跑 `npm run placeholders -- --check` → **FAIL**，而 `git diff` 显示文件**零差异**。

### 定位过程

1. 重跑生成器再 `diff` ⇒ **141 行全部标记不同，但内容逐字一致** —— 典型的行尾符差异。
2. Node 读字节：committed blob `crlf:0 / lf:141`，重新生成 `crlf:0 / lf:141`，**byteEqual true**。
   ⇒ 不是 git blob 的问题，是**工作区文件**。
3. `git status` 报 M 但 `git diff --stat` 为空 + warning 提示
   `LF will be replaced by CRLF the next time Git touches it` ⇒ **`core.autocrlf=true`，仓库无 `.gitattributes`**。
4. 直接验证：`git checkout --` 该文件后统计 → **CRLF 141 / LF 141**，
   此时 `--check` **FAIL**；再 `npm run placeholders` 写成 LF 后 → **OK**。

**根因**：`tools/list-placeholders.mts:150` 的 `cur !== md` 是**逐字节**比对，
而 `writeFileSync` 在 Windows 上不转换行尾、`git checkout` 却按 autocrlf 写出 CRLF。
⇒ **每次拉取后必红，且内容完全正确**。

**为什么这条特别值得记**：错误信息是「与 `placeholders.ts` 不一致，跑 `npm run placeholders` 重新生成后提交」——
把人指向**改代码**，而代码完全没问题。照着做只会写出一个 LF 文件、再被下次 checkout 打回 CRLF，**无限循环**。
这与项目记的「假绿」系列互补：**假绿是本该红却绿，这个是该红却红且原因在工具自身**。

### 修法

比对前 `normalizeEol()`（`\r\n → \n`）；失败时额外判断是否**仅**行尾差异，是则追加提示，
不再让人去改代码。

**反向验证**（防修成「永远通过」）：手动篡改一个单元格 → `--check` **FAIL** 且未误报行尾原因；
恢复 → **OK**。
