## 追加会话：C2-5 专项分析（框架修正）

用户要求分析 C2-5 二道闸的优缺点。**框架修正**：我上一轮把三类性质不同的错误混成了一类。

### 错误分类（关键推论）
| 错误类型 | 例子 | 能否机械判定 | 性质 |
|---------|------|------------|------|
| 时序错位 | 词未出口动效已进 | ✅ fromFrame vs 词级 startFrame | **客观错误** |
| 密度过载 | 一句 8 字塞 4 个 motion | ✅ 每 cue item 数超阈值 | **客观错误** |
| 语义次优 | 卡在「参数」但该强调「三倍」 | ❌ 真需语义判断 | **主观次优**（品味，非 bug） |

**关键推论**：真正「看起来像对」的只有第三类，恰好是三类里最不需要自动化的一类。前两类纯机械校验即可。

### 方案对比结论
| 方案 | 成本 | 误报 | 判断 |
|------|------|------|------|
| A. LLM 语义闸 | token低/延迟高 | **高** | 需 POC |
| B. 编辑页全量高亮 | 零 | 中（告警疲劳） | 筛选信号待解 |
| C. **对齐置信度高亮** | **零（数据已在手）** | **低** | **推荐** |

**方案 C 是我上一轮漏掉的解**：C2-4 已产出每词置信度，这份数据钱已付过。低置信词恰是最不该信的词 → 高亮规则改为「只标出目标词对齐置信度低于阈值的锚点」。

### LLM 闸的三个硬约束（若采用）
1. 必须用**比较式问法**（「有没有更该被强调的词」）而非「这个词合理吗」—— 二元判断校准极差，LLM 对绝大多数词都会答合理，门会失效
2. 阈值极度偏向多报（漏报成本 >> 误报成本）
3. 输出必须定位到具体 item，不能只给总数

### 推荐处置（分层）
- **第一层 机械校验（必做，非选项）**：时序 + 密度校验，零成本零误报。无论 C2-5 如何裁决，均须写入 F 分支校验器清单
- **第二层 语义次优**：倾向不做 LLM 闸，改用方案 C 置信度高亮
- 若采用 LLM 闸：先在 C 分支跑小样本测误报率，登记为 `design-decision-to-evaluate`，不直接进 Spec

已写入 `docs/decisions/OPEN-DECISIONS.md` 专项分析章节。

## 追加会话：C4 封口（footprint 几何仲裁）

用户裁决：① 加 footprint 字段 ② 相交不同组选 **warning** ③ 主从冲突**需要特例放行**。

### 核心机制
每个 motion item 落盘带 `footprint`（归一化矩形 `[x,y,w,h]`，0-1），校验期做矩形相交检测：

| 条件 | 判定 |
|------|------|
| 相交 + 同 `exclusive` 组 | **error** |
| 相交 + 不同组 | **warning**（列出不拦） |
| 不相交 | 通过（即便同组） |

### 关键设计决定（我的主张，用户未反对）
主从冲突放行**由 `scope` 枚举自动推导，不做字符串白名单**。
- ❌ 白名单 `noConflict: ["subject-transform","overlay-safe"]` → 命名空间可扩展，白名单无限膨胀，新模板需手工登记 = 校验黑洞
- ✅ B6 的 6 个 scope 枚举天然分两类：载体类（`subject-transform`/`footage-transform`）与叠加类（`overlay-safe`/`under-subject`）。跨类组合即主从，自动放行

**收益：新增模板零维护**。只有新开 scope 枚举值才需重评放行矩阵。

### 对 B6 的改动
模板强制契约新增 `footprint` 项（归一化矩形，模板默认值，item 可覆盖）。

### 边界划分（重要）
C4 只管 **overlay 之间**的空间冲突。「不得遮挡 presenter」是**分支 D**（主体安全区）。D 的判定结果经 `occludesSubject` 契约字段参与 C4 的 error 判定 —— 两者不重复，D 判「图形 vs 主体」，C4 判「图形 vs 图形」。

### 残留待处理（归入 C3）
footprint 若允许动画中途变化（元素从角落滑到中央），静态矩形无法表达。倾向要求 **footprint 取全动画期最大包围盒**；item 可声明 `footprintAnimates: true` 降级为 warning。

## 追加会话：C6 封口 —— C 分支整体完成

用户裁决：读完 C6 详解后四条全部认可（① 禁用 Series + 双层 Sequence ② z 序靠 DOM 嵌套不用 zIndex ③ 载体类走独立背景链 ④ 三条工程约束接受）。

### C6 三条核心机制
1. **禁用 `<Series>`** —— 其语义是「依次播放」，内部自动把后一个 Sequence 起点算成前一个终点，**结构上无法表达重叠**，与硬约束 3 直接冲突。用 Series 生成的 storyboard 必为串行，是语义级错误
2. **双层 Sequence 坐标转换** —— 外层 `from=trackStart`（min of items），内层 `from=item.fromFrame − trackStart`。外层存在的意义是把绝对帧转成轨道内相对帧，理由与 C5 否掉 item 层 handoffFrom 相同
3. **z 序 = DOM 嵌套顺序**（`<AbsoluteFill>`），不用显式 `z-index` —— 因 `transform` 会创建新层叠上下文，「设了 999 却因父级 transform 失效」极难排查
4. **载体类（subject-transform/footage-transform）与叠加类必须分栈** —— 前者作用在视频元素上、**串联**（裁切→缩放→再裁切）；后者在画面之上、**并列**。混栈会导致语义倒置

### 细写时新发现的三条工程约束（此前无任何决策覆盖）
| 约束 | 裁决 |
|------|------|
| **composition 尾部截断** | item 结束帧超 composition 时长，Remotion **静默截断不打日志** → resolver 必须校验报 error（用户认定不可省） |
| **fps 与烘焙绑定** | 改 fps 会让全部已烘焙 fromFrame 语义漂移 → 顶层固化 fps，改 fps 必须重新烘焙 |
| **Sequence API 随版本变** | premount/绝对定位要求随版本不同 → E 分支锁版本后回填 |

### 我上一轮的判断错误（重要教训）
我把 GSAP 和 CSS animation 归为一类「会自己走的动画」并要一并禁掉 —— **归类错了**。

**正确的红线表述**：不是「禁用某个库」，而是「**任何动画的推进权必须属于 frame，不能属于库自己的 ticker**」。

GSAP 完全能做：
```js
const tl = gsap.timeline({ paused: true });
tl.to(el, { opacity: 1, duration: 0.3 });
tl.progress(frame / durationInFrames);   // 纯函数式 seek
```
甚至可只作值计算器：`gsap.parseEase("power2.inOut")(progress)`。

**真正的禁止清单（5 条，均可 lint 静态检查）**：
| 禁止 | 原因 |
|------|------|
| Date.now() / performance.now() | 墙钟时间 |
| Math.random() | 须固定种子 mulberry32 |
| CSS animation / transition | 自走动画，渲染闪烁 |
| R3F 的 useFrame() | 墙钟驱动 |
| GSAP 非 paused ticker | 同上 |

**选型分层依据**（官方注释）：simple cases 优先原生 `interpolate()`；需要 SplitText / MorphSVG / MotionPath / CustomEase 时才引入 GSAP。

### 核心洞察：遮挡容忍度不是标量，是向量
人脸遮挡 = 内容失效（零容忍）；手持物遮挡 = 失去「他手里拿什么」这层信息（轻遮可忍）；躯干背景遮挡 = 几乎无影响。
**用单一「最大遮挡比例」处理，语义上必然出错** —— 要么把产品挡太多（违反 B-roll 诉求），要么放松到人脸也被挡（违反硬约束 1）。

### D2 裁决：区域分级 + 令牌预算制
| 区域 | 遮挡预算 | 判定方式 |
|------|---------|---------|
| 人脸/头肩 | **0%** | person bbox 上部 + 关键点检测 |
| 手持物 | **≤20%** 面积 | 手部关键点邻域 + 局部显著性，shot 级累积 |
| B-roll 主体 | **≤30%** 面积 | shot 级显著性峰值区 |
| 其余 | 无限 | — |

**校验方式**：不是判「有没有相交」，而是算「各级区域各被占多少额度」，总和超预算才报错。

**安全区推导三原则**：① 安全区取 bbox 上部而非整个 bbox（腿部以下可压，全 bbox 禁区会过度收紧）② 按 shot 取并集不逐帧跟随（让 motion 可行域在 shot 内稳定，否则动效跟人一起飘，与硬约束 3 冲突）③ 主体不在场的 shot 安全区为空（无主体即无遮挡问题，硬约束 1 的自然推论）

### D4 裁决：冲突自动载体降级
「缩放到载体里播 motion」不是独立选项，而是**冲突时的确定退路**：
```
冲突 →①同预算内挪 footprint →②挪不动则自动切 carrier 模式 →③仍冲突才报错
```
**意义**：把「遮挡多少」从「必须精确的答案」变成「可调的偏好」。阈值可放宽（冲突时走载体）也可收紧。
载体模式原是硬约束 2 内容，此处从「设计选项」升级为「冲突自动解法」。

### D5 裁决：手持物 shot 级时间累积
「小物品、变化不大」→ 从**实时跟踪难题降级为镜头级累积统计**。
逐帧跟踪会因手指交叠/换手剧烈抖动；shot 内累积天然抗噪。检测不稳时在 B2 编辑页人工框选覆盖。

### D3 裁决：fullscreen 一律人工确认
无自动放行规则（carrier 模式生效时例外）。
