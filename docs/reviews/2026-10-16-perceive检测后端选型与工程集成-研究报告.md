## 引言

VideoPipeline 项目需在实拍口播视频上叠加 motion-graphic overlay，其 `02-perceive` 阶段要以纯 Node.js 实现对每秒抽样帧的人脸、手持物与 B-roll 主体的离线检测——这是当前管线的唯一硬阻断点。项目既定的一组工程定案（全 Node 不引 Python 运行时、CPU 离线、Windows 换机可移植、失败必须显式报错且模型不入库）并非普通需求清单，而是一台强力设计过滤器：`onnxruntime-node` 向 Windows x64 提供 MIT 许可的预编译二进制、开箱即用（[onnxruntime-node](https://www.npmjs.com/package/onnxruntime-node)），而 Ultralytics YOLO 全系的 AGPL-3.0 网络条款则直接封杀了主流姿态/检测权重在闭源商用场景的可用性（[Ultralytics License](https://www.ultralytics.com/license)）。

本报告在这组约束下回答三个问题：哪些候选能通过过滤、各条路线在 Node 侧是否具备工程可行性、最终应如何组合落地并控制风险。全文共五章：第 1 章厘清硬约束的过滤作用并确立七维评判基线；第 2 章评测 YuNet、RTMO/RTMPose 与 MediaPipe 三条路线的 Node 可行性；第 3 章按 face／pose→主体／handheld·broll 三类目标做选型取舍；第 4 章给出集成、glue 自研与模型管理方案；第 5 章收敛许可边界、失败模式与确定性验证计划。

核心发现先行：其一，Node 可行性呈递减梯度——YuNet（中高）> RTMO/RTMPose（中）> MediaPipe（不可行），后者因官方仅支持浏览器环境而出局；其二，三类目标均应采用"够用即可"的精度档（人脸主选 YuNet，权重约 230KB 且为 MIT，见 [OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)），把算力预算投向失败处理与时间累积；其三，全部候选均无现成端到端方案，真正的工作量是自研并验证预处理/解码 glue——这是本项目的核心工程风险。

## 1. Node 侧 CPU 离线感知的硬约束与候选模型谱系

**本章论点**：本项目的六条显性工程定案（外加一条隐含的许可合规约束），并非并列的"要求清单"，而是一组**强力的设计过滤器**——它们先于任何模型评测，就淘汰掉了大部分市面候选。理解每条约束"过滤掉了什么"，是理解后续章节为何只剩少数候选可评的前提。

### 1.1 硬约束的过滤作用

**约束一：全 Node（onnxruntime-node，不引 Python）。** 该约束直接淘汰所有 Python-only 实现。首当其冲的是 **MediaPipe 官方包**——Google 的 `@mediapipe/tasks-vision` 官方定位为**浏览器 Web**，其文档明确面向"web applications"，依赖 CDN 加载 wasm 与浏览器 Canvas；社区要让它在 Node 跑，只能用 Playwright 起无头 Chromium 桥接（如 `mediapipe-nodejs`），既重又脆弱（[mediapipe-nodejs](https://github.com/beenotung/mediapipe-nodejs)）。同理，MMPose/MMDeploy 的**导出流程**是 Python（用于产出 ONNX），但**推理运行**可留在 Node——这一区分是本项目能保留 RTMO/RTMPose 路线而不违反"全 Node"的关键：Python 只作为**一次性模型导出工具**存在于开发机，不进运行时。

**约束二：CPU 离线、无 GPU。** 过滤掉一切默认依赖 CUDA/TensorRT 的部署路径，也把"服务式 API"（需联网调用云端模型）彻底排除。这使模型选型被压向**轻量级 + 单帧 CPU 可接受**的区间；对 1 秒/帧的批处理口径，"几十毫秒/帧"即可满足。

**约束三：换机可移植、Windows 可跑、安装成本低。** 过滤掉需要本地编译原生扩展、或拖垮环境的重依赖方案。`onnxruntime-node` 官方即向 **Windows x64 提供预编译二进制**（CPU，NAPI_v3），开箱即用、MIT 许可（[onnxruntime-node](https://www.npmjs.com/package/onnxruntime-node)）；反观 MediaPipe 方案需处理 `vision_wasm_internal.wasm` 缺失、版本错配等安装坑，与"换机可移植优先"直接冲突。

**约束四：确定性可复现。** 过滤掉含随机性、或会因图优化引入数值漂移而不自知的方案。ONNX Runtime 的图优化在个别模型上可能导致结果退化甚至"空输出"，需靠 `ORT_ENABLE_BASIC`/`ORT_DISABLE_ALL` 兜底（[ORT 图优化文档](https://mintlify.wiki/microsoft/onnxruntime/concepts/graph-optimizations)）；这要求选型时将**固定输入尺寸、固定执行提供者、可校验的输出**纳入基线。

**约束五：模型文件不入库。** 过滤掉无法通过脚本稳定下载并校验的模型。这推动选型偏向托管于 HuggingFace/GitHub Releases、有 SHA-256 可校验、许可证清晰的模型（详见第 4 章）。

**约束六：失败必须显式报错（M-4）。** 过滤掉任何"静默降级/空结果"的兜底式方案，也即**排除了用 VLM/大模型替代检测**的取巧路线——检测率不足时必须抛出错误，而非给一个空 region。这条约束对候选模型提出"能明确区分 0 张脸 vs 检测失败"的要求。

**约束七（隐含）：许可合规。** 这一条把**整个 YOLO 系排除出候选**：Ultralytics 的 YOLOv5/v8/YOLO11/YOLO26 **全系 AGPL-3.0**，含网络条款，闭源商用须购企业授权（[Ultralytics License](https://www.ultralytics.com/license)）。项目 M-2 备选的 `YOLO26n-pose`（[Ultralytics YOLO26](https://docs.ultralytics.com/models/yolo26)）正踩此红线，故仅作对照项，不作正选。同样被许可过滤的是 **SCRFD/InsightFace 系**——其代码虽 MIT，但**预训练权重明确限"非商业研究用途"**，商用需另获授权（[Eden AI 2026](http://edenai.co/post/top-free-face-detection-tools-apis-and-open-source-models)）。

### 1.2 服务场景与产物契约

感知阶段服务的是"实拍口播视频 + motion-graphic overlay"管线，**按秒抽样**（不追求逐帧跟踪）。产物 `regions.json` 中每个区域至少含：`kind`（**face | handheld | broll**）、归一化 box、`confidence`、`source`（模型/版本/抽样帧）、`shotId` 与时间范围、`lowConfidence` 标记。目标口径是**非对称的**：人脸绝不可被覆盖（漏检代价极高），手持物与 B-roll 控制在预算内（可容忍一定误差）。这一非对称性意味着**人脸检测必须优先保召回**，而 handheld/broll 可接受更宽松的触发阈值。

### 1.3 候选模型谱系

**人脸检测**：YuNet 是当前最优起点——OpenCV Zoo 官方权重仅 **~230KB**（2023mar）/ ~0.2MB（2026may 动态输入版），MIT 许可，5 点关键点，可检测 10×10~300×300 像素人脸（[OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)）。第三方基准（i7-12700K, ONNX Runtime, 320×320）测得 YuNet AP_hard 0.811、FPS 456（[face-clustering 技术选型](https://github.com/duanyunlun/face-clustering-service/blob/main/docs/technical-options.md)）。SCRFD 精度略高（10G: WIDER Easy/Med/Hard = 95.16/93.87/83.05）但**权重非商用**（[uniface Model Zoo](https://yakhyo.github.io/uniface/models)）；RetinaFace 精度相当但体积更大（MobileNet 1.7–3.8MB，ResNet50 达 104MB）（体积数据见 [uniface Model Zoo](https://yakhyo.github.io/uniface/models)），许可随实现而变。

**人体姿态**：RTMO（单阶段，无需人体检测器）与 RTMPose（两阶段 top-down）同属 OpenMMLab，模型库覆盖 t/s/m/l/x 五档；RTMPose-m 在 i7-11700 CPU 上单人次延迟 **11.1ms**，RTMPose-s 仅 4.5ms（[Fora Soft 2026 对比](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/openpose-mediapipe-rtmpose-pose-tracking)）。RTMO-l 达 COCO 74.8% AP、ONNX 推理 19.1ms（V100）（[MMPose RTMO](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmo)）。MMPose 系代码与 checkpoint 一般标 **Apache-2.0**，但需注意社区对"权重受 COCO 等数据集限制、商用需确认"的提示（[SpriteFrameStudio](https://gitee.com/andangel/SpriteFrameStudio)）——此点列为第 5 章待核项。MediaPipe Pose（BlazePose）提供 lite 3MB / full 6MB / heavy 12–26MB 三档、33 关键点，但受 Node 约束限制（[BlazePose 模型卡](https://developers.google.com/ml-kit/images/vision/pose-detection/pose_model_card.pdf)）。YOLOv8n-pose 约 3.3M 参数、CPU ONNX 131.8ms/帧，但 **AGPL-3.0**（[Ultralytics pose 基准](https://github.com/woodyring/ultralytics)）。

**手部**：MediaPipe Hand 提供 21 关键点/手，社区已有 ONNX 导出（Qualcomm `MediaPipe-Hand-Detection.onnx`、Luxonis hand-landmarker，均 Apache-2.0，检测器 6.76MB / 关键点 7.71MB）（[Qualcomm](https://huggingface.co/qualcomm/MediaPipe-Hand-Detection), [Luxonis](https://models.luxonis.com/luxonis/mediapipe-hand-landmarker)）。MMPose 亦提供 RTMPose-m Hand（256×256, 21 点, COCO-WholeBody-Hand 81.5 PCK@0.2）（[MMPose 模型库](https://mmpose.readthedocs.io/en/latest/model_zoo/hand_2d_keypoint.html)），常配 RTMDet-nano 手部检测器。

**手持物 / B-roll 主体**：无专用模型，候选方向为通用目标检测 + 经典显著性。RTMDet（Apache-2.0）最契合——tiny 40.9 mAP、m 49.3–51.7 mAP，且 RTMDet-s 仅 **~3MB** 可作轻量人体/人物检测器（[Qualcomm RTMDet](https://aihub.qualcomm.com/compute/models/rtmdet), [Harvard RTMW3D](https://mmla.gse.harvard.edu/tools/rtmw3d)）。媒体侧另有 OpenCV 经典显著性（StaticSaliencySpectralResidual/FineGrained）作纯 CPU 兜底。

**运行时层（对照）**：`onnxruntime-node`（MIT，预编译 Windows CPU 二进制）为正选运行时；`MediaPipe Tasks Vision`（Apache-2.0，浏览器优先，Node 需桥接）（[@mediapipe/tasks-vision](https://www.npmjs.com/package/@mediapipe/tasks-vision)）与 `Python sidecar`（M-2 已否）作对照项（[onnxruntime-node](https://www.npmjs.com/package/onnxruntime-node)）。

### 1.4 评判基线

综合项目既有约定（shotcraft §8.6），本章确立七维统一比较清单，供第 2 章逐路线评测：**① Windows 安装成本；② CPU 耗时（单帧/单人次）；③ face·hand·pose 输出质量；④ 许可证（可商用性）；⑤ 模型体积；⑥ 是否需 GPU；⑦ 失败时能否产出明确错误**。本项目视角下的**通过条件**为：可 `npm install` 即用、CPU 单帧 ≤ 数百毫秒、许可可商用（Apache/MIT）、模型可脚本化下载校验、且检测率为零时能显式报错。任一维度不达标即出局——这解释了大量"技术上很强"的模型为何未进候选。

### 1.5 小结

六条显性硬约束，外加一条隐含的许可合规约束，共同构成一台**设计过滤器**：许可条款淘汰了 YOLO 全系与 SCRFD 权重，运行时条款淘汰了 Python sidecar 与 MediaPipe 官方 Node 路径，可移植/确定性/显式失败条款则把候选压向"轻量 ONNX + onnxruntime-node"这一窄带。最终通过筛选进入逐路线评测的，是人脸 YuNet、姿态 RTMO/RTMPose、手部 MediaPipe-Hand-ONNX / RTMPose-Hand、手持物 RTMDet，共四条路线——其中人脸与姿态两线在第 2 章评测、手部与手持物两线在第 3 章评测；它们的共同特征是 Apache/MIT 许可、体积可控、CPU 可跑，且**均需自研预处理/后处理 glue**（承第 4 章）。

## 2. YuNet、RTMO/RTMPose 与 MediaPipe 三条路线在 Node 侧的工程可行性证据

**本章论点**：第 1 章确立了七维基线与四条候选路线（人脸 YuNet / 姿态 RTMO/RTMPose / 手部 MediaPipe-Hand-ONNX·RTMPose-Hand / 手持物 RTMDet）。本章评测其中**两条候选路线**——人脸 YuNet、姿态 RTMO/RTMPose——的 Node 可行性，并对照评估**两条运行时路线**——MediaPipe Tasks Vision 与 Python sidecar；手部与手持物两条候选路线的评测见第 3 章。结论先行——**上述路线的 Node 可行性呈递减梯度：YuNet（中高）> RTMO/RTMPose（中）> MediaPipe（低，实为不可行）**；而共同的致命短板是：**截至检索时点，本章评测的路线中没有任何一条存在公开的、纯 onnxruntime-node 的端到端案例**。换言之，可行性判定的对象不是"有没有现成库"，而是"自研 glue 的工作量与风险是否可控"。

### 2.1 路线一：YuNet ONNX → onnxruntime-node（证据强度：中高）

**I/O 契约已明确（事实）**。OpenCV Zoo 的 `face_detection_yunet_2023mar.onnx` 为固定输入；`face_detection_yunet_2026may.onnx` 为动态输入版，**明确为兼容 ONNX Runtime 引擎而重导出**（H/W 改为符号维度）（[OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)）。其 I/O 契约经第三方在 onnxruntime CPU 上冒烟验证：输入 `input` float32 `[1,3,H,W]`，输出 12 个张量——`cls/obj/bbox/kps` 各 3 档 stride（8/16/32），锚点数 1600/400/100，opset 11（[HF skillsafe-ai/yunet](https://huggingface.co/skillsafe-ai/yunet)）。这直接证明**模型可在 onnxruntime 载入并前向**。

**预处理/解码需自研（事实 + 推断）**。与 opencv-python 的 `cv.FaceDetectorYN`（封装了预处理+后处理）不同，Node 侧没有等价封装，必须复刻：① BGR 通道序、**无 mean/std 归一化**（原始 0..255），H/W 取 32 倍数（[`@genrwork/face` 文档](https://www.npmjs.com/package/@genrwork/face)）；② 解码 `score=sqrt(clamp(cls)*clamp(obj))`、box 中心 `(col+dx,row+dy)*stride`、`w/h=exp(·)*stride`，每格 1 anchor、不套 sigmoid。上述解码逻辑已有**逐行移植自 OpenCV C++ 的公开实现**（`@genrwork/face` 的 `decodeYunet`），但其自述**未经真实权重验证、且标记 web-only**——可直接借鉴公式，却**不能直接用于 onnxruntime-node**。

**社区案例缺口（决定性负面证据）**。检索范围：**GitHub 代码搜索、npm 与 Google 网页检索**三渠道，关键词组合为 `onnxruntime-node` 分别搭配 `YuNet` / `face_detection_yunet` / `yunet`（并含 `node`），时间窗**截至 2026-10**。在此范围内，得到的 Node 端人脸检测案例**全部是 SCRFD 或 RetinaFace**，而非 YuNet：例如 `ppu-uniface-demo` 用 onnxruntime-node + SCRFD 构建人脸检测/识别 API（[ppu-uniface-demo](https://github.com/PT-Perkasa-Pilar-Utama/ppu-uniface-demo)），另有 RetinaFace + onnxruntime-node 的服务化示例（[CSDN](https://blog.csdn.net/weixin_42518874/article/details/158915374)）。**未检索到任何 YuNet 在 onnxruntime-node 上的公开端到端案例**。这既说明 glue 稀缺，也从侧面说明"YuNet 的 ONNX 可用"尚属**逻辑可行、未经社区实证**。

**验证路径（建议的最小验证）**：载入 2026may 动态版 → 自研 yunetPreprocess + decodeYunet 移植 → 用 OpenCV/onnxruntime-python 的同图结果做**逐框对齐**（cross-check），确认 FPS 与 AP 后可定为通过。**定级"中高"的依据（权重透明）**：①**模型可跑——已证**（I/O 契约经第三方在 onnxruntime CPU 上冒烟验证）；②**解码公式——有据**（存在逐行移植自 OpenCV C++ 的公开实现可借鉴）；③**端到端——未证**（无 onnxruntime-node 公开案例，glue 尚未经本项目实测）。三项中"已证/有据"占其二，缺的只是"最后一公里"的实证——**风险可控而非有现成方案**。

### 2.2 路线二：RTMO/RTMPose → onnxruntime-node（证据强度：中）

**导出流程（事实）**：RTMO/RTMPose 的 ONNX 由 **MMDeploy 的 `tools/deploy.py` + `pose-detection_*_onnxruntime_dynamic*.py`** 配置导出，导出 RTMO 需 PyTorch 1.12+ 与 mmdeploy main 分支（[MMPose RTMO](https://github.com/Vujos/mmpose/tree/05ed0a0e82ded68511b742bb57bbb3162255b4ec/projects/rtmo)）。这一 Python 流程**只在开发机一次性执行**，产物 `end2end.onnx` 供运行时 Node 使用——不违反"全 Node 运行时"。注意：官方导出的 ONNX **尾部含 NMS 算子**，且输出结构为 `dets[1,N,5]` + `keypoints[1,N,17,3]`，LayerNorm 在 opset 11 下会被拆分，部分引擎兼容性差（[导出避坑指南](https://blog.csdn.net/fern8/article/details/155050875)）——这些是**导出侧**的坑，与 Node 运行时无关，但会增加交付物复杂度和跨机复现难度。

**后处理 = SimCC 解码（事实）**：RTMPose/RTMO 输出两轴 1D 分布，解码为 argmax + 亚像素抛物线插值，再经 `scale/center` 还原坐标（[OpenMMLab 样例](https://github.com/open-mmlab/OpenMMLabCamp/discussions/233)）。相比热图，SimCC 后处理**更简单**（无需找峰值+细化 2D 热图），但仍需**在 JS 复刻**，且 `scale_x/scale_y`（约 1.2/1.28）随版本变化，需打印张量 shape 确认。

**RTMO-ORT 参考项目：解决了什么、没解决什么（决定性证据）**。`namas191297/rtmo-ort` 是"纯 ONNX Runtime 的 RTMO 推理 + CLI"，提供 `PoseEstimatorORT(onnx, device).infer(img)`，模型经 GitHub Releases 分发（[RTMO-ORT](https://github.com/namas191297/rtmo-ort)）。**但它是 Python 包（`pip install rtmo-ort[cpu]`），API 与 CLI 均为 Python，无任何 JS/Node 绑定**。因此它解决的是"脱离 MMPose/MMDeploy 依赖运行 RTMO ONNX"，**没解决**"在 Node 里跑"——它的预处理（letterbox/resize）、SimCC 解码、坐标映射逻辑**可作为 JS 移植的权威参照**，但移植工作仍需本项目自担。

**CPU 性能（事实）**：RTMPose-m 在 i7-11700 上单人次 11.1ms、RTMPose-s 4.5ms（[Fora Soft 2026](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/openpose-mediapipe-rtmpose-pose-tracking)）；RTMO-l ONNX 19.1ms（V100，GPU）——CPU 单帧几十毫秒，对 1fps 抽样口径**充裕**。定级"中"的理由：许可干净、ONNX 可用、性能足够，但**无 JS 端案例、后处理需自研**，且导出链较重。

### 2.3 路线三：MediaPipe Tasks Vision（证据强度：高——不可行）

**官方立场原文（决定性证据）**：Google MediaPipe 官方 issue #4800 中，维护者 schmidt-sebastian 明确写道：**"We currently only support browser environments and don't have testing infrastructure that can validate that our libraries work in Node."**（我们当前只支持浏览器环境，且没有能力验证库在 Node 中工作）。同一 issue 中多名用户报告 Node 下报错 `document is not defined` / `ReferenceError: self is not defined`（[mediapipe issue #4800](https://github.com/google-ai-edge/mediapipe/issues/4800)）。官方 Web 设置文档也仅列 Chrome/Safari 为支持环境（[MediaPipe Setup Web](https://developers.google.cn/edge/mediapipe/solutions/setup_web)）。

**桥接成本与脆弱性（事实）**：社区唯一可行方案是 `mediapipe-nodejs`——用 Express 起本地服务 + Playwright 无头 Chromium 执行浏览器端 API（[mediapipe-nodejs](https://github.com/beenotung/mediapipe-nodejs)）。这意味着运行时**捆绑一个 Chromium**，安装体积与换机成本极高，且与"换机可移植、安装成本低"约束直接冲突。已知坑还包括 `vision_wasm_internal.wasm` 缺失、wasm 版本错配、module worker 中 `importScripts` 不支持等。定级"高（不可行）"：官方原文即判死刑，无需进一步验证。

### 2.4 对照项：Python sidecar（M-2 已否，闭环）

sidecar 路线（Node 主进程 + 常驻 Python 推理进程）在工程上有真实代价：**独立进程本身即是一种故障隔离，但子进程崩溃必须由主进程显式监听其 `exit`/`error` 事件（或另加健康检查/看门狗）才能被感知，否则崩溃对主服务并不透明；此外常驻推理进程还会与本机其他进程争抢内存/CPU，且日志分散于 JS 与 Python 两处**（[Node.js child_process 文档](https://nodejs.org/api/child_process.html)）；架构对比研究亦指出，进程内 ONNX 以原生插件（native addon）形式在同一进程执行、省去跨进程通信与序列化开销，代价则是与主进程共享内存、缺乏隔离（[LPNU 边缘推理框架对比研究](https://science.lpnu.ua/sites/default/files/journal-paper/2025/nov/41049/vse-113-118.pdf)）——就延迟与内存而言，进程内推理通常优于外部 sidecar（此为**工程经验判断**，未依赖具体基准数字）。叠加"用户会换电脑跑、安装成本要低"的约束，sidecar 引入的 Python 环境（conda/venv + Torch/MMCV）正是 M-2 要规避的"无法维护的大型 Python 环境"。**M-2 的否决理由在此闭环。**

### 2.5 小结与共性风险

三条路线的 Node 可行性梯度为 YuNet（中高）> RTMO/RTMPose（中）> MediaPipe（不可行）。但必须指出**共性风险**：**三者均无现成 onnxruntime-node 端到端案例**——YuNet 只有 web-only 的解码移植（未验证），RTMO 只有 Python 的 RTMO-ORT（无 JS），MediaPipe 官方直接不支持 Node。这意味着本项目的核心工作**不是"选一个库"，而是"自研并验证一套 glue"**（预处理+解码+NMS+坐标映射+失败处理，详见第 4 章）。这一认知应在决策时明确：可行性 = 模型可跑（已证实） × glue 可写（高置信） × **结果可验证（尚待本项目的 cross-check 实验，列第 5 章）**。

## 3. 人脸、人体姿态与手持物/B-roll 三类感知目标的候选匹配与选型取舍

**本章论点**：第 1 章回答了"约束过滤后剩什么"，第 2 章回答了"能不能在 Node 做成"；本章切换**任务维度**——针对每一类检测目标（face / pose→主体 / handheld·broll），在既定候选池内做**横向取舍**，给出"主选 + 备选 + 弃选理由"，并说明三类目标的**非对称精度预算**如何映射到阈值、抽样与 `regions.json` 输出。

### 3.1 人脸（face）：YuNet 主选 + 安全区构建

**取舍依据：精度 × 体积 × 许可三角（事实 + 分析）**。人脸路线的候选是 YuNet / RetinaFace / SCRFD 三者。SCRFD 精度最高（10G：WIDER Easy/Med/Hard = 95.16/93.87/83.05）但**权重限非商业研究**，直接违反许可约束（[Eden AI 2026](http://edenai.co/post/top-free-face-detection-tools-apis-and-open-source-models)）；RetinaFace 精度相当但体积大（MobileNet 1.7–3.8MB、ResNet50 达 104MB）（[uniface Model Zoo](https://yakhyo.github.io/uniface/models)）。YuNet 以 **~230KB、MIT 许可、可检测 10×10~300×300 像素人脸** 胜出（[OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)）。**需明确一点**：本项目人脸精度需求是"框定安全区以避免覆盖"，而非身份识别或活体——**AP_hard 0.81（YuNet）与 0.83（SCRFD）的 2pp 差异（注：二者来自不同基准——YuNet 取自[独立第三方基准](https://github.com/duanyunlun/face-clustering-service/blob/main/docs/technical-options.md)、SCRFD 取自 uniface，属跨基准对比，仅供量级参考），在"每秒抽样 + 全时段并集"的安全区口径下几无工程意义**，因此放弃精度更高但许可/体积更差的方案，是合理的工程取舍。

**安全区构建方法：全时段并集（事实 + 项目口径）**。依据项目内部调研《video-talkcraft 调研与对比》§6.1 的实证口径（注意：该文档与另一份《video-shotcraft 多维对比与 VideoPipeline 提升方案》为**两份不同文档**）：**每秒采样一帧、取每帧最高置信度脸、对全时段做并集、并外扩安全边距（上方 60%、左右 20%、+30px）**。此方法与业界通行做法一致——将各帧检测框扁平化后取 `min(top-left)` / `max(bottom-right)` 生成一个覆盖"人脸曾出现过的所有位置"的单一静态矩形（union bounding box），且**跳采（只在少数采样帧上检测、再用时间聚合覆盖其间的帧）依然可靠**，因为平滑移动的脸的**极端位置**不会被跳过。学界近年已将该思路系统化：UCLA 的 **MBAM（multi-frame bounding-box aggregation masking）** 通过"在时间窗内聚合各帧检测框 + 把任一检出传播到该窗内所有帧"显著降低漏检，并配合"跳帧/周期性上下采样注入时间多样性"在低检测率下维持高召回（[MBAM, UCLA/IROS](https://ssysarch.ee.ucla.edu/files/26_MultiframeMasking_IROS.pdf)）。这为"每秒抽样而非逐帧"提供了直接佐证。

**风险与"显式报错"口径（事实 + 分析）**：安全区口径的致命风险是**漏检被静默吞掉**。业界共识是将此类系统设计为 **fail-closed**——以"漏检率、泄漏帧、覆盖率"作为验收指标，容量/覆盖率不足时**抛错并提示人工补区**，而非放行原始帧（[AlgoFace 面部脱敏实践](https://www.algoface.ai/face-redaction-privacy-by-design)，其框架引用 NIST 隐私框架与 NISTIR 8053）。某隐私视频产品的具体实现可作范式：导出前用 `FaceCoverageValidator` 沿与跟踪器**相同的抽样网格**复盘时间线，覆盖率低于硬阈值即**拦截导出并要求人工补区**（该产品自述失败路径**不允许任何未覆盖帧**；其具体阈值属**实现自述，标注为实践参考、待核**）（[blurrd.xyz](https://www.blurrd.xyz/blog/safe-faces-so-far)）。这**正面印证 M-4**：检测率低必须显式报错而非静默给空区。

### 3.2 人体姿态（pose）→ 主体区域

**RTMO vs RTMPose 的匹配度（事实）**。两者同源（OpenMMLab），架构取舍相反：RTMPose 是**两阶段 top-down**（先人体检测、再逐人估姿态），**延迟随人数线性增长**，但**单人场景最快**；RTMO 是**单阶段**，**无需独立检测器**，延迟几乎不随人数变化。RTMO 论文原文结论：**在 ONNXRuntime 下，RTMO 约在 4 人时与 RTMPose 速度持平；在 TensorRT FP16 下，≥2 人时 RTMO 更快**（[RTMO 论文](https://arxiv.org/html/2312.07526v1)）。工程经验法则（**实践参考**）：**≤2 人偏 RTMPose，≥4 人偏 RTMO，拥挤遮挡场景偏 RTMO**（[Billy Tse 对比](https://www.billytse.dev/blog/rtmo-one-stage-realtime-multi-person-pose-estimation)）。

**对本项目的映射（分析）**：口播视频通常是**单人为主**场景，按经验法则应偏 RTMPose；但本项目的姿态用途是**主体位置/安全区**（每秒抽样、非逐帧跟踪、非动作分析），因此 **RTMO 的"单模型、无检测器"简化价值可能高于其精度差异**——少维护一个 RTMDet 检测器即减少一处失败面。**精度档位**：既然不用于动作分析，**t/s/m 低档位即可**（RTMPose-m CPU 单人次 11.1ms，档位选择可参照 [Fora Soft](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/openpose-mediapipe-rtmpose-pose-tracking)）。

**"姿态做主体框" vs "人脸框 + 外扩"（分析）**：业界混合范式是**宏观-微观两段**——先用轻量检测框（macro）定位人，再对裁剪区域跑姿态（micro），可省算力（该范式在动作分析社区的实践讨论，**实践参考**，[Train Matricx](http://trainmatricx.com/blog/skeletal-vs-bounding-boxes-sports-ai)）；FreeMoCap 的 "YOLO cropping" 即用人体检测框裁 ROI 再喂姿态，代价是**约翻倍的耗时**，仅在主体较小/误检多时启用（[FreeMoCap](https://freemocap.github.io/documentation/yolo-cropping.html)）。对本项目：**若人脸框已由 YuNet 稳定给出，则"人脸框 + 外扩即主体区"几乎零边际成本**；姿态框（骨架外接框）更贴合躯干/手部但有额外算力与后处理成本。**建议：人脸框外扩为主，姿态为按需增强**（例如需要手部/躯干精确区时）。

### 3.3 手持物（handheld）与 B-roll 主体

**组合式取舍（事实 + 分析）**：无 turnkey 方案，采用"主 + 兜底"组合。**主选 RTMDet（通用检测，Apache-2.0）** 做人物/常见主体检测（[Qualcomm RTMDet](https://aihub.qualcomm.com/compute/models/rtmdet)）；**兜底用经典显著性**。但显著性有明确局限：OpenCV saliency 模块被实测评价为"**效果都很差，只能用于简单场景**"，其中 `StaticSaliencySpectralResidual` 最快（768×576 单帧 **3.2ms**）但精度最差，`StaticSaliencyFineGrained` 效果较好但单帧达 **119.2ms**（[cfanz 实测](https://cfanz.cn/resource/detail/rGOoopJZLvYwR)，**实践参考、待核**）——**故显著性只宜作低成本的粗筛/兜底，不宜作主判据**。

**手持物 RTMDet 的评测要素（事实 + 缺口）**：与第 2 章三条路线同格式给出——
- **可行性（事实）**：RTMDet 为单阶段通用检测器，可导出 ONNX、经 onnxruntime-node 载入前向（与 RTMO/RTMPose 同一运行时路径）；**许可 Apache-2.0**（OpenMMLab），可商用；**体积可控**——RTMDet-s（COCO 80 类通用检测）约 **~3MB**（浏览器端 ONNX Runtime Web 亦以 RTMDet-s 作人物检测器）（[Harvard RTMW3D](https://mmla.gse.harvard.edu/tools/rtmw3d)）。它做的是"**类**-level"通用检测（人物/常见主体），而非手持物专属类别。
- **证据强度：中**。
- **决定性证据**：RTMDet 已在浏览器内 ONNX Runtime 上作为人物检测器稳定运行（RTMW3D 管线），证明其 ONNX 推理链路成熟（[Harvard RTMW3D](https://mmla.gse.harvard.edu/tools/rtmw3d)）。
- **缺口**：**无手持物专属模型**——RTMDet 只能给"人物/常见物体"框，拿不到"手持物"这一语义，故必须与姿态手腕点组合（见下）；RTMDet 存在一例公开的 JS/onnxruntime-node 移植参照（**单项目实证、待核**，详见第 4 章 §4.3），**本章其余候选仍无公开端到端案例**。

**用手腕关键点定位手持物（事实，来自 SHOP 论文）**：学术上已有成熟范式——先人体姿态估计取 **wrist 关键点作为手持物 ROI 中心**，用**头径（约 19.8cm）作尺度因子**换算像素距离，只保留距手腕约 18cm 内的检测以滤误报；**手腕被遮挡时回退用 elbow 作中心**（[SHOP, arXiv:2203.15228](https://arxiv.org/pdf/2203.15228)）。该论文观点明确：**基于手腕比直接检测手更稳**（手易被持物遮挡、姿态多变）。这为"用姿态手腕点 + 目标检测"组合提供权威依据。

**手部检测两候选的评测与取舍（事实 + 分析）**：手持物定位的另一条思路是"直接跑手部关键点模型"。两条候选与第 2 章同格式评测如下——
- **`MediaPipe-Hand-ONNX`（证据强度：中）**：MediaPipe Hand 提供 **21 关键点/手**，社区已有 ONNX 导出——Qualcomm 版本检测器 **6.76MB** / 关键点 **7.71MB**、Luxonis 版本为 **224×224 hand-landmarker**，**均 Apache-2.0**（[Qualcomm](https://huggingface.co/qualcomm/MediaPipe-Hand-Detection), [Luxonis](https://models.luxonis.com/luxonis/mediapipe-hand-landmarker)）。**可行性**：ONNX 格式理论上可走 onnxruntime-node；**缺口**：**无公开的 JS/Node 端到端案例**，预处理/后处理需自研（与全报告共性风险一致，如实标注）。
- **`RTMPose-m Hand`（证据强度：中）**：**256×256、21 关键点、COCO-WholeBody-Hand 81.5 PCK@0.2**（Hand5 集 96.4 PCK@0.2），常配 **RTMDet-nano** 手部检测器；代码与权重一般标 **Apache-2.0**（数据集商用限制见第 5 章待核项）（[MMPose 模型库](https://mmpose.readthedocs.io/en/latest/model_zoo/hand_2d_keypoint.html)）。**可行性**：同为 ONNX 路线，可经 onnxruntime-node 载入；**缺口**：同样**无 JS 端端到端案例**，且需同时维护"手部检测器 + 手部关键点"两个模型。
- **与"手腕点"方案的关系与取舍（分析）**：SHOP 论文已证**从姿态得到的 wrist 点足以承担手持物 ROI 定位**（且比直接检测手更稳）——这意味着手部模型（21 关键点）的**增量价值主要在"更精细的手部区域/手势语义"，而非"能否定位手持物"**。多引入一个（或两个）模型即多一处失败面与维护成本；本项目对**计数一致性**高度敏感，而"姿态手腕点 + RTMDet"是**零额外手部模型**的方案，更契合 M-4 的"失败面最小化"取向。**故本章主选"姿态手腕点 + RTMDet"，把手部模型（MediaPipe-Hand-ONNX / RTMPose-m Hand）列为备选**——仅在需要精确手部区域或手势语义时才启用。

**shot 级时间累积的影响（分析）**：本项目约定手持物按 **shot 级时间累积**（非逐帧）。这对候选选择有两重影响：① 容忍**单帧漏检**，可用更高阈值换低误报（漏检在 shot 内其他帧补回）；② 与 union bbox 同理，**稀疏采样足以覆盖手持物的时间分布**，进一步降低对单帧精度的要求。

### 3.4 三类目标的非对称预算映射

**预算差异（事实/口径）**：人脸**保召回**（漏检代价 = 覆盖人脸，绝不可接受），handheld/broll **控制在预算内**（可容忍一定误差）。映射到工程参数：

| 目标 | 检测阈值 | 抽样策略 | 时间累积 | regions.json |
|---|---|---|---|---|
| face | **偏低阈值**（保召回） | 每秒 1 帧 | 全时段并集 + 外扩 | confidence + lowConfidence；**低检测率触发报错（M-4，fail-closed）** |
| handheld | 中高阈值（控预算） | shot 内稀疏采样 | **shot 级累积** | confidence + `lowConfidence` |
| broll | 中高阈值 | 同上 | shot 级累积 | confidence + `lowConfidence` |

> **来源/口径说明**：本映射表由 §3.1–§3.3 的取舍结论与项目内部口径（《video-talkcraft 调研与对比》§6.1 的抽样/并集/外扩口径）**综合推出，非独立实测结论**；具体阈值需在第 4 章施工与第 5 章交叉校验中确认。

人脸与 handheld/broll 的差异**不只是阈值**，更在**失败处理**：前者 fail-closed（覆盖率不足即报错），后者允许标记 `lowConfidence` 后继续。

### 3.5 候选组合建议（初步）

| 类别 | 主选 | 备选 | 弃选及理由 |
|---|---|---|---|
| face | **YuNet（MIT, 230KB）** | RetinaFace-MobileNet（体积换精度） | SCRFD（权重非商用）、MediaPipe FaceDetector（Node 不可行） |
| pose→主体 | **人脸框外扩（零边际成本）**；需精确区时 **RTMO**（无检测器、单模型）或 **RTMPose**（单人更快） | — | YOLO-pose 系（AGPL） |
| handheld | **姿态手腕点 + RTMDet ROI 组合** | 手部 ONNX 模型（MediaPipe-Hand-ONNX / RTMPose-m Hand） | 纯显著性作主判据（效果差） |
| broll | **RTMDet（通用检测）** | 显著性兜底 | YOLO 系（AGPL） |

### 3.6 小结

三类目标的取舍遵循同一逻辑：**在许可与 Node 可行性双重约束下，选"够用即可"的精度档，把节省的成本投向失败处理与时间累积**。人脸以 YuNet + 全时段并集 + fail-closed 保召回；姿态优先用"人脸框外扩"零成本落主体区，仅在需要手部/躯干精度时引入 RTMO/RTMPose；手持物以"姿态手腕点 + RTMDet"组合 + shot 级累积覆盖，手部模型（MediaPipe-Hand-ONNX / RTMPose-m Hand）列备选。所有选择均**中立呈现**，具体性能数字待第 4 章施工验证与第 5 章交叉校验确认。

## 4. onnxruntime-node 集成方案、预处理/后处理 glue 自研与模型管理策略

**本章论点**：第 2 章把"三条路线均无现成 Node 端到端案例、必须自研 glue"列为共性风险。本章的任务是把这个**风险陈述转化为可执行的工程方案清单**——不是再论证要不要自研，而是回答"自研什么、用什么、怎么组织、代价多大"。好消息是：经过检索，**JS 侧的目标检测 glue 已有可复用的公开参照**（尤其是 RTMDet 的完整 JS 移植），自研并非从零。**此处需明确修正前文一处判断**：第 2/3 章基于当时检索得出的"无公开端到端案例"结论，对 RTMDet 已不再成立——RTMDet 存在一例公开的 JS/onnxruntime-node 移植参照（详见 §4.3）；但范围须收窄——**这是目前发现的唯一一例**，YuNet、RTMO/RTMPose 与手部两候选（MediaPipe-Hand-ONNX / RTMPose-m Hand）**仍无**公开端到端案例。

### 4.1 onnxruntime-node 集成架构

**会话与推理（事实）**。核心 API 为 `ort.InferenceSession.create(modelPath, options)` 与 `session.run(feeds)`；输入用 `new ort.Tensor('float32', Float32Array, [1,3,H,W])` 构造（NCHW 布局），输出从 `results[outputName].data` / `.dims` 取（[onnxruntime-node npm](https://www.npmjs.com/package/onnxruntime-node), [ORT JS API](https://mintlify.wiki/microsoft/onnxruntime/inference/javascript-api)）。`SessionOptions` 提供 `executionProviders`（本项目固定 `['cpu']`）、`graphOptimizationLevel`（`disabled|basic|extended|all`）、`intraOpNumThreads` / `interOpNumThreads`、`executionMode`（`sequential|parallel`）、`enableCpuMemArena` / `enableMemPattern`（[SessionOptions 接口](https://faxu.github.io/onnxruntime/docs/api/js/interfaces/InferenceSession.SessionOptions.html)）。

**确定性配置（事实 + 建议）**。ONNX Runtime 的图优化在个别模型上可能引入数值差异甚至"空输出"（[ORT 图优化文档](https://mintlify.wiki/microsoft/onnxruntime/concepts/graph-optimizations)）。因此本项目**建议**：生产用 `graphOptimizationLevel: 'all'` 求速度，但**建立一条 `'disabled'` 的位精确对照通道**用于交叉校验；`executionProviders` 固定为 `['cpu']`、线程数固定（如 `intraOpNumThreads` 固定 N）以避免非确定调度。这些是"确定性可复现"约束在集成层的落地动作，**对应第 1 章七维基线中的"安装成本"与"失败显式性"两个维度**。

### 4.2 Node 端图像 I/O 与预处理管线

**抽帧链路（衔接）**：感知阶段消费项目既有 ffmpeg 抽帧产物（每秒 1 帧的图片序列），因此本管线输入是"已解码或待解码的帧文件/缓冲"，不重复实现解码器。

**解码与 resize 的选项评估（事实）**——这是本项目"轻依赖"约束的关键抉择点：

| 方案 | 架构 | 优点 | 代价 / 风险 |
|---|---|---|---|
| **sharp** | 原生 libvips | 快 4–40×、内存低（流式）、事实标准（[npm-compare](https://npm-compare.com/canvas,imagescript,jimp,sharp), [Optimage 2026](https://optimage.dreamintrepid.com/blog/sharp-vs-jimp-nodejs-image-benchmark-2026)） | **需原生二进制**；已知 npm 在 Node 25 上拉取 `@img/*` 平台包失败导致整个安装回滚（[ldas.jp](https://ldas.jp/en/posts/kuzushiji-yolo-ndl-ocr-js-port)）→ **与"换机可移植"冲突** |
| **jimp** | 纯 JS | 零原生依赖、随处可装 | 慢（12MP 图峰值内存 ~800MB）、大图吃力（[Optimage](https://optimage.dreamintrepid.com/blog/sharp-vs-jimp-nodejs-image-benchmark-2026)） |
| **@napi-rs/canvas** | N-API 预编译 | 预编译稳定、类浏览器 Canvas API、预处理代码可复用（[ldas.jp](https://ldas.jp/en/posts/kuzushiji-yolo-ndl-ocr-js-port)） | 需原生插件但预编译覆盖主流平台 |
| **纯 Buffer 手写** | 无依赖 | 极致可控、零安装 | 需自实现 bilinear resize + letterbox，工作量大 |

**倾向建议（分析）**：鉴于"换机可移植优先"，**避免把 sharp 作为硬依赖**（其 Node 版安装脆弱性有实证）；可优先考虑 `@napi-rs/canvas`（预处理代码可直接移植）或对固定小输入（如 YuNet 320×320）**纯 Buffer 手写 resize/letterbox**——后者虽需自研但完全零安装风险，契合约束。最终选择待第 5 章验证计划确认。

### 4.3 逐模型 glue 自研清单（本章主体）

**YuNet**：预处理 = BGR 通道序、H/W 取 32 倍数（向上 pad）、**无 mean/std 归一化（原始 0..255）**；解码 = `score=sqrt(clamp(cls)*clamp(obj))`、box 中心 `(col+dx,row+dy)*stride`、`w/h=exp(·)*stride`，每格 1 anchor、不套 sigmoid（[`@genrwork/face`](https://www.npmjs.com/package/@genrwork/face)）。`decodeYunet` 可作**逐行参照**（但需自查，其未对真实权重验证）。

**RTMO/RTMPose**：预处理 = letterbox（保持比例 + pad）；后处理 = **SimCC 解码**（两轴 1D 分布 argmax + 亚像素抛物线插值 → 经 scale/center 还原坐标）（[OpenMMLab 样例](https://github.com/open-mmlab/OpenMMLabCamp/discussions/233)）。**RTMO-ORT 的 Python 实现可作移植参照**（其 letterbox/解码/坐标映射逻辑权威，[RTMO-ORT](https://github.com/namas191297/rtmo-ort)）。

**RTMDet（关键发现：已有完整 JS 移植参照）**：一位开发者已将 NDL 的 RTMDet 版面检测**完整移植到 JS/Node（onnxruntime-node + rtmdet-s）**（[ldas.jp](https://ldas.jp/en/posts/kuzushiji-yolo-ndl-ocr-js-port)，**实践参考：单项目实证、AI 辅助撰写，待核**）。**此发现修正了第 2/3 章基于当时检索的"无公开端到端案例"判断**——RTMDet 是目前发现的**唯一一例**公开 JS/onnxruntime-node 移植参照（YuNet、RTMO/RTMPose 与手部两候选仍无）。关键事实：**该导出版本已内置 NMS**（属该**导出版本**的属性、非 RTMDet 通例，见下方"共通组件"厘清），输出为 `dets [1,N,5]=(x1,y1,x2,y2,score)` + `labels [1,N]`，**后处理只需分数阈值**；预处理 = 黑边 pad 到方形（左上对齐）→ resize 1024 → **RGB→BGR** → `(px-mean)/std`（BGR 序，MEAN=[103.53,116.28,123.675]，STD=[57.375,57.12,58.395]）→ CHW。移植结果与 Python 参照**逐框误差约 2px**（**单项目实证、实践参考，待核**），可作**预处理正确性已被初步验证**的证据。据此，RTMDet 路线的 glue **风险评级可予以下调**（依据为单项目实践参考，待核）。

**共通组件设计（分析）**：letterbox（含 pad 与逆映射）、NMS（按置信度排序 + 贪心 IoU 抑制，[JS NMS 完整源码](https://blog.csdn.net/it_xiangqiang/article/details/134000418)）、坐标换算（原图↔模型空间）三者可**抽为共享模块**。**需厘清 NMS 的归属**：RTMDet 与 RTMO 的**当前选用导出版本均已将 NMS 内置进 ONNX 图**（RTMO 官方导出版"尾部含 NMS 算子"，见第 2 章 §2.2），因此三条路线中**真正需要在 JS 侧自研 NMS 的主要是 YuNet**（其导出输出为 cls/obj/bbox/kps，不含 NMS）；共享 NMS 模块**主要服务 YuNet**，并作为"若改用未内置 NMS 的 RTMDet/RTMO 导出版本"时的通用兜底。参考实现：浏览器端 YOLO 管线展示了完整链路——letterbox(灰 114) → RGBA→CHW 归一化 → 解析输出 → sigmoid → 阈值 → `cxcywh→xyxy` → NMS(IoU 0.45) → 逆 letterbox（[MiBeeNvr](https://blog.mickeyzzc.tech/posts/mibee-oss/mibee-nvr-yolo11n)）。

**复杂度评估（估计）**：

| 模型 | 预处理 | 后处理 | 难点 / 易错点 |
|---|---|---|---|
| YuNet | BGR + 32 pad（简单） | 多尺度 stride 解码 | 通道序、pad 对齐、exp/锚点公式 |
| RTMO/RTMPose | letterbox（简单） | SimCC 解码 | scale/center 随版本变化，需打印 shape 确认 |
| RTMDet | BGR + mean/std + pad（简单） | 仅阈值（NMS 内置） | 通道序与 mean/std 序需严格 BGR |

### 4.4 模型管理策略（"不入库"约束下）

**工具链（事实）**：`@tinyaxis/model-downloader` 提供并行 Range 下载、**SHA-256 + size 校验、断点续传、原子安装、HF 镜像**（[npm](https://www.npmjs.com/package/@tinyaxis/model-downloader)）；`@johnhenry/hf-cache` 复用 HF 缓存布局、支持离线（[npm](https://www.npmjs.com/package/@johnhenry/hf-cache)）。**工程动作**：① 下载脚本 pin 到具体 `revision`（commit/tag）而非 `main`；② 落地后按 manifest **记录 SHA-256**，每次使用前校验；③ 本地目录约定（如 `models/<name>/<version>/`）+ **随附许可文件**；④ 支持镜像/代理以适配网络。**许可的合规边界详论归第 5 章**，本章仅列工程动作。

### 4.5 失败处理与确定性在集成层的落地

**显式错误路径清单（做法）**：① 模型缺失 → `InferenceSession.create` 抛错，启动时**预检文件存在 + 校验和**；② 形状不符 → `Tensor` 长度与模型输入不匹配抛 `RangeError`（[ORT 环境说明](https://leeroopedia.com/index.php/Environment:Microsoft_Onnxruntime_Nodejs_Runtime_Environment)）；③ **低检测率 fail-closed** → 人脸覆盖率低于阈值即抛错（承第 3 章）。所有路径 **try/catch 显式捕获**，绝不给空 region。确定性落地见 §4.1（固定 EP/线程 + `'disabled'` 对照通道）。

### 4.6 集成性能预算

**单帧总耗时构成（分析，引既有数据推算）**：以 1fps 抽样、320×320 级输入为例，单帧 = 抽帧已由 ffmpeg 前置（不计） + 预处理（resize/letterbox，纯 JS 约 1–10ms 量级） + 推理（YuNet 约 1.5ms，取自 [HF skillsafe-ai/yunet](https://huggingface.co/skillsafe-ai/yunet) 的 320×320 CPU 冒烟测试——单次冷启值、非基准；RTMPose-m 单人次 11.1ms；RTMDet-m 视档位） + 后处理（NMS/解码，<5ms）。**合计约在 10–50ms/帧量级**，相对"每秒 1 帧"的批处理口径**富余极大**。真正的时间成本在**抽帧与 I/O**，而非推理——这进一步支持"选够用的精度档、把预算留给工程稳健性"的取向。

### 4.7 小结

本章把"自研 glue"落实为四块可执行清单：**集成层**（固定 EP/线程 + 确定性对照）、**预处理层**（避开 sharp 硬依赖，倾向零风险的纯 Buffer 或 @napi-rs/canvas）、**glue 层**（YuNet/RTMO/RTMDet 各有权威参照，RTMDet 已有 JS 端逐框对齐实证——**单项目、待核**）、**模型管理层**（下载器 + pin + SHA-256 + 许可随附）。关键结论：**glue 自研的工作量比第 2 章的"风险陈述"暗示的更小**——**此结论须附一处对前文的修正**：RTMDet 存在一例公开的 JS/onnxruntime-node 移植参照（§4.3），故第 2/3 章"无公开端到端案例"的结论对 RTMDet 不再成立；但该参照为目前发现的**唯一一例**，YuNet、RTMO/RTMPose 与手部两候选**仍无**公开端到端案例。最大不确定性已收窄到"YuNet 的 Node 端实测"与"sharp 依赖取舍"两点，二者均在第 5 章验证计划覆盖。

**小结**：本项目的候选（RTMO/RTMPose，body7/COCO-only 权重）**商用许可成立**——**前提是确认实际选用的确为 COCO-only（非 `pt-aic-coco`）checkpoint**；"数据集限制"说法对 COCO 是误读，对 AI Challenger 是需规避/确认的残余项，对 EDPose 是真实特例（本项目未选）。

#### 5.1.3 AGPL 边界复核（确认）

Ultralytics YOLO 全系（v5/v8/YOLO11/YOLO26）为 **AGPL-3.0**，其**网络条款（Section 13）**规定即使只提供服务（SaaS/API）而非分发软件，也须向使用者提供完整对应源码；闭源商用须购企业授权（[Ultralytics](https://www.ultralytics.com/license)）。**本项目管线即便仅在本地运行，也按'避免任何 AGPL 依赖'处理**——YOLO 系（含 YOLO26n-pose）确认排除，第 1 章结论成立。

### 5.2 失败模式分类学

| # | 失败模式 | 检测点 | 处置 | 分档 |
|---|---|---|---|---|
| F1 | 模型文件缺失 | 启动预检（fs 存在性） | 抛错、不启动 | 硬失败 |
| F2 | 校验和不符 | 下载后/使用前 SHA-256 比对 | 抛错、重新下载 | 硬失败 |
| F3 | 输入形状不符 | `Tensor` 长度 vs 模型 input | 抛 `RangeError`、终止该帧 | 硬失败 |
| F4 | 会话创建失败（ABI/损坏） | `InferenceSession.create` catch | 抛错、提示重装 | 硬失败 |
| F5 | **图优化空输出** | 输出张量全零/异常 | 降级 `basic`/`disabled` 复跑 | 硬失败（人脸）/告警 |
| F6 | **低检测率** | 抽样帧命中率 < 阈值 | **face：抛错（fail-closed）**；handheld/broll：标 `lowConfidence` 继续（fail-soft） | 见右 |
| F7 | 依赖安装失败（sharp 等） | `npm install` 阶段 | 改用零原生依赖方案 | 构建期失败 |
| F8 | **输入帧损坏 / 解码失败** | 读取 / 解码该帧时异常 | 抛错并记录，**不静默跳过或继续** | 硬失败 |

**与 M-4 的映射**：M-4 要求"失败必须显式报错、绝不静默产出空结果"。F1–F5 与 **F8** 一律**硬失败**（抛错）；F6 按目标**非对称分档**——**face fail-closed**（覆盖率不足即抛错，正面依据见 [blurrd.xyz Safe Faces](https://www.blurrd.xyz/blog/safe-faces-so-far)），**handheld/broll fail-soft**（`lowConfidence` 标记后继续，因目标口径是"控制在预算内"）。不存在"F6 静默给空 region"的路径。

### 5.3 确定性验证计划

**位精确对照通道（事实 + 设计）**：ONNX Runtime 图优化可能引入数值差异；`graphOptimizationLevel: 'disabled'` 可关闭全部优化以做位精确复现（[ORT 图优化文档](https://mintlify.wiki/microsoft/onnxruntime/concepts/graph-optimizations)）。**验证设计**：① 固定 `executionProviders: ['cpu']` 与固定 `intraOpNumThreads`；② 同一输入在 `all` 与 `disabled` 两档各跑一次，比对输出张量差异；③ **记录环境指纹**（Node 版本、onnxruntime-node 版本、OS/CPU、模型 SHA-256）写入产物元数据，实现可复现。

**cross-check 实验设计（验收判据）**：以 Python/OpenCV 参照实现为"真值"，对同一批图做**逐框对齐**——YuNet 与 OpenCV `FaceDetectorYN` 比对（见 §5.4）；RTMDet 参照 [ldas.jp 移植](https://ldas.jp/en/posts/kuzushiji-yolo-ndl-ocr-js-port)（其已达**逐框误差 ~2px**——**单项目实证、待核**，可作验收量级标杆）。判据建议：**同一图内匹配框的中心/尺寸误差 ≤ 数像素、检出数一致（允许 ≤1 框抖动）**。

### 5.4 分阶段验证清单（把"最大不确定性"落成步骤）

**阶段 A：YuNet 的 onnxruntime-node 最小验证**（对应最大不确定性）
1. 用下载脚本获取 `face_detection_yunet_2026may.onnx` 并校验 SHA-256；
2. `InferenceSession.create` 载入，打印 `inputNames/outputNames` 确认 I/O；
3. 自研 `yunetPreprocess`（BGR、32 倍数 pad、0..255 无归一化）+ `decodeYunet`（score/box/kps 公式）；
4. 对同一图跑 Node 与 OpenCV `FaceDetectorYN`，**逐框对齐**；
5. **通过判据**：检出数与坐标在容差内一致 → 该路线从"逻辑可行"升为"实证可行"。

**阶段 B：图像预处理依赖取舍实测**（对应第二不确定性）
1. 分别用 `@napi-rs/canvas` 与**纯 Buffer 手写** resize/letterbox 处理样本帧；
2. 对比：安装成功率（换机/不同 Node 版本）、单帧耗时、输出像素一致性；
3. **通过判据**：选择"安装零失败 且 耗时在预算内"者；**默认避免 sharp 硬依赖**（Node 版本安装脆弱性有实证）。

### 5.6 小结（全报告收束）

本报告沿"**约束过滤（第 1 章）→ Node 可行性（第 2 章）→ 目标取舍（第 3 章）→ 落地集成（第 4 章）→ 合规与验证（第 5 章）**"的链条收敛出可执行结论：**人脸用 YuNet（MIT）**、**姿态/主体用 RTMO/RTMPose 或人脸框外扩（Apache-2.0）**、**手持物/B-roll 用 RTMDet + 组合策略（Apache-2.0）**，全部满足 MIT/Apache 可商用、CPU 可跑、脚本化下载的约束；**YOLO 系（AGPL）与 SCRFD 权重（非商用）明确排除**。许可层面，RTMPose/RTMO 商用成立（Apache-2.0 代码 + CC BY 4.0 标注数据集；权重须为 COCO-only 命名），仅 `pt-aic-coco` 权重存 AI Challenger 残余不确定性待规避。失败处理严格对齐 M-4（face fail-closed / handheld·broll fail-soft）。全项目仅剩两项技术验证（YuNet 实测、依赖取舍）与三项参数校准，均已给出可执行步骤。

## 结论

本报告沿"约束过滤→Node 可行性→目标取舍→落地集成→合规与验证"的链条，收敛出可执行结论。

关键发现：一、经许可与运行时双重过滤后，唯一可行窄带是"轻量 ONNX + onnxruntime-node"——YOLO 全系（AGPL-3.0）与 SCRFD 权重（限非商用）出局，MediaPipe 官方 Node 路径因仅支持浏览器而不可行（[mediapipe issue #4800](https://github.com/google-ai-edge/mediapipe/issues/4800)）。二、人脸以 YuNet（MIT，约 230KB）主选，配全时段并集 + 外扩安全区 + fail-closed。三、姿态/主体优先用人脸框外扩（零边际成本），需精确区时按需引入 RTMO/RTMPose。四、手持物/B-roll 以"姿态手腕点 + RTMDet"组合 + shot 级累积覆盖，手部模型列备选。五、全链 MIT/Apache 可商用，RTMPose/RTMO 商用成立（官方 [LICENSES.md](https://github.com/open-mmlab/mmpose/blob/main/LICENSES.md) 与维护者 issue 回复佐证），仅 `pt-aic-coco` 权重的 AI Challenger 条款存残余不确定性。

跨章洞察：本项目真正的风险不在"无库可用"，而在"无端到端案例、必须自研 glue"——可行性 = 模型可跑（已证）× glue 可写（高置信）× 结果可验证（待实测）。集成层通过固定 EP/线程与 `'disabled'` 位精确对照保障确定性，单帧 10–50ms 预算对 1fps 抽样富余极大。

未来方向：执行两项技术验证——YuNet 的 Node 端逐框对齐、图像预处理依赖（sharp／@napi-rs/canvas／纯 Buffer）取舍；并行推进三项参数校准（人脸与手持物阈值、fail-closed 覆盖率下限）；并锁定 COCO-only 权重以规避许可残余风险。
