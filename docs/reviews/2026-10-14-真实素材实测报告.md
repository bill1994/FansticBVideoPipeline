## 二、🔴 P0 缺陷：`t_dtw` 单位误用（10 倍误差）

### 现象

`transcribeWhisper` 把 `t.t_dtw` 直接当毫秒写入 `startMs`：

```ts
// src/stages/whisper-adapter.ts:184-196
const start = t.t_dtw;              // ← 值域 [36, 2996]
if (typeof start !== 'number' || start < 0) { ... }
words.push({
  startMs: start,                    // ← 实为 10ms 帧
  endMs: parseTimestamp(t.timestamps?.to) ?? start + 200,  // ← 毫秒
  ...
});
```

后果：`startMs` 与 `endMs` **量纲不一致**，且 `startMs` 比真实值小10 倍。

### 证据（逐条实测）

| token | `t_dtw` | `×10` 预测 | 真实 `from` | 差 | 当前代码写入的 startMs |
|---|---|---|---|---|---|
| 「老」 | 52 | 520 | 320 | +200 | **52**（应为320，差 268） |
| 「包」 | 224 | 2240 | 2180 | +60 | **224**（应为 2180，差 1956） |
| 「就是」 | 296 | 2960 | 2770 | +190 | **296**（应为 2770，差 2474） |
| 末token「pu」 | 2996 | 29960 | 29990 | −30 | **2996**（应为 29990，差 26994） |

全量统计：
- `t_dtw` 值域 `[36, 2996]`，音频长 30000ms ⇒ **最大值恰为 1/10**
- `|t_dtw×10 −from|` 误差：中位 **180ms**、p90 380ms
- 而当前代码的误差 `|t_dtw − from|`：中位 **1462ms**、max 2696ms

⇒ **修正系数就是 ×10**（whisper 内部 DTW 以 10ms 帧为单位）。

### 为什么昨天没发现

昨天的合成素材（纯音调）恰好掩盖了它：
- 纯音调下 DTW 退化，所有 token 挤在一处 → 误差不显著
- 昨天的"startMs 全是 386"其实也是这个 bug 的表现（386帧 = 3860ms 附近的真实时刻被压成了 386ms）

**教训**：「合成素材只能证明链路通」这条昨天记下了，今天得到印证 —— 但**方向相反**：不是 DTW 退化，而是单位错误恰好被退化掩盖。

### 影响面

- 全部 `word:N` 锚点的时间位置偏早 10 倍
- 下游 `fromFrame` 烘焙随之错误
- **但时序校验查不出来** —— 因为 `fromFrame` 与目标词区间**同源错误**，两者一致 relative 比较会「通过」
- 这与 2026-10-13 记录的「P0 假绿」是同一类病：**静默的错误比响亮的报错危险**

### 修法

```ts
/** whisper 的 t_dtw 以 10ms 帧为单位（实测：值域 [36,2996] 对应 30s 音频）。 */
const DTW_FRAME_MS = 10;
const start = t.t_dtw * DTW_FRAME_MS;
```

⚠️ 同时须核对 `endMs` 来源：`timestamps.to` 是**毫秒字符串**（实测 `00:00:00,440` → 440ms），量纲正确、可直接用。**只有 `t_dtw` 需要换算。**

## 三、DTW 精度实测（修完单位后）

| 指标 | 值 |
|---|---|
| 有效 token | 119（原始 129，丢弃 `t_dtw<0` 的 10 个） |
| 唯一 `startMs` 数 | 100 / 119 ⇒ **分散度充足** |
| `startMs` 逆序| **0 处**（单调性成立） |
| 误差 vs `timestamps.from` | 中位 **180ms**，p90 380ms，max 7040ms |

⚠️ **180ms 中位误差对动效对齐意味着什么**：30fps 下 180ms ≈ 5.4 帧。词级锚点若以此为准，动效会**比人声晚约半个字**。对「卡在词上」的手感是明显可感的偏差。

⇒ 建议：**`offset` 默认值不该是 0**，应按实测误差分布取负偏置（约 −180ms），或直接在 DP 对齐阶段用 SRT cue 时间做二次校正。

## 四、base 模型中文表现（决定阈值能否校准）

whisper 实际输出 vs SRT 原文：

| SRT 原文 | whisper 输出 | 问题 |
|---|---|---|
| 给老婆整了双鞋圈显眼包 | 俾老婆整個雙鞋圈鞋眼包 | 繁体 + 「显→鞋」同音错字 |
| 就是耐克和Stussy联名的Spiridon Kukini Ⅱ | 就是耐克和Stasi連鳴的Spread on Cu | 大量品牌词识别失败 |
| 它把spirit Donkage的中底和cookie的 | 他把Spread on cage的中底和Cukin | 音译词错误率高 |
| 黑白主色调低调耐看 | 黑白煮色調低調耐看 | 「主→煮」同音错字 |
| 鞋子是无鞋绳的一体式网眼袜套 | 鞋子是無鞋神的怡體是網眼挖套 | 错字较多 |

**判读**：
1. 🔴 **输出繁体** —— 中文简体场景需在 token 清洗阶段加繁简归一，否则 DP 对齐永远对不上
2. 🔴 **同音错字率高**（显/鞋、主/煮、绳/神）—— 这是 base 模型的容量上限
3. ⚠️ 品牌/音译词（Stussy、Spiridon、Kukini）几乎必错 —— 但**这恰恰证明方案 (b) 正确**：文本权威归 SRT，whisper 只出时间

### p 分布（解码概率）

| 指标 | 值 |
|---|---|
| 均值 | 0.7660 |
| min / max | 0.0529 / 1.0000 |
| p < 0.5 的 token | 26 个（**21.8%**） |

对照 C2-2 初值「低置信词占比 ≤ 30%」⇒ **21.8% 通过，余量仅 8 个百分点**。

⚠️ 且这个21.8% 里混着繁简错字带来的低分——**base 模型的 p 低不完全是因为时间戳不可靠**。换 small 模型后此值大概率下降，阈值需重新测。

## 五、阈值校准结论：**本次不给结论**

### C2-2（meanConfidence / lowConfidenceRatio）

🔴 **暂不给值**。理由：
- 实测 21.8% 是在 **base 模型**下测的，而`config.ts` 注释已写明「base 是起点，small 通常中文明显更准；若发现识别错字多，换 small 是第一优先级的调整」
- 本次已发现错字多⇒ 按自己的规则该换 small 再测，否则测出的阈值绑定在一个错误的模型档位上
- 更关键：修完 `t_dtw` 后 `meanConfidence` 本身不变（它只吃 `p`），但**门控的意义依赖于时间戳可信** —— 单位错误没修之前，任何阈值都是在给错误信号开门

### alignedRatioMin

🔴 **不给值**。`alignedRatio` 需要第二步 DP（`text-align.ts`）才能算，而 DP 实现前无法测量。
且实测已暴露一个 DP 必须处理的问题：**繁简 + 同音错字**，DP 的相似度匹配需要先做繁简归一，否则「整個」与「整個」之外的组合会全部落空。

### 建议的下一步顺序（调整后）

1. 🔴 **修 `t_dtw` 单位**（10 倍）—— 不修则一切下游不可信
2. 换 **small 模型**重测（base 中文错字太多，测出的阈值无意义）
3. 写单测锁死「`t_dtw×10` 落在 `timestamps.from±400ms` 内」
4. token 清洗加**繁简归一**
5. 再做第二步 DP → 测 `alignedRatio` → 才谈阈值校准
