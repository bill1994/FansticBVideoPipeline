## 一、用户预期流程（原文语义）

1. 输入**原始视频 + 原始 SRT** 文件
2. 运行 skill，经过中间处理步骤，生成 **storyboard 和 motionboard**
3. 基于这两个 board，从**素材库**中挑选合适的 motion
4. 若无匹配素材 ⇒ 由**模型根据 board 中产出的 motion prompt** 生成新的 motion，**可选择保存至素材库**
5. 最后在 **Remotion Studio** 中进行审核

---

## 二、总体结论

预期流程与现行决定**大方向一致**：输入形态、两 board 结构、模板挑选机制、Studio 审核方向在现行架构里都有对应。差异集中在三处：

- **2 个环节尚未建成**：Studio 审核硬闸（= 提案 P1-a）、模型生成（= 提案 P1-b）—— 均已于 2026-10-22 ACCEPTED，未落地；
- **1 个契约缺口**：board 不产 motion prompt —— 不在任何现行计划里，为本次比对新发现（已增补进提案 §4.5，见 §六）；
- **4 项操作 / 门 / 范围差异**：不构成路线冲突，但影响「一条命令黑箱跑通」的预期手感。

## 四、逐项冲突与影响

### 冲突 1（高）· Studio 审核环节不存在 —— 与 B1 / A1 / D2 直接冲突

- **现行决定**：`cli.ts` 无 `review` 命令（B1）；validate 只把 `decision.review='must_review'` 写进**警告队列**（A1）；render 启动闸只强制 fullscreen 确认（D3-a），**不强制 must_review**（D2）。
- **差异点**：预期流程的最后一环（Studio 审核）目前没有工具化入口，只能靠用户自开 Studio + 手改 `06-review/confirmed.json`。
- **影响**：custom 产路与安全阀批次（sim_max 中位数 <0.4 ⇒ 整批转 custom + must_review）**没有硬闸**，未审内容可直接进渲染；第二道闸的产物是「建议」而非「阻断」（项目「定义了≠生效」第六例）。P1-a 落地前，此风险持续存在。

### 冲突 2（高）· 「无匹配 → 模型生成」当前是人工逃生口，不是自动生成

- **现行决定**：B4/N-3 裁决绑不上时走 `custom` 路由 + 产路地板 must_review —— 含义是「交给人」；P1-b（生成自动化）已 ACCEPTED 但未实现，且明确生成放在**创作期会话/工具**，不在 `npm run pipeline` 渲染管线内调 LLM（红线）。
- **差异点**：预期流程的「模型生成」循环（生成 → 预览 → 入库 → 重新绑定）今天不存在；placement 上，用户把生成放在审核前，P1-a 把生成能力放在审核会话内。
- **影响**：今天 intent 无匹配会**卡在人审**，无自动路径；若用户按预期流程操作，会在「无匹配」处断流。placement 差异可兼容（会话内生成即审核前），但落地时需明确，否则会出现「审核时才发现没料可生成」的顺序倒置。

### 冲突 3（中）· board 不产 motion prompt —— 契约缺口（本次新发现）

- **现行契约**：motionboard 条目只有 `intent`（受控词表 `MOTIONBOARD_INTENTS`）+ `featuredText`（显示文案）+ `note` + `confidence` 等；`ALLOWED_MOTIONBOARD_ITEM_KEYS` 是封闭白名单，多一个键都拦。P0 规则：自由文本不进机器判定。
- **差异点**：预期流程要求「模型根据 board 中产出的 motion prompt 生成」——board → prompt → 生成 的因果关系，现行契约表达不了；P1-b 原稿也只写「按 prompt 生成」，**未规定 prompt 从哪来**。
- **影响**：生成器没有合法输入通道；若不补契约，实操中只能由人在会话里现编 prompt，board 与生成物之间断链，不可复现、不可审。
- **已执行**：增补进提案 §4.5 —— `MotionBoardItem` 加可选 `genPrompt?: string`，只被创作期生成器与人审读，binder/validate/render 不读（守 P0）；无 genPrompt 的 no-fit 维持 custom 人工逃生口（生成是增强不是替换）。**待用户审阅定案。**

### 冲突 4（中）· 素材库的成熟度与定义

- **现行状态**：motion 模板库 = 11 声明（builtin）/ 9 实现，另 `templates/specs/` 8 份共创 spec（合计 19 声明 / 17 实现，画廊口径）。`pointer-callout` / `whip-pan` 两个声明未实现，被引用会渲成**故意做丑的占位块**（`data-template-missing`），而 validate **看不见渲染层实现状态**。
- **口径歧义**：若「素材库」指视觉资产（图片/B-roll）：`docs/proposals/2026-10-15-视觉资产库纳入计划书.md` 已**搁置**（2026-10-19 裁决；重开条件 = 模板 11/11 且 ≥3 条真实成片验证）。
- **影响**：挑选集实际只有 17 个已实现；引用未实现模板会静默出占位块（校验全绿）；「保存至素材库」的版本化入库（`custom/<语义名>@0.1` → 定稿 1.0）是 P1-b 的一部分，未建；若预期指视觉资产库，则整条线未启动。

### 冲突 5（低 / 操作）· 「运行 skill 后出两 board」vs 分段快照 + 模型中继

- **现行形态**：分阶段 CLI（`align → perceive → storyboard → validate → render`）+ 不可变快照；模型精修路径需在 storyboard 运行之间由模型写 `motionboard.json`；align/perceive 有产物即跳过（改代码须 `--force`）；storyboard/validate/render 每次重算；改 `fps` 全部已烘焙帧作废。
- **影响**：不是真冲突（生成器路径可一次产出两 board，M-3 后分布还是语义的），但「一条命令黑箱出片」给不了——模型中继路径本来就需要模型在环；且 01/02 快照的 `--force` 语义容易让「改了代码没生效」误判为流程断点。

### 冲突 6（低 / 门）· align 门控可能第一步就阻断线性流

- **现行决定**：C2-4/C2-2 —— 置信度门控不过 ⇒ 退出码 1 阻断，须人工写 `confirmed.json`（stage:"alignment"）放行。
- **影响**：新素材首跑不保证直通；这是刻意设计（降级必须显式，不静默伪造），但与你「输入即跑通」的预期有摩擦——首次使用新素材时，流程可能停在 align 而不是走到 Studio。

### 冲突 7（低）· 校验位置与生成物验收

- **现行形态**：预期流程未提及 validate；现行 `04-validate`（18 项 + 2 条 extra，error 即阻断）夹在 storyboard 与 render 之间；生成的 MotionSpec 须先过 P1-b 六道验收（注册 / paramsSchema / 画廊三帧 / 动效断言 / 确定性 lint / 版本化）才准入库，最终 storyboard 仍要过 validate。
- **影响**：生成物若 footprint / scope / layer / paramsSchema 声明不全会被拦或出 warning；且 E-C6-01（item 超 Composition 被 Remotion 静默截断、全链路无报错）对结构未知的生成物尤其危险——提案自己也把这条列为必须防的点。校验不是可选项，是生成物的第二道门槛。
