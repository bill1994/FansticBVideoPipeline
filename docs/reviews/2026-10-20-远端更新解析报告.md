## 二、逐条变更解析

### 2.1 `a7705e4` fix(pipeline): 端到端审计 6 项修复 + 2 项连带

**风险等级：高**（含行为契约变更 + 数据兼容性）
**影响面：全局**（改动 `cli.ts` 与三个 stage，属主入口调用路径）

#### ① 渲染失败退出码：`RenderFailedError`（exit-code.ts:新增类 / cli.ts / render.ts）

- **原来**：`render.ts` 失败时抛 `ConfigError`，而 CLI 把 `ConfigError` 一律映射为**退出码 2**（参数错）
- **现在**：新增 `RenderFailedError` + `exitCodeFor()` 显式映射，`EXIT.RENDER_FAILED(4)` 真正成立
- **证据**：`src/core/exit-code.ts` 新增类注释原文——
  「错误文案写着『渲染失败（退出码 4）』，实际进程退出码是 2。**报错信息自己报错了自己的退出码**」
- **附带修复**：映射逻辑原先内联在 `cli.ts` 的 `catch` 里，**不可测** ⇒ 抽成函数。新增 `tests/exit-code.test.ts`（51 行）
- 🔴 **判据复用**：「不可测的约定等于没有约定」—— 这条正是本项目「文档说有、代码没接线」那类问题的镜像

#### ② `confirmed.json` 支持记录数组 + `stage` 参与判定（confirmed.ts 新增 / storyboard.ts / render.ts）

- **原来**：`ConfirmedRecord` 定义在 `stages/render.ts`，`storyboard` **完全不读**它，却在门控失败时提示用户「写 confirmed.json 再继续」⇒ **实测用户照做后重跑仍 exit 1、报错一字不改**
- **现在**：上提为 `core/confirmed.ts`（217 行），`stage` 真正参与判定，支持 `{records:[...]}` 多条（旧单条写法兼容）
- **上提的理由（结构层）**：`storyboard` 若从 `stages/render` 导入会形成「**03 依赖 05**」的跨级依赖 ⇒ 与「禁跨级引用」同源
- **关键设计**：只收 `must_review` 不收 `alternatives`（后者语义是「有备选待选」，而本项目**没有备选机制**，收了只制造噪音）
- **死锁问题已解决**（文件头原文）：单条记录会让「既需alignment 放行、又需 fullscreen 确认」的 job 陷入死锁 ⇒ 修`stage` 校验的同时必须支持多条
- **测试**：`tests/confirmed.test.ts`（288 行，本次最大测试文件）

#### ③ 素材分辨率进契约（P4）（video-size.ts 新增 / Root.tsx / types.ts / Overlay.tsx / MotionItem.tsx）

- **原来**：`Composition` 宽高**硬编码 1920×1080**，`SourceManifest` 无 width/height ⇒ **素材分辨率根本不进契约**
- **实测后果**（源码注释原文）：640×360 占位素材渲出 1920×1080；**竖屏素材完全无路可走**
- **现在**：`SourceManifest.width/height` → `resolveRenderSize()` → `Composition`；取值优先级 **清单 → ffprobe → 兜底**，`RenderSize.from` 字段记录来源
- **上提理由**：同①，`probeVideoSize` 原在 `stages/builtin-perceive.ts`，`render` 要用就得「05 依赖 02」
- **无破坏性**：`canvasWidth` 缺省 1920 ⇒ 旧模板单测不需要构造 Remotion context
- **测试**：`tests/video-size.test.ts`（65 行）

#### ④ 起草稿 item 未知键检查（P5）（storyboard.ts）

- **原来**：`bake` 用 `{...item}` 展开 ⇒ `routing` / `review` / `handoffIn` 这类**写错的键会原样落进 `storyboard.json`**，全链路不报错、成片也不报错
- **判断**：这是**唯一「静默污染产物」的路径**（`params` 内部有 `E-P1-01` 兜着，item 顶层此前是无人区）
- **现在**：`ALLOWED_DRAFT_ITEM_KEYS` 白名单 + `KEY_HINTS` 针对性提示（`handoffIn` 会提示「已于 2026-10-15 删除，请用 `params.enter`」）
- **归类**：**结构错误 → `ConfigError` / 退出码 2**，不占 18 项名额（与「`carrier` 引用未注册模板」同类）
- **测试**：`tests/draft-keys.test.ts`（96 行）

#### ⑤ 渲染期 `fitScale` 兜底（P6 第一步）（contract.tsx / 3 个模板 / text-metrics.ts）

- **原来**：全部模板 `whiteSpace: nowrap` ⇒ 长文本既不折行也不缩放，直接跑出框；而构建期校验 #17 是**估算且已知低估**（16 字实测溢出、估算说没超）
- **现在**：超框时等比缩至框内，`minScale = 0.7`
- **两条设计决策（有理由）**：
  - **用估算不用 DOM 测量** —— 渲染须确定性；`getBoundingClientRect` 服务端拿不到，且会让「同一帧两次渲出不同结果」成为可能；估算与校验项 #17 **同源**，两处口径一致才不会「校验说没超、渲染却缩了」
  - **到0.7 下限仍溢出就让它溢出** —— 缩到 0.7 以下就不像设计了，那是「该改文案」的信号
- **连带修正**：`text-metrics.ts` 的 `FRAME_WIDTH_PX` 硬编码改为 `ctx.source.width ?? FRAME_WIDTH_PX`
  ⇒ 否则**竖屏素材（1080 宽）会按 1920 估算，系统性漏报溢出**
- **测试**：`tests/fit-text.test.ts`（53 行）
- ⚠️ **未实施部分**：3 个模板（`kinetic-line` / `stat-card` / `tag-float`）已接 `fitScale`，**其余 6 个实现模板未在本次改动内**⇒ 详见第五节

#### ⑥ `reviewQueue`：让 `decision.review` 有消费者（P2）（validate/index.ts / report.ts）

- **原来**：`item.decision.review` 算出来**零消费者** —— 算完写进 `storyboard.json` 就没人看了
- **现在**：`validate-report.json` 输出 `reviewQueue`（只收 `must_review`）+ CLI 文本报告里打印「👀 人工审核队列」
- **明确不是校验项**：不进 `checked`、不影响 `ok`、不产 `ReportItem`；空队列时**整个字段省略**（未出现即「没有要看的」）
- **测试**：`tests/review-queue.test.ts`（56 行）
