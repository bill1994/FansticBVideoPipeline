# P0 实测报告：`-ojf` 导致中文 token 被字节截断

**日期**：2026-10-14
**触发场景**：`npm run align` 走真实中文素材（small 模型）
**严重级别**：🔴 **P0 —— 数据在源文件层面已损坏，不可逆**
**状态**：根因已确认（非推测），修复方案待裁决

---

## 1. 现象

30s 中文口播（`TestResources/kukini.mp4` 前 30 秒，small 模型）：

```
119 个 token 中，49 个（41%）的 text 是纯 U+FFFD（�）
```

具体表现（经 `transcribeWhisper()` 的完整清洗路径）：

```
给老婆整了�������、���眼包就是��克和斯��西��名的Spiritone Cookini II…
```

对照 `main.exe -oj` 直出的同一段音频：

```
给老婆整了双鞋圈、鞋眼包就是耐克和斯达西联名的Spiritone Cookini II…
```

**同音频、同模型，一条路正确，一条路损坏。**

---

## 2. 根因链（已用原始字节证实）

```
① @remotion/install-whisper-cpp 在 tokenLevelTimestamps:true 时
   给 whisper.cpp 传 -ojf（--output-json-full，逐 token 输出）
                    ↓
② whisper.cpp 1.5.5 在 -ojf 模式下，把多字节 UTF-8 汉字从中间切断，
   每个碎片单独写成一个 JSON 字符串：
        "text": "\xe5\x8f"    ← 「整」的前 2 字节，第 3 字节 0xad 丢失
        "text": "\x8c"        ← 孤立续字节（起始字节也没了）
        "text": "\xe9"        ← 三字节序列只剩了头
   实测该文件中存在 66 处非法/截断 UTF-8 序列
                    ↓
③ Node 侧 readFile(jsonPath, 'utf8') 遇到非法字节
   → 每个非法片段各替换成一个 U+FFFD
```

证据文件：`jobs/real30/01-align/probe-ojf.json`

```python
# 文件字节中 ef bf bd（U+FFFD）出现次数 = 0
# 但 decode('utf-8') 抛 UnicodeDecodeError: invalid continuation byte @2416-2417
```

**结论**：whisper.cpp 写出的是**被截断的 UTF-8 字节**，不是合法的 U+FFFD。
损坏发生在**写入磁盘之前**，Node 只是被动地把非法字节渲染成 `�`。

---

## 3. 为什么这是最危险的一类 bug

| 特征 | 说明 |
|---|---|
| **英文素材 100% 通过** | ASCII 是单字节，永远不会被截断 ⇒ 用英文测试根本发现不了 |
| **本项目是中文口播** | ⇒ 必然 100% 触发 |
| **源文件已损坏** | 字节已丢，不可逆，无法在 Node 侧「洗回来」 |
| **之前从未覆盖** | 所有单测用的都是手写 token，从没在真实中文素材上跑过 token 级路径 |
| **与「静默假绿」同族但更险** | 静默假绿是「校验通过但结果错」；这里是「数据本身已坏」 |

---

## 4. 关键判据：区分「模型不会」与「管道坏了」

| 路径 | 输出 |
|---|---|
| `main.exe -oj`（segment 级） | ✅ 文本完全正确 |
| `main.exe -ojf`（token 级） | ❌ 66 处截断 |

⇒ **不是模型识别问题，是 `-ojf` 的输出编码问题。**

---

## 5. 顺带修正的两个旧结论

| 旧结论 | 修正 |
|---|---|
| 「whisper 中文输出繁体字形」 | **仅 token 级路径成立**。`-oj` 的 segment 文本是**简体** |
| 「`main.exe -oj` 可用于取 token」 | **不成立**。`-oj` 只有 8 个 segment，**不含 token 级数据**；token 级必须过 `@remotion/install-whisper-cpp`（因为它才加 `-ojf`）⇒ 这个 bug **绕不开** |

---

## 6. 修复方向（待裁决）

### 方案 A：弃用 token 级，接受 segment 级
- 文本 100% 正确、且是简体
- ❌ 粒度从 119 降到 8 段/30s ⇒ 动效无法跟随单个字词
- ❌ **会动摇 M-1 方案 b 的既有裁决**（它依赖 token 级时间戳）

### 方案 B：自己 spawn `main.exe`，绕开 npm 包的 `-ojf` 封装 ⭐ 倾向
- 保留 token 级能力，不改 M-1 裁决
- 需自己处理：模型路径、`--dtw` 参数映射、绝对路径、临时文件
- ⚠️ 包的一半价值（install/download/getModelPath）仍可复用，只替换 `transcribe()` 这一层

### 方案 C：`-oj` 取文本 + `-ojf` 取时间 + DP 对齐
- 文本权威、时间权威，两者靠第二步 DP 对齐
- ❌ 实测「按下标硬配」**不成立**（`-oj` 文本含 `、` 和空格等非 token 字符，index 整体偏移）
- ❌ 但项目**本来就要做第二步 DP** ⇒ 这条路可能「顺路免费」
- 风险：DP 对齐失败时无兜底

### 方案 D：用 token `id` 反查词表
- `-ojf` 的 token **带有完整整数 `id`**（49 个损坏 token 全有 id）
- 用 whisper 词表反查 id → 正确字符
- ✅ 最干净，不破坏任何既有结构
- ⚠️ 未验证：需 whisper 的 `vocab.json` / `tokenizer.json`，且 id→字符 的正确性未测

## 7. 附：small 模型质量对比（与本次 P0 独立的结论）

| | base | small |
|---|---|---|
| 「绳」 | ❌ 听成「神」 | ✅ 无鞋绳 |
