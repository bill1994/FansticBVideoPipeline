### 3.4 定性与修复建议

**性质**：🔴 高。`W-C3-01` 从 4 → 14 说明 **M-1f 铺词改变了 `caption` 类 item 的起点对齐特征**（铺词后 cue 起点更可能落在词级边界上）。

**风险**：
- 若用户按旧报告判断「只有 4 条轻微 warning」，会**低估当前真实噪声量3.5 倍**
- 项目已有先例警示：`PROGRESS.md` 记过「49→4 条 W-C3-01 改用 SRT 时间后自然消退」，**方向相反的历史变动恰好也在这个码上** ⇒ 该码对词时来源高度敏感

**修复建议**（按优先级）：
1. 🔴 **在 `validate` 阶段加一道「产物时序自检」**：读取 `storyboard.json` 的生成时间与 `words.json` 的生成时间，若 `storyboard` 早于 `words` ⇒ 报 warning「下游产物基于旧版上游，请重跑 storyboard」。
   **理由**：项目已有 `guardSnapshot` 防「回写上游」，但**没有防「用旧上游产出新下游」** —— 这是同一族问题的另一半。
2. 🟡 **更正 `PROGRESS.md` 中 11 warning 的记录**（该数字属旧版本产物，不应作为当前基线）。
3. 🟡 `W-C3-01` 本身值得复核：`caption-bar` 用 `cue:N` 锚点时，起点本就等于 SRT cue 边界，而 SRT 边界与重铺后的词边界高度重合 ⇒ 该warning 对字幕轨可能**结构性误报**，应考虑对 `caption` 类 item 豁免（如同 `split-frame` 的用具名豁免先例）。

## 四、其他问题清单

### 4.1 ✅ SRT 解析：零缺陷（重点排查项已验证）

直接调用 `parseSrt()` 实测：

```
解析成功：48 cue，耗时 6ms
text 含残留 \r 的 cue : 0 条      ← CRLF 无泄漏
非单调 cue              : 0
空文本 cue              : 0
原文件 cue 数 → 解析后   : 48 → 48  ✓
末cue 结束帧 6633 / 视频总帧 6667 → ✓ 在范围内
```

**评价**：解析器对 CRLF / BOM / 末尾空行容错到位（`split(/\r?\n/)`），且**解析失败一律抛 `ConfigError` 不返回空数组** —— 这是正确姿态（空数组会让下游误以为「这段没台词」）。

⚠️ **工具层面（非项目缺陷）**：Git Bash 下 `grep -c $'\r'` 对该文件返回 0（误判为 LF），Node 读出 192 个 `\r`。**结论：判断行尾必须用 Node/`od`，不能用 Git Bash 的 grep** —— 我自己第一次就差点误判。

### 4.2 ⚠️ `storyboard/SKILL.md` 与实现分叉（P2）

**SKILL.md 第 211–214 行明写**：
> 「🔴 **警告：item 顶层多写的字段不会被拦**（2026-10-19 实测）。当前**没有**「未知 item 字段」校验项……会经 `{...item}` 原样落进 `storyboard.json`，全链路无报错。」

**实现（`src/stages/storyboard.ts:69`）**：
```ts
const ALLOWED_DRAFT_ITEM_KEYS = new Set([...]);
// 未知键 → 抛 ConfigError（退出码 2），并附 KEY_HINTS 针对性提示
```

- **复现条件**：任何人（或模型）按 SKILL.md 的指引行事
- **影响**：SKILL.md 是**被模型读取的行为契约** ⇒ 文档说「不会拦」，模型就会放心地多写字段，而实际会被拒 ⇒ **模型会得到一个与文档矛盾的报错**
- **严重程度**：🟡 中（不损坏产物，但会让执行者困惑并浪费一轮返工）
- **定位**：`504937b` 那次「五份 SKILL 按实现更正」漏掉了这一条
- **修复**：把该段改写为「item 顶层未知键**会被拦**（`ALLOWED_DRAFT_ITEM_KEYS`，退出码 2），允许键清单见下」
