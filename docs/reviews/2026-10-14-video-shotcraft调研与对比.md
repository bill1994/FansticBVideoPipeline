### 1.4 关键实现流程

**八阶段流水线**（`references/pipeline.md` 标题即"八阶段制作流水线"）：

```
阶段 0 产品理解与执行约束 ── 只读检查项目，产出产品简报 + 需求到执行决策表
阶段 1 视觉方向与 styleframe ── 纯 HTML/CSS 静态帧定调（不渲视频、不写 Remotion）
阶段 2 功能到镜头映射 ── 扫 124 卡 frontmatter，每功能选卡
阶段 3 分镜与制作放行 ── 排能量曲线 + 帧级时间轴 + hold/rest 帧预算
─────────── 以下开始花大钱 ───────────
阶段 4 最终素材采集 ── dev server → 三件套（全页 2x + 元素抠图 + layout.json）
阶段 5 逐镜头实现 ── 每镜 2 个验收帧号，still 静帧肉眼验收
阶段 6 声音设计 ── BGM 定骨架 + SFX 相对表达式钉帧
阶段 7 独立终检与交付 ── 干净上下文 subagent 审查 + 双版本渲出
```

**三种创作模式**（`SKILL.md` 明确定义，互不合并）：

| 模式 | 行为 |
|---|---|
| 直接使用模板 | 走 Ink Press 替换流程，不进入 pipeline |
| 自主自由创作 | Agent 连续推进，阶段 0–3 **不逐阶段等待确认** |
| 共同创作 | 阶段 0–3 逐级用户确认，再从阶段 4 继续 |

**核心资产：镜头配方卡**（`references/shots/`，124 张 / 10 类）。每张卡的固定骨架（以
`typography/flying-words.md` 为例）：

```yaml
---
name: flying-words
一句话: 22 个关键词按黄金角铺在扁椭圆截面上…跑满 2 整圈首尾无缝
适用: 关键词云的动态背景；片头片尾的信息量垫层
时长: 约 6.0s（180f@30fps，2 个完整循环，可无缝接续）
能量: 高（全屏持续 3D 位移，画面无一刻静止）
---
## 意图        ← 为什么这么做，什么场景用
## 动效核心    ← 具体数值：透视 1100px、z −1750→800、生命曲线 [0,1,0.5,0.2,0]
## 参数表      ← 表格：参数 | 典型值 | 调节手感（含越界后果）
## 已知坑      ← 🔴 命门参数，不得降档
## 参考实现    ← 指向 demos/typography/flying-words/
```

`测试` 卡的"参数表"列名是「参数 | 典型值 | **调节手感**」——不是罗列数值，而是写
**"调大/调小会怎样"**。例如：

> `散开系数 <1 词全从正中喷出像爆炸；>2 早早飞出画外，隧道变喷泉`

**判例式审美准则**（`aesthetic-rules.md`，28KB）。五类编号，可直接被终检引用：

- **R1–R4** 节奏（呼吸、加速度、宁慢勿快、卡点≤3处）
- **Q1–Q11** 质感/运镜/构图（真实截图、纹理分辨率链路、镜头要稳…）
- **S1–S5** 声音（按片种选音、钉帧管理、拟音优先）
- **C1–C3** 文案（画面锁定后重写、标语要具体）
- **P1–P4** 流程（自己截帧检查、参考先拆解、干净 revert、功能清单逐一对应）

## 二、值得借鉴之处

### 2.1 🔴 「配方卡 = 语义 + 参数真相在 demo 源码」的双层结构

**做法**：卡片给语义和参数表，但 `SKILL.md` 核心理念第 6 条明确写：

> "配方卡给的是语义和参数表，准确的 demo 源码才是调校过的参数真相（缓动、时值配比、摘罩时机、已知坑的规避写法）。**凭卡名和理解新写＝放弃全部调校积累。**"

配套硬规则（pipeline 阶段 5 第 1 条）：**每镜头先解析再三读**——
`gallery/api/library.json` 校验卡名与 `style-key` → 读卡全文 → 按"参考实现"定位
读 demo TSX 全文 → copy 组件。三步缺一不可。

**对本项目的价值**：我们的 `docs/templates/2026-10-13-模板库首批清单.md` 有 10 个
模板的**契约值推导依据**，但 `templates/` 目录**零实现**。这个双层结构正好是我们缺的
第二层——**参数真相必须有一份"调校过的实现"作为不可争辩的锚点**，否则每次重写都要
重新调参，且调参结论无法积累。

**可直接抄的形式**：给每个模板芯片写一份"参数表"，第三列不是"取值范围"而是
**"调节手感/越界后果"**。这一列才是经验，取值范围只是数据。

### 2.2 🔴 「调校决策档案」——把审美判断变成可审计的 JSON

**发现**：`shot-polish/` 目录，`notes/` 217 个 JSON + `final-notes/` 151 个 JSON。
每个文件记录**一个 demo 的调校过程**：

```json
{
  "stem": "KanadaPerspectiveSnap",
  "issues": [
    "主体是一张灰色占位卡…左上角还留着调试卡名",
    "透视与扭转和位移同一条曲线同时收，到位前几帧卡片已经平了，鱼眼感几乎看不到",
    "落定只有 6px 震屏，缺少动漫式'定格一拍'的视觉重音；之后 100f 完全空转"
  ],
  "changes": [
    "甩入 18f：位移 −1350→0 走 snappy 急停，透视 260→1800px / rotate3d 62°→0 / scale 1.8→1 走晚收曲线",
    "落定重音：rotateY 冲到 +6° 再弹簧回零、8px 震屏 2f、48 道动漫集中线 9f 向外退散"
  ],
  "issuesEn": [...], "changesEn": [...]
}
```

**为什么值得借鉴**：这是把"审美为什么这么调"落成了**机器可读、双语、可 diff 的档案**。
它的价值不在归档本身，而在：

1. **复盘可检索**——"鱼眼看不到"这类症状可以被搜索，下次遇到直接查既有解法
2. **决策可追溯**——几轮之后没人记得为什么是 18f 而不是 24f，档案里有
3. **中英双列**——同一判断写两遍，逼作者把话说清楚；也方便非中文协作者

**对比本项目**：我们的 `docs/decisions/OPEN-DECISIONS.md` 已有 42 条 RESOLVED 裁决，
是这个方向的正确形态，但**粒度是架构决策**（如 M-1 方案 b）。缺的是**参数级决策档案**——
比如"为什么 `MATCH_MIN_SIMILARITY` 是 0.35 而不是 0.5"这个判断，现在只存在于
memory 日志和代码注释里，没有独立可检索的档案。

### 2.3 「先便宜产物定方向，再进昂贵阶段」的成本纪律

**做法**（pipeline 阶段 1）：

> "对选定方向**不渲染视频、不写 Remotion 代码**，写一个纯 HTML/CSS styleframe 页"

阶段 1 的常见坑第一条更直白：

> "用渲染视频做风格提案：太贵，改方向的心理成本也高。静态帧足够定调。"

阶段 0–3 全是"纸面"工作，阶段 4 才开始采集素材、阶段 5 才写代码。文档里有一句总结：

> "方向性问题不进昂贵的逐镜头阶段。"

**对本项目的价值**：我们的 pipeline 是 `align → perceive → storyboard → validate → render`，
**顺序上已经是"先算后渲"**，但缺一个明确的"方向确认闸"——目前 `03-storyboard` 要求
用户**手写 `sim_max` / `confidence`**，没有中间产物让用户在花大钱前先看方向。

**可借鉴的具体动作**：在 `03-storyboard` 之后、`05-render` 之前，加一个
**纯数据预览的 styleframe 等价物**——不渲染视频，只输出"这条 cue 会用哪个模板、
占多少帧、和其它 item 怎么排"的结构化预览（HTML 或纯文本时间轴）。成本近乎零，
但能在模板实现阶段避免"做完了才发现方向不对"。

### 2.4 「声明式钉帧表 + 相对帧表达式」——消灭时间线漂移

**做法**（pipeline 阶段 6 第 4 条）：

> "**from 一律写相对表达式**——`SHOTS.x.from + offset`，卡点片写 `beatF(n)`——
> **绝不写裸数字帧号**。时间线平移时钉帧表自动跟随，免除全表重钉。"

并配一条最贵的顺序教训：

> "**画面时间线锁定后才开始**（做声音）。画面每动一次，钉帧表就要全体重对。"

**对本项目的价值**：这与我们的**烘焙器设计高度同源**——`{anchor:"word:37", offset:"-8f"}`
不写绝对帧，由烘焙器算。我们已经在锚点层做到了。**但我们还没把这个原则推广到音效/SFX 层**
（目前项目无 SFX 层）。如果将来加声音，这条纪律要直接抄。

反过来，**这一点我们做得比它更彻底**：它的 `SHOTS.x.from + offset` 仍是**帧数加偏移**，
而我们的锚点是 `word:N`（语义锚点），时间基准变化时**语义不变**。它的相对表达式在
"镜头顺序变了"（第 3 镜变第 5 镜）时仍会失效，我们的语义锚点不会。

### 2.5 「干净上下文 subagent 做终检」——对抗确认偏差

**做法**（pipeline 阶段 7 第 2 条 + `final-review.md`）：

> "派一个**干净上下文的 subagent** 做第三方审查。不给它制作过程中的辩解、修改历史或'应该通过'的暗示"

`final-review.md` 开头更明确：

> "审查 Agent 必须处于干净上下文，不参与制作；不要给它制作过程中的理由、辩解、修改历史或预期结论。"

配套的报告格式要求**每条结论附帧号**：

```
F2 ✗ 第 340 帧：已确认的知识图谱功能没有出现在成片。
Q2 ✗ 第 615 帧：3D 推近后正文文字发糊，见关键帧 f615.png。
```

并且有一条防自欺的纪律：

> "不要用没有证据的'整体不错'代替逐项检查，也不要为了报告好看而全部标记通过。"

**对本项目的价值**：这是**直接可用的**。我们的 `04-validate` 是 16 项校验（JSON→JSON），
但那是**程序校验**，测不到"这个动效做得好不好看"。项目文档里也承认
`meanConfidence` "测不到 SRT 与音频是否对得上"——同理，16 项校验测不到审美。

**建议直接引入**：在 04 之后加一个「独立审查」闸，用干净 subagent 对**渲染产物**做
逐帧检查，结论必须带帧号。这与我们已有的「静默假绿」教训完美呼应——**必须有一道
不共享制作者上下文的检查**。

### 2.6 判例式（编号）文档体系

**观察**：`aesthetic-rules.md` 的每一条都有编号（R1–R4 / Q1–Q11 / S1–S5 / C1–C3 / P1–P4），
`final-review.md` 的检查项也有编号（P/F/V/S/B/D/A/Q 八类）。这带来的效果是：

- 终检报告可以直接写 `Q2 ✗`，**指向精确、可引用、可争论**
- 新增判例只追加编号，**不重排已有编号**（与我们的"登记册只追加"纪律同源）
- 编号一旦发布就不能改语义，否则历史报告全部失锚

**对本项目的价值**：我们的错误码（`E-*` / `W-*` 25 条）已经是这个形态，且做得很好。
可以借鉴的是**把这套编号体系从"错误码"扩展到"审美/工程准则"**——给三个占位阈值
之外的定性判断也编上号，让 review 结论可以 `R2 ✗` 这样引用。

### 2.7 CI 门禁的「产物一致性」检查

**做法**（`pr-checks.yml`，四个作业）：

| 作业 | 检查 |
|---|---|
| `unit-tests` | `npm test`（vitest 纯函数） |
| `verify` | ① `sync-from-cards.py` 重生成 → `git status --porcelain` 检查漂移<br>② `library.json` 引用的每个样片在 release 上真实存在<br>③ URL 形状正则校验（防 XSS）<br>④ tsc strict 编译全部 demo |
| `workbench-build` | tsc -b + vite build + 主题回归 + 遗留兼容 |
| `demo-smoke` | 逐个 demo 渲首帧，断言不崩 |

第 ① 项的注释解释了为什么用 `git status --porcelain` 而不是 `git diff --exit-code`：

> "a brand-new card's regenerated source copy is UNTRACKED, which diff can't see — that's exactly the 'added a card, forgot to commit the copy' mistake this gate exists to catch."

**对本项目的价值**：这是**「生成物必须与源同步」的自动化门禁**，直接对应我们的
「登记册纪律」——项目文档里写过「增补校验项**须先改登记册**，不得只在正文里加，
这条纪律当天就抓到过两次漏同步」。**我们靠纪律，它靠 CI**。CI 更可靠，因为纪律会被遗忘。

**可落地的动作**：如果本项目有从源生成的派生物（如 `docs/templates/` 清单 →
某个 JSON），加一条 CI 检查"重新生成后 `git status` 必须干净"。

### 2.8 兼容性分层：新增能力不破坏旧产物

**观察**（`PageCam.tsx`）：

```tsx
// Does any key request 3D? If not, keep the original flat markup exactly.
const has3D = keys.some((k) => k.rotX !== undefined || ...);
if (!has3D) {
  return ( /* 原始扁平 markup，像素级一致 */ );
}
// 3D 模式：绕焦点旋转缩放，rotX=rotZ=0 时退化为扁平变换（已证等价）
```

即：**新增 3D 能力时，用显式分支保证"未使用新特性 ⇒ 输出与旧版逐像素一致"**。
文档还专门写「With rotX=rotZ=0 this reduces to the flat transform (**proven identical**)」——
不是"应该一致"，是**证明一致**。

`workbench` 的「版本判据」也是同一思路：用清单内容哈希判断"是不是同一版成片"，
旧存档压进撤销栈（⌘Z 可找回）。

**对本项目的价值**：这与我们的**「不可变快照」纪律同源**（阶段目录下游不得回写上游）。
可借鉴的是那个**"证等价"的要求**——我们改 `align.ts` 时加了内置后端，注释里写了
"保持契约与向后兼容"，但**没有测试证明"配了 `ALIGNER_CMD` 的路径输出与改动前一致"**。
它可以，我们应该也可以。

### 2.9 工作台的「同源清单」设计

**做法**（`template/src/workbench.ts` 顶部注释）：

> "Every table here is imported from Main.tsx, so editing the timeline there moves the
> workbench too — **there is no second copy of the timing to drift.**"

以及：

> "清单里的每张表都从 Main.tsx `import`（`SHOTS` / `CAPTIONS` / `SFX` / 字卡文案表），
> **不要手抄第二份**。"

**为什么精妙**：给成片做一个可视化编辑器，最大风险是"编辑器的时间线"和"代码的时间线"
**两份真相漂移**。它用"清单必须 import 不能抄"从源头消灭了这个问题。

**更值得注意的可编辑度设计**（三层）：

| 层 | 能改什么 | 对代码的要求 |
|---|---|---|
| 时间与图层 | 起点/时长/变速/裁剪/不透明度/位移 | 组件是 `useCurrentFrame()` 纯函数 |
| 内容与样式 | 文案/颜色/字号/位置/开关 | 参数暴露为**带默认值的 props** + `schema` |
| 拆解导入 | 逐镜头拆成多轨 | 提供 `src/workbench.ts` 清单 |

关键设计：**"节奏命门保持常量"**——「Motion timing (cues, eases, camera keys) is
deliberately NOT exposed.」即**只暴露"改了不会搞坏质感"的参数**，缓动/时值/相机键
**故意不开放**。

**对本项目的价值**：这是**给用户改的边界设计**。我们的项目明确记录过风险：
`DENSITY.maxItemsPerCue` 是占位值却产 error，而**"项目无编辑 UI，用户只能手改 JSON"**。
工作台给出了正确的解法方向——但更重要的是那个**克制**：**只开放安全参数，命门保持锁定**。
如果我们将来做编辑界面，必须抄这个"哪些能给用户改、哪些锁死"的分层，而不是全开放。

### 2.10 反自欺的纪律条款（措辞值得学）

散见于文档的几条，都是把"容易犯的错"直接写进规则：

| 出处 | 原文 |
|---|---|
| README / SKILL.md | "It is not a video generator." / "诚实留空优于占位" |
| pipeline 阶段 5 坑 1 | "**首检交给用户**：…'镜头视角很差，而且有小抖动'这种问题**不该由用户发现**" |
| pipeline 阶段 5 坑 5 | "跳过 demo 代码直接写：参数是几轮真实裁决调校出来的，新写的版本几乎必然回踩已知坑" |
| final-review 报告格式 | "不要为了报告好看而**全部标记通过**" |
| pipeline 阶段 7 坑 2 | "自检报告流于'全部 ✓'：**用户会读清屏幕上每个字**、会自己截帧对比" |
| SKILL.md 理念 4 | "节奏偏好是**单向的**：历史反馈全部指向'放慢/停留'，从未有一次'太慢了'" |

**最后一条尤其值得学**：「从未有一次太慢了」——这是把**历史反馈的方向性**
统计出来，作为默认值。这与我们对 `MATCH_MIN_SIMILARITY = 0.35` 的校准方法完全一致
（用实测分布而非手感定阈值），但**它把"方向性"也当成了可积累的证据**。

## 三、可做得更好的地方

> 前提说明：本仓库定位是**口播实拍 + 自动叠加 overlay**，video-shotcraft 是
> **产品页宣传片（无实拍人物）**。两者目标不同，以下对比只针对**架构与工程实践**，
> 不比较"哪个片子更好看"。

### 3.1 🔴 它有审美但没有"内容与音轨的对齐"，这正是我们的核心能力

**它的局限**：整条 pipeline 里**没有任何"文字时间戳对齐"环节**。阶段 5 的分镜表是
人工/Agent 手排的，阶段 6 的 SFX 用 `SHOTS.x.from + offset` 或 `beatF(n)` 对齐——
**对齐的基准是"镜头"和"音乐拍"，不是"人说了哪个字"**。

证据：`references/` 下 11 个文档，没有一个是关于 ASR / 强制对齐 / 字幕时间戳的；
`assets/scripts/` 只有页面采集（`capture-template.mjs`），没有音频处理。

**这合理**——产品宣传片通常**无口播**，或口播是后期配音（配音时长已知）。
但**这正是我们项目的价值所在**：口播视频里，"字什么时候出现"必须由音频推导，
SRT 只有句子级窗口。

**我们的做法更好**：
- M-1 方案 b（文字权威归 SRT、时间戳从音频重推）——它没有对应机制
- `alignedRatio` 门控（测「SRT 与音频是否对得上」）——它的终检**只能测"是否好看"，
  测不到"字幕是否和声音对上了"**（A9 只查切点误差，不查字级对齐）
- 末段外溢必须"压缩而非裁掉"（保 72 词）——它无此问题（无音频对齐）

**结论**：**在"内容与音轨严格对齐"这个维度，我们比它领先一个身位**。
它的强项是"视觉语法库 + 审美积累"，我们的强项是"时间基准的可靠性"。

### 3.2 它有 124 张卡但"卡片复用"的粒度比我们粗

**它的做法**：卡是**整镜头**级别的（一个卡 = 一段 3–8s 的完整动效）。
`flying-words` 约 6s / 180f，是"一整个隧穿镜头"。

**观察到的粗糙处**：
- 卡与卡之间**没有组合机制**——`sequences/` 只有 3 个文件（bridge 模板），
  且文档里说"先查 sequences/ 有无适用的桥段模板；有则按其填空"
- 复用单位是"整卡"，无法表达"这张卡的第 2 个动效 + 那张卡的第 3 个动效"
- demo 是**自包含成片级**的（`demos/` 各卡实现），复用时靠"copy 进新项目"
  ——`SKILL.md` 明说"copy 进新项目后自由修改（**不 import 本库**）"

**我们的做法不同**：我们的模板契约是**参数级**的（`synthesize()` + `paramsSchema`），
校验项 #16 `E-P1-01` 禁止模型自造键/帧/颜色，模板与数据是**声明式绑定**关系，
不是"copy 一份代码改改"。

**我们更好的地方**：**复用粒度更细、且有契约保护**。它 copy 代码的方式在"改了模板
但只改了这一个项目"时没问题，但**无法回答"这个项目的改动是否应该回流到库"**——
它的 `shot-polish/` 档案正是在处理这个问题（把 demo 的调校结果固化成 `final-notes/`），
但那是**人工流程**，没有机制保证。

**可建议给它的**：引入 `paramsSchema` 式的契约绑定，让卡成为"声明 + 参数"而非"代码副本"。

### 3.3 「静默假绿」问题：它的验收体系有，但不如我们的硬

**它的验收**：`final-review.md` 是**逐项 checklist + 帧号证据**，比"总体感觉"强得多。
但注意它是**人（或 subagent）看帧**判断的——**没有一条自动断言**能拦住
"checklist 全 ✓ 但实际有 3240ms 时间空洞"这类问题。

它 CI 里的自动检查（`pr-checks.yml`）是**产物一致性 / 编译 / 冒烟不崩**，
**不是质量断言**。`smoke-render-demos.py` 的自述是"渲染每个带时长导出 demo 的首帧
**断言不崩**"——只保证不崩。

**我们的做法更硬**：我们吃过「`alignedRatio=1.000` 但仍有 3240ms 空洞」的亏，
所以把**空洞 / 重叠 / 单调性 / 负时长 / 零时长 / 首末帧**全部锁成了**断言**
（`tests/text-align.test.ts`）。这些是**自动的、每次跑测试都验的**，
不依赖审查者的注意力。

**结论**：**在"可自动断言的质量属性"上我们更强**。它的质量保障依赖密集的人工/Agent
看帧（成本高、依赖注意力），我们靠 183 项测试 + 16 项校验。

**它的这个短板值得它自己警惕**：150 个 demo，`shot-polish` 每个都要人工看帧调校，
**规模上去后人工审不过来**。我们的断言思路可以让它把"呼吸是否 ≥1s"、"字标 hold 是否
≥30f"这类**可量化的审美规则**变成断言——`final-review.md` 的 B3 项
（"品牌字标 hold 是否至少 1 秒，批量动效收尾是否至少静止 0.5 秒"）
**完全是可以自动测的**，但它放在了人工 checklist 里。

### 3.4 工程复杂度与依赖重量：它比我们重，且部分路径未验证

**证据**：

| 项 | 它的状态 | 我们的状态 |
|---|---|---|
| 仓库体积 | **200MB**（1648 条目） | 轻量（代码 + docs） |
| Node 依赖 | 4 个独立 `package.json`（根 / template / workbench / videos） | 单一 |
| Python 依赖 | 3 处（jianying-export 需 venv + pyJianYingDraft；publish 纯标准库；BGM 分析需 uv） | 无 Python |
| 外部服务 | Upload-Post API（需 key）、Remotion 自下载 Chrome | 无 |
| 跨平台 | 🔴 `windows_draft.py` **未真机验证**（README 明说 "win untested"）；"Tested on macOS" | Windows 上实测通过 |

**它的自认短板**（README 原文）：
- "JianYing draft installers (**mac tested / win untested**)"
- "Tested on **macOS**; Linux works with the notes below"
- Headless Linux 三堵墙（并发上限 / 旧 headless 移除 / CDN 被墙）

**我们更好的地方**：单一 Node 栈、无外部服务依赖、**Windows 上真机实测通过**
（这是我们的用户环境）。它那套"Python + venv + pyJianYingDraft + 剪映版本敏感"
的导出链路，对我们来说**引入的是风险不是能力**。

⚠️ **但这里必须诚实**：它的复杂度是**为了覆盖更多产出形态**（剪映工程、社交发布、
浏览器编辑器），是**有意的功能扩张**，不全是坏事。我们"轻"是因为**我们只做一条链路**。
这属于**取舍差异**，不是绝对优劣。

### 3.5 确定性：它守住了红线，但我们可以更上一层

**它的做法**（`SKILL.md` 理念 9）：

> "禁 `Date.now()`/`Math.random()`，一切伪随机固定种子（mulberry32/哈希，
> seed 从 index 派生），逐帧可复现。"

`assets/lib/helpers/rand.ts` 只导出 `mulberry32` 一个函数（8 行），
并有单测覆盖。**这条它是认真的**。

**观察到的边界**：
- `mulberry32` 的实现是 `a = seed | 0`——**种子会被截断到 32 位有符号**
- 文档说"seed 从 index 派生"——但**派生函数本身**（如何从 index 得到 seed）
  在各 demo 里是自己写的，没有统一工具
- 没有看到**"渲染两次逐像素 diff"** 的自动化验证

**我们可以做得更好的地方**：
1. **种子派生函数统一化**——把"index → seed"也收进 `helpers/`，而不是各 demo 自己写。
   否则同一个 index 在不同 demo 里可能得到不同 seed，复现性依赖各自实现正确。
2. **加一条自动验证**：同一 Composition 渲两次 → 逐帧像素 diff = 0。
   这比"禁用某些 API"更强——**禁用 API 是防御，逐像素 diff 是证明**。
   这与它自己 `PageCam` 里 "proven identical" 的精神一致，只是它没用到确定性验证上。

**注意**：这一条我们目前**也没做到**（项目里也没有像素级复现实测），
所以这是**双方都可以改进的点**，不是我们领先。

### 3.6 「八阶段」对短任务的仪式过重

**它的做法**：pipeline 是**八阶段**，阶段 0–3 全是纸面工作（产品简报、需求决策表、
styleframe、镜头映射、分镜、帧级时间轴）。`guided-free-creation.md` 还要求
"每轮只问 1–3 个最能减少返工的问题"，并在 5 个节点暂停确认。

**合理之处**：对"一支 60s 产品宣传片"这种**高成本、一次性**产出，前置对齐非常值得。

**局限**：对**批量、短、重复**的任务（如"给这 20 个 SKU 各出一条 15s 视频"），
八阶段的开销可能超过产出价值。它的三种模式（模板/自主/共同）缓解了这点
（模板模式不进 pipeline），但**模板模式只能有一个模板**（Ink Press）——
124 张卡在模板模式下用不上。

**我们的做法不同**：我们的 pipeline 是**流水线式**（`align → … → render`），
每阶段可独立重跑、阶段目录是不可变快照——**更适合"同一套流程跑很多条素材"**。
用户这次验收的正是这个："我其他素材都跟这个差不多的"——**批量一致性是我们的场景**。

**这给它的建议**：把"阶段 0–3"的结果**做成可复用的批次级产物**（一批素材共用一份
视觉方向 + 分镜骨架），而不是每支片子重跑一遍八阶段。

### 3.7 「124 卡」的规模与维护成本

**观察到的维护痕迹**：
- `demos/_legacy/` **162 个文件**——退役的 demo 保留在仓库里
- `shot-polish/notes/` 217 + `final-notes/` 151 ——**每个 demo 的调校档案**
- CI 里专门有 `test-legacy.mjs`——"Retired demos remain compatible with **saved projects**"

**这说明**：卡片/ demo 一旦发布，**就有用户工程依赖它**，不能随便删。
`workbench` 的"版本判据 + 旧存档进撤销栈"也是为这个服务的。

**它的应对是负责任的**（保留 + 兼容测试），但**成本在累积**：
1648 条目、200MB、四套 package.json、三种测试语言。

**对我们的启示**（这是**注意事项**不是优势）：一旦我们开始发布模板，
**模板的版本兼容就会成为永久成本**。我们现在 `templates/` 零实现，
正好是**在设计"模板版本策略"的最佳时机**——建议：
- 模板 id 与版本号分离（`flying-words@2`），旧版本保持可渲染
- 在 16 项校验里加一项"模板 id 是否在已发布清单内"（防模型自造 id）
- 参考它的 `manifestKey` 思路，给模板清单加内容哈希

## 四、结论摘要

### 最值得借鉴的三条

1. **「参数真相在实现，卡片只给语义」的双层结构** —— 直接对应我们 `templates/`
   零实现的窘境。参数表第三列写"调节手感/越界后果"而非取值范围。
2. **干净上下文 subagent 独立终检（结论必带帧号）** —— 补上我们"16 项校验测不到审美"
   的缺口，且与我们的「静默假绿」教训完美呼应。
3. **调校决策档案（结构化 JSON，中英双语）** —— 把"为什么这么调"变成可检索资产，
   粒度到参数级。

### 我们明确领先的三条

1. **内容与音轨的对齐**（SRT 文字权威 + 音频时间推导 + `alignedRatio` 门控）——
   它整条 pipeline 无此能力，因为产品宣传片这个品类不需要。
2. **可自动断言的质量属性**（空洞/重叠/单调性/首末帧全部锁进测试）——
   它依赖人工看帧，规模上去审不过来。
3. **轻依赖 + 单栈 + Windows 真机验证**（vs 它 200MB / 四套 package.json /
   三种脚本语言 / 剪映导出 win 未验证）。

### 双方共同可改进的

- **逐像素复现验证**：它禁用了非确定性 API（防御），但没做"渲两次 diff=0"（证明）。
  我们也没做。这一点**它的 `PageCam` 里已有 "proven identical" 的精神**，
  只是没用到确定性验证上。
