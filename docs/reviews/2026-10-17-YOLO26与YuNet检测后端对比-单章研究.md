# YOLO26 与 YuNet 作为视频管线感知检测后端（纯 Node / CPU / 离线批处理）的工程取舍

> 时效窗口：last_1_year（检索日 2026-10-17）。所有官方数字与第三方实测已分开标注；非同口径数字显式提示。凡无可靠证据处标「未找到可靠证据」，不填空。
>
> **术语约定（本项目固定含义，全文按此理解）**：`face` = 人脸/头肩区域，遮挡额度 0%，低检测率须 fail-closed 报错；`handheld` = 主持人手持的**讲解用物品**（产品/道具）的**物体检测**，遮挡额度 ≤ 20%，可 fail-soft；`broll` = **B-roll 空镜中的主体**（产品特写与展示）的**物体检测**，遮挡额度 ≤ 30%，可 fail-soft。三者中只有 `face` 属于"不被允许漏检"的通道。运行时常量：纯 Node（`onnxruntime-node` 推理），不引 Python **运行时**；训练/导出是一次性离线步骤，不受此约束。

## 一、结论先行

1. **YOLO26 的官方通用权重做不了人脸，但 YOLO 架构能做——差别在「权重」，不在「架构」。** 这两件事必须分开说。COCO 80 类里只有 `person`，**没有 face 类**（Ultralytics 官方 COCO 数据集页把 80 个类名逐条列出，第 0 类是 `person`，通篇无 face）([Ultralytics COCO 文档](https://docs.ultralytics.com/datasets/detect/coco))，所以**官方 COCO 预训练权重**只能输出人体框。**但社区早已用 WIDER FACE 微调并导出 ONNX 的 YOLO-face 权重，下载即用、不必自己重训**（详见 §二.2 补充节）——本节初稿「必须自建标注重训」的表述过严，**已在本版更正**。Ultralytics 官方术语页亦明确「在面部数据集上微调的 Ultralytics YOLO26 模型」可执行人脸检测 ([Ultralytics 人脸识别术语页](https://www.ultralytics.com/zh/glossary/facial-recognition))。
   **因此 face 通道继续选 YuNet 的理由，不是「做不到」，而是性价比**：
   - **(i) 参数量与体积**：现成 YOLOv8n-Face 为 **3,005,843 参数 / ONNX 11.7 MB**，YuNet 为 **75,856 参数 / 229,738 B** —— 约 **40 倍参数、51 倍体积**。而本项目 `face` 区域的用途只是「取人脸框上部、按 shot 取并集、外扩成安全区」，属**粗几何**而非身份识别，40 倍参数换不到可见收益。
   - **(ii) 许可面**：YOLO-face 是 Ultralytics 权重迁移学习的产物，按厂商立场仍属 AGPL-3.0 覆盖物，分享即触发 §4–§6；YuNet / opencv_zoo 为 **MIT**。
   - **(iii) 维护性**：YuNet 是 opencv_zoo 官方条目、有论文与持续再导出（2023mar → 2026may 动态输入版），且本机已完成与 OpenCV 参照的逐框对齐实测；YOLO-face 权重为第三方个人项目，无版本承诺。
   **一条必须澄清**：「运行时纯 Node」**不是**任何一条 YOLO 路线（含自带通用 detect/pose 与专用 face 权重）的受阻点——ONNX 由 `onnxruntime-node` 直接加载，不触及 `02-perceive` 的纯 Node 约束。
2. **官方 CPU 延迟数字不可直接搬进本项目的选型比较。** `yolo26n-pose` 的 40.3 ms 口径是「ONNX + CPU + COCO val 平均 + batch=1 + 640px + NMS-free 头」，而且 pose 文档页**根本没标 CPU 型号**（只有概览页说明论文里 43% 那个数是 Intel Xeon @ 2.00 GHz）([Ultralytics Pose 文档](https://docs.ultralytics.com/tasks/pose/), [YOLO26 概览](https://docs.ultralytics.com/models/yolo26/))。与此机 YuNet 12ms@512×512 属不同口径，**不可比较**。
3. **官方「最高 43% CPU 提速」未被独立复现。** 社区实测（i7-9700K，纯 CPU，ONNX）得到 yolo26n 65.3 ms vs yolo11n 74.1 ms，约 **12%**，且该实测作者同时报告 YOLO26 在检测精度与鲁棒性上不如 YOLO11 ([ultralytics#24304](https://github.com/ultralytics/ultralytics/issues/24304))。
4. **AGPL 的风险点不在「自用」，在「分享」，而且免费也算。** 不 convey 的使用无任何条件；一旦把含 AGPL 组件的产物交给他人（含无偿赠送），即触发 §4–§6 的完整对应源码义务。§4 原文写得很直白：*"You may charge any price or no price for each copy that you convey"* — **价格从来不是触发条件** ([AGPL-3.0 §4](https://www.gnu.org/licenses/agpl-3.0.en.html))。
5. **在 face 这一单一任务上，YuNet 是明显的工程最优解**：75,856 参数、230 KB、专为小脸设计、宽松许可。YOLO26 在本项目里的**剩余价值只在 `handheld` / `broll` 这两个通道**（两者都是物体检测，定义见文首术语约定）。COCO 80 类里的 `cup` / `bottle` / `cell phone` / `book` / `laptop` 等类目**有可能覆盖其中一部分品类**；但本项目的讲解物品、展示品是否落在 COCO 80 类之内，**本报告未核实**——这正是 §三.2 离线验证要回答的第一个问题。两者的遮挡额度 ≤20% / ≤30% **允许 fail-soft**，不需要像 `face` 那样 fail-closed。但引入它就要为这两个可 fail-soft 的兜底任务单独承担 AGPL 合规成本，因此建议先做一次性离线验证、拿到真实可检出率再决定（见 §三.2）。
6. **系统压力是「变大」而不是「变小」，但大部分可摊薄（直接回答第 2 问）。** 相对 YuNet，YOLO26 的模型体积约 **20–35×**、参数量约 **32–38×**、单帧耗时约 **3.3–5.4×**（后两者口径不同，仅作量级参考）。按本项目 **1 fps** 抽帧、1 小时素材 3600 帧估算，检测总耗时从 YuNet 的约 **43 s** 增至约 **140 s（官方 38.9 ms 口径）～235 s（社区 65.3 ms 口径）**——即约 **3.3–5.4 倍**的增长，但在离线批处理里**不构成实际障碍**。`onnxruntime-node` 的 100 MB 级固定安装成本**两者共用**，与选型无关。真正**无法用工程手段摊薄**的是 **AGPL 合规成本**：它随"是否分享产物"在 0 与"整套对应源码义务"之间跳变，不能靠加机器、降帧率、压模型解决。

## 二、分问题论据

### 1. YOLO26 的准确事实

- **发布状态与时间**：2026 年 1 月正式发布（官方平台页写明 "released January 2026"），2026-01-14 由创始人 Glenn Jocher 在 YOL Vision 2025 首发后正式上线 ([Ultralytics 新闻稿](https://www.ultralytics.com/news/ultralytics-redefines-state-of-the-art-vision-ai-with-yolo26), [Ultralytics Platform](https://platform.ultralytics.com/ultralytics/yolo26))。技术报告为 arXiv:2606.03748，2026-06-02 提交 ([arXiv](https://arxiv.org/abs/2606.03748v1))。
- **型号矩阵**：n / s / m / l / x 五档（官方新闻稿明确 "five model variants, Nano (n), Small (s), Medium (m), Large (l), Extra large (x)"）。
- **支持任务**：detect、segment、**semantic segment**、depth、classify、pose、obb 共 7 类（比 v1.1 记录的 5 类多出 sem 与 depth，属新增事实）；另有开放词汇版 YOLOE-26 ([YOLO26 概览](https://docs.ultralytics.com/models/yolo26/))。
- **参数量 / 体积 / 官方 CPU ONNX 延迟（官方数字，勿与第三方混用）**：

| 型号 | mAP 50-95 (e2e) | CPU ONNX (ms) | T4 TensorRT (ms) | params (M) | 平台标注体积 |
|---|---|---|---|---|---|
| YOLO26n | 40.1 | **38.9 ± 0.7** | 1.7 ± 0.0 | 2.4 | ~5 MB |
| YOLO26s | 47.8 | 87.2 ± 0.9 | 2.5 ± 0.0 | 9.5 | ~19 MB |
| YOLO26m | 52.5 | 220.0 ± 1.4 | 4.7 ± 0.1 | 20.4 | ~42 MB |
| YOLO26l | 54.4 | 286.2 ± 2.0 | 6.2 ± 0.2 | 24.8 | ~51 MB |
| YOLO26x | 56.9 | 525.8 ± 4.0 | 11.8 ± 0.2 | 55.7 | ~113 MB |

（延迟/mAP 来自 [YOLO26 概览](https://docs.ultralytics.com/models/yolo26/)；体积来自 [Platform 模型页](https://platform.ultralytics.com/ultralytics/yolo26)。官方注释明确：Speed 为 `nms=False` 的 NMS-free 头，params/FLOPs 为融合后模型。）

- **pose 分支**：`yolo26n-pose` mAP 57.2、**CPU ONNX 40.3 ± 0.5 ms**、2.9 M 参数、7.6 GFLOPs（[Pose 文档](https://docs.ultralytics.com/tasks/pose/)）——**v1.1 的 2.9M / 40.3ms 核实为真**，但请注意：该页 Speed 脚注只写 "averaged over COCO val images with ONNX on CPU"，**未给 CPU 型号**，比 detect 页的口径信息更弱。
- **e2e 无 NMS 导出**：核实为真，`nms=False` 可选；官方另有说明「默认的一对多头仍需 NMS，精度略高；一对一头输出 (N,300,6)」（[YOLO26 概览](https://docs.ultralytics.com/models/yolo26/)）。
- **未核实（合并为一条待补实测）**：`yolo26n.onnx` / `yolo26n-pose.onnx` **导出物的确切字节数**与 **`onnxruntime-node` 下的载入耗时（session create）**——官方页面这两项都没给（平台标注的 5 MB / 8 MB 是 `.pt`，不是 ONNX）。建议一次本地导出实测同时收这两个数，落进 v1.2，避免分成两条悬空待办。

### 2. 🔴 COCO 80 类里有没有 face？

**没有。明确证据：** Ultralytics 官方 COCO 数据集页把 80 个类名逐条列出，从 `0: person` 到 `79: toothbrush`，**全程不含 face / head 类**（[Ultralytics COCO 文档](https://docs.ultralytics.com/datasets/detect/coco)；同一清单在 COCO8 数据集页的 `coco8.yaml` 中重复出现，[COCO8 文档](https://docs.ultralytics.com/datasets/detect/coco8)）。COCO 官方任务定义里也没有人脸框标注——关键点任务只标注 person 的 17 个身体关键点（[COCO 官网](https://cocodataset.org/)）。

**结论**：标准 YOLO 检测权重**只能输出 `person` 人体框，不能直接输出人脸 bbox**。要得到人脸框，路径是使用**在面部数据集上训练的专用权重**——可以自行微调（WIDER FACE 等基准数据公开可下载，成本在训练、验证与许可承接），**也可以直接用社区已训练好的 YOLO-face 权重（含 ONNX）**，后者不需要自己训练，详见 §2.2 补充。Ultralytics 官方明确「重训会替换分类头，无法"扩展"原有权重」([Ultralytics 论坛](https://forum.ultralytics.com/t/finetuning-model/1252/2))，这也解释了为什么必须用专用权重而不能靠参数调整。

**对 v1.1 的一个补充洞察（重要）**：`yolo26n-pose` 输出的 17 个 COCO 关键点里包含 nose / 双眼 / 双耳（索引 0–4），理论上可由这 5 点反推一个「头部近似区域」。但这不是人脸框，且 pose 模型对侧脸、后脑、低头、小脸都会丢点 —— 在 `face` 通道「遮挡额度 = 0 / 低检测率 fail-closed」的要求下，用关键点凑头部框会把失败模式从"没检测到"变成"检测到了但框错了"，比直接报错更危险。**不建议**；它只适合作为"人物是否在画面中"这类粗粒度信号的中间产物（见 §三.3），**不能**当作人脸检测的替代品。

#### 2.2 补充：现成的 YOLO-face 权重（对初稿「必须重训」的更正）

初稿写「要输出人脸框必须拿 WIDER FACE 级标注重训」，**这句不准确，现更正**：社区已有训练完成、可直接下载（含 ONNX 导出）的 YOLO-face 权重，**不需要自己重训或自己标注**。

| 权重来源 | 覆盖架构 | 是否提供 ONNX | WIDER FACE（自评，口径未统一） | 参数 / 体积 |
|---|---|---|---|---|
| lindevs 系（Moltas18/yolov8-face 等镜像） | YOLOv8 n/s/m/l/x | ✅ `yolov8n-face.onnx`，11.7 MB，附 SHA-256 | Easy 93.79 / Medium 91.82 / **Hard 79.38**（v8n） | 3,005,843 / 6.0 MB（pt）、11.7 MB（onnx） |
| akanametov/yolo-face | YOLOv11 / v10 / v8 / v6 | ⚠️ 仓库 Release 的 ONNX 列表以 yolov12 系为主，face-n 的 ONNX 需自行导出 | README 仅给 PR 曲线图，**未给 AP 数值表** | README 未列出 |
| Ultralytics 官方 | YOLO26 | — 官方不发布人脸专用权重，只说明「在面部数据集上微调后可用」 | — | — |

**必须注意的三点**：

1. **WIDER FACE 数字不可直接比。** YuNet 侧有两个公开口径：opencv_zoo README 正文写 `0.834 / 0.824 / 0.708`（论文口径），opencv_zoo `tools/eval` 表写 `0.8844 / 0.8656 / 0.7503`；YOLO-face 侧是第三方自评 `93.79 / 91.82 / 79.38`。**三套数字的评测脚本、输入尺寸、是否多尺度都不同，任何"谁高几个点"的结论都不成立**——本报告不做该对比。
2. **权重是第三方个人项目**，非 Ultralytics 官方发布，无版本维护承诺；且推理示例用 `imgsz=1280`（训练 640），意味着推理成本按 1280 计。
3. **许可归属不变**：这些权重是 Ultralytics 权重迁移学习的产物，按厂商立场仍属 AGPL-3.0 覆盖物；仓库 README 的 License 段也仍写着 GPL-3.0 + Enterprise 双许可。

**一个值得注意的反讽**：Ultralytics 讲「人脸识别」的那篇官方术语页，示例代码里跑的检测器是 **YuNet**（配 SFace 做人脸比对），不是自家 YOLO——页面正文的说法是「**在面部数据集上微调的** YOLO26 可以做人脸检测」，即**官方立场也是「需专用权重」**，与本节结论一致 ([Ultralytics 人脸识别术语页](https://www.ultralytics.com/zh/glossary/facial-recognition))。

> **更正性质**：这一节改了初稿的一个事实判断（「必须自己重训」→「已有现成权重」），**但不改变 face 通道的选型结论**——理由从「做不到」改为「40 倍参数、51 倍体积、许可受限、无官方维护，而该通道只需要粗几何」，见 §一.1。

### 3. YOLO26 vs 专用人脸检测器（YuNet / SCRFD）



**支持的证据（YuNet 侧）**：
- YuNet 是为「小脸占多数」这一分布专门设计的：论文指出 WIDER FACE 中约 80% 人脸是小脸，通用骨干网络把参数浪费在只占约 2% 的大脸上；YuNet 仅 **75,856 参数**，在 WIDER FACE val **hard 集 81.1% mAP（单尺度）**，Intel i7-12700K 上用 **ONNXRuntime** 跑 320×320 只要 **1.6 ms/帧**（[YuNet 论文 PDF](https://link.springer.com/content/pdf/10.1007/s11633-023-1423-y.pdf)）。
- 该测量环境（ONNXRuntime + Intel CPU）与 YOLO26 的 CPU ONNX 口径**同类**，但因 CPU 型号不同（i7-12700K vs Xeon 2.0GHz），数字仍**不可直接比较**。
- YuNet 的检测范围约 10×10 至 300×300 像素人脸，训练时即按此分布优化（[opencv_zoo README](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)）。
- 轻量检测器在小脸/侧脸/遮挡上优于传统方法：OpenCV 官方对比实验里 YuNet 在 640×640 图上检出 137 张脸 vs Haar 29 张，耗时 22.32ms vs 111.26ms（[OpenCV 官方博客](https://opencv.org/?p=17939/)）——注意这是 YuNet vs Haar，**不是** vs YOLO。

**反驳/保留（通用检测器侧）**：STAL（Small-Target-Aware Label Assignment）确实是 YOLO26 针对小目标的正向改进，第三方分析给出 YOLO26x 的 AP_small 38.8% vs AP_large 71.4% 的分层数据（[Robolabs 基准分析](https://www.robolabs.ai/fr/resources/blog/benchmarking-reality-check-cv-model-deployment)，属第三方技术博客，非同行评议）。这说明 YOLO26 的小目标能力有进步，但在 COCO 的"小目标"尺度定义下仍是弱项。

**未找到可靠证据**：公开的「YOLO26 / YOLO11 人脸召回率 vs YuNet 人脸召回率」对照实验。检索到的 YOLO-face 对比表（YOLOv8-Face mAP 94.2% @WIDER FACE 等）来源为营销型博客且**未见可复现方法**，本报告不采用。因此第 3 问的直接对照只能给"结构性强、直接实证缺"的结论：**在单一任务上，专用检测器以 1/32–1/38 的参数量（YuNet 75,856 对 yolo26n detect 2.4 M / pose 2.9 M）拿到了针对该任务优化的召回曲线，通用检测器在此任务上不存在"多任务统一"之外的净优势。** 单帧耗时此处**只列数字、不列倍数**：本机 YuNet 512×512 实测 **12 ms**，对比官方 yolo26n 640px 口径 **38.9 ms**、社区 640px 口径 **65.3 ms** —— 三者的 **CPU 型号与输入尺寸均不同，不可直接相除**。**本课题不存在同口径倍率**：YuNet 实测在 512×512 / 本机 CPU，YOLO26 只有 640px 官方值与另一台 i7-9700K 的社区值；§二.6 表格给的是**跨口径量级参考**（表中已标注不可相除），不是同口径对比。

### 4. YOLO26 相对 YOLO11 / YOLOv8 的实际改进

**官方声称**（须与实测分开看）：
- 原生端到端无 NMS（`nms=False`）、彻底移除 DFL、MuSGD 优化器、ProgLoss、STAL（[官方新闻稿](https://www.ultralytics.com/news/ultralytics-redefines-state-of-the-art-vision-ai-with-yolo26)）。
- **nano 版在标准 CPU 上最高快 43%**；概览页把这个数精确锚定为「论文中 YOLO26n vs YOLO11n、Intel Xeon CPU @ 2.00 GHz、CPU ONNX」（[YOLO26 概览](https://docs.ultralytics.com/models/yolo26/)）。论文摘要只报 T4 TensorRT 延迟，43% 出现在正文/官网而非摘要（[arXiv 摘要](https://arxiv.org/abs/2606.03748v1)）。
- 官方表格里 YOLO26n 的 38.9ms 与 YOLO11n 的前代数字对比并不在同页给出，需跨页取数——本身就是口径风险。

**第三方实测 / 复现情况**：
- **社区 Issue #24304（最接近可复现的一份）**：i7-9700K，同一套 ultralytics 环境，ONNX CPU 推理 —— yolov8n 77.5ms、yolo11n 74.1ms、yolo26n **65.3ms**；换算 **比 YOLO11n 快约 12%，比 YOLOv8n 快约 16%**，**远未达 43%**。同一实测里 PyTorch CPU 推理 yolo26n 66.7ms vs yolo11n 72.1ms（约 7%）。作者并报告精度与鲁棒性劣于 YOLO11 ([ultralytics#24304](https://github.com/ultralytics/ultralytics/issues/24304))。该 Issue 未见官方给出同口径回应，属"未闭环"状态。
- 第三方教程实测称 YOLO26n CPU 56.1ms→38.9ms、降 31%（[sotaaz 分析](https://sotaaz.com/post/yolo26-tutorial-en)），与官方 43%、社区 12% 三方不一致 —— 说明**该数字强依赖 CPU 型号与后端配置，不能作为跨机器承诺**。
- **结论**：43% 是"论文最优条件下单点"，不是可迁移的工程常数；本项目应按 **10–15%** 的保守改进量估算，甚至按"无改进"做预算。

### 5. AGPL-3.0 的义务边界（本课题最高风险项）

**(a) 「分发 / conveying」的准确定义与触发条件**
AGPL-3.0 §0 定义：*"To 'convey' a work means any kind of propagation that enables other parties to make or receive copies. Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying."*（[AGPL-3.0 §0](https://www.gnu.org/licenses/agpl-3.0.en.html)）。即：**convey = 让别人能拿到副本**。FSF 的解读与此一致：§4–§6 的义务"只在程序被分发、更准确地说，被 convey 给接收者时才适用"（[FSF Bulletin: The fundamentals of the AGPLv3](https://www.fsf.org/bulletin/2021/fall/the-fundamentals-of-the-agplv3)）。

**(b) 「免费」是否构成分发？—— 构成。**
这是本课题最容易踩的坑。三条直接证据：
- §4 原文：*"You may charge any price or no price for each copy that you convey"* —— 价格与触发条件完全解耦（[AGPL-3.0 §4](https://www.gnu.org/licenses/agpl-3.0.en.html)）。
- FSF GPL FAQ「Is making and using multiple copies within one organization or company 'distribution'?」答：组织内部复制给自己用**不是**分发；但 *"when the organization transfers copies to other organizations or individuals, that is distribution"*（[GNU GPL FAQ #InternalDistribution](https://gnu.org/licenses/gpl-faq.html.en)）。
- 补充 FSF FAQ 4.25 条：给**同一公司同事**拷一份、且双方都是工作使用，不算 convey，"副本属于公司"；据此反推：**给公司/组织之外的任何人（哪怕免费、哪怕朋友）就是 convey**（[GNU GPL FAQ #v3CoworkerConveying](https://www.gnu.org/licenses/gpl-faq.html.en#v3CoworkerConveying)）。

**(c) 「自用不触发」vs「分享触发」的分界线**
- **自用**：§2 明确 *"This License explicitly affirms your unlimited permission to run the unmodified Program... You may make, run and propagate covered works that you do not convey, without conditions so long as your license otherwise remains in force."* —— 只要你**不 convey**，无任何条件（[AGPL-3.0 §2](https://www.gnu.org/licenses/agpl-3.0.en.html)）。FSF 亦确认私有使用、不发布即无义务（[GNU GPL FAQ #GPLRequireSourcePostedPublic](https://www.gnu.org/licenses/gpl-faq.html)）。
- **分享**：一旦 convey，§4（逐字副本：保留版权声明、许可证全文、无担保声明）+ §5（修改版：显著标注修改与日期；**§5(c) 整个作品整体按 AGPL 授权给任何拿到副本的人**）+ §6（以目标码形式 convey 时须一并提供机器可读的 **Corresponding Source**，五种方式之一）同时生效（[AGPL-3.0 §4/§5/§6](https://www.gnu.org/licenses/agpl-3.0.en.html)）。
- **§13（网络交互）在本项目不适用**：本项目是本地离线批处理，没有任何"用户远程通过网络与本程序交互"的场景；§13 只要求**修改过的版本**在提供远程网络交互时"prominently offer"对应源码（[AGPL-3.0 §13](https://www.gnu.org/licenses/agpl-3.0.en.html)）。所以**§13 不是本项目的风险来源，§4–§6 才是**。
- 一句话边界：**「自用」= 不 convey = 零义务；「无偿分享给他人」= convey = 必须整体 AGPL + 交出完整对应源码。** 商业化与否、收不收钱、用户多少，都不改变这个判断。

**(d) Ultralytics 双许可：厂商主张 vs 法律要求（必须分开写）**

> ⚠️ **阅读提示（请先看这一句再往下）**：本小节是对许可条款的**解读，不构成法律意见**。本课题里最容易被直接照做、也最容易踩坑的就是这一段——如果要把下面的推论写进流程或对外说明，请先让律师确认。

- **厂商主张**：Ultralytics 的许可页 FAQ 明确写：只要使用其代码/模型/架构/训练管线/微调模型，就必须二选一 —— 要么把**整个项目**开源为 AGPL-3.0，要么买 Enterprise License；并列举「即使你：从零自己训练、不用预训练权重、**仅在内部使用或仅用于研发**、通过 SaaS/API 私有部署……」都适用（[Ultralytics License 页](https://www.ultralytics.com/license)）。
- **法律要求**：AGPL-3.0 §2 授予"不受限制地运行"的权利，且**不 convey 的作品可以无条件地制造、运行、传播**；§10 明确 *"You may not impose any further restrictions on the exercise of the rights granted or affirmed under this License."*，§7 把超出许可清单的附加条款一律定性为 "further restrictions"（[AGPL-3.0 §2/§7/§10](https://www.gnu.org/licenses/agpl-3.0.en.html)）。
- **如何读这两者的差**：厂商 FAQ 把「内部使用 / 纯研发」也纳入付费区，**超出了 AGPL 文本本身授予的权利边界**，属于厂商的商业政策主张而非 AGPL 的法定要求；同时要注意 Ultralytics 是版权人，它可以对**自己**的软件另发商业许可，但**已经按 AGPL 合规使用的人，其 AGPL 授权是不可撤销的**（§2 "irrevocable provided the stated conditions are met"）。
- **实操含义**：只要本项目**不 convey**，AGPL 侧确实没有义务；但厂商可能在分发渠道（模型托管、商标、文档）层面主张别的条件，这条本报告未能核实到权威文本 → 标 **未找到可靠证据**。

**(e) 模型权重的许可归属**
- **权重本身**：Ultralytics FAQ 直接回答「Are Ultralytics YOLO trained models licensed under the AGPL-3.0? **Yes.** All Ultralytics YOLO trained models fall under the AGPL-3.0 License by default. The AGPL-3.0 License covers the training code and the models produced by that training code.」（[Ultralytics License 页](https://www.ultralytics.com/license)）。即 `.pt` 与 `.onnx` 导出物**按厂商立场都是 AGPL-3.0 覆盖物**。这条对 §三.2 的"是否引入 YOLO26 做 handheld/broll"同样适用：**重训与否不改变权重的许可归属**。
- **输出物（JSON 坐标）**：AGPL §2 有一句常被忽略的关键限定：*"The output from running a covered work is covered by this License only if the output, given its content, constitutes a covered work."*；FSF 进一步解释 *"The output of a program is not, in general, covered by the copyright on the code of the program... whether you pipe it into a file, make a screenshot, screencast, or video."*，以及 *"when a program translates its input into some other form, the copyright status of the output inherits that of the input"*（[AGPL-3.0 §2](https://www.gnu.org/licenses/agpl-3.0.en.html), [GNU GPL FAQ #WhatCaseIsOutputGPL](https://www.gnu.org/licenses/gpl-faq.html)）。
  → **推导**：模型对你自己的视频帧输出 bbox 坐标 JSON，其版权继承自**你的视频**，不因模型是 AGPL 而被"传染"；把这份 JSON 喂进自有管线不构成衍生作品。§5(c) 规定的是"整体授权给拿到副本的人"，但"整体"指 convey 出去的那个**程序作品**，不是它的运行时数据输出。
- **真正的传染点**：不是 JSON，而是**"载入并运行该模型的代码"**。如果本项目在 Node 里直接调用 ultralytics 的 JS/Python 代码，或把 AGPL 权重随产物一起 convey 出去，那才落到 §5/§6。**只把 ONNX 当数据文件、用 onnxruntime（MIT）推理、运行时下载不随产物分发**这条路径，在 AGPL 文本下风险最低 —— 但"不随产物分发"必须真做到，否则又回到 (b)。
- **未找到可靠证据**：`onnxruntime-node`（MIT）加载 AGPL 模型权重是否构成衍生作品的司法判例或权威解释。业界对此无统一答案，本报告不做断言。

### 6. 工程压力对比（同一台无 GPU 机器）

| 维度 | YuNet（230 KB）+ 可选姿态模型 | 单个 YOLO26 多任务模型 | 量级差 |
|---|---|---|---|
| 模型体积 | `face_detection_yunet_2026may.onnx` = **229,738 B**（本机实测；上游 2023mar 为 232,589 B） | `yolo26n` ≈ 5 MB（`.pt`，官方平台标注）；pose 版 ≈ 8 MB；ONNX 导出物体积**未核实** | 约 **20–35×** |
| 单帧 CPU 耗时 | 本机实测 **~12 ms @512×512**；论文 1.6 ms @320×320（i7-12700K, ONNXRuntime） | 官方 38.9 ms（detect）/ 40.3 ms（pose），口径为 640px + COCO val 平均 + `nms=False`；社区实测 65.3 ms（i7-9700K, ONNX） | 官方口径约 **3.3×**，社区口径约 **5.4×**（CPU 型号与输入尺寸均不同，**不可直接相减/相除**，仅量级参考） |
| 参数量 | **75,856**（YuNet 论文） | 2.4 M（detect）/ **2.9 M**（pose） | 约 **32–38×** |
| 常驻内存（RSS） | **未实测** | **未实测** | 本维度缺数据，不做推算（见下） |
| 依赖安装体积 | `onnxruntime-node@1.30.0` **本机实测 288 MB**（`du -sh node_modules/onnxruntime-node`，2026-10-17），**两者共用** | 同左 | YuNet 230 KB ≈ **0.08%**、yolov8n-face ONNX 11.7 MB ≈ **4%** —— 都不改变安装成本的量级 |

**关于内存（RSS）维度为何缺**：本报告未取得 YuNet 与 yolo26n 在同机同输入尺寸下的常驻内存实测，二手资料中也没有可复现的同口径数字，按"不填空"的原则留空、不做倍数推算。按本管线经验，离线批处理里视频解码与帧缓冲的占用通常高于模型常驻内存，因此该维度对选型的权重较低（**此句为本管线经验判断，非本次实测结论**）；若后续要补，建议在同一次离线验证里用 `/usr/bin/time -v` 或 `process.memoryUsage().rss` 顺带记录。

**关于 `onnxruntime-node` 体积这个前提的核实结论**：**已实测** —— 本机 `du -sh node_modules/onnxruntime-node` = **288 MB**（`onnxruntime-node@1.30.0`，2026-10-17）。此前版本不引用任何二手 MB 数字（各版本 / 各统计口径差异极大，无可验证的一手来源），现已用本地实测值替代。凡需体积占比一律以 **288 MB** 作分母；换机或升级 ORT 后应重新测量。

**关键结论**：`onnxruntime-node` 这块 **288 MB** 的固定成本**与选哪个模型完全无关**，两者共用。因此"用 YOLO26 会不会让安装包变大"这个担心放错了位置 —— 相对增量只是模型文件本身（YuNet 0.23 MB ≈ 固定成本的 0.08%，yolov8n-face ONNX 11.7 MB ≈ 4%）；真正被放大的是**单帧耗时的 3.3–5.4×**（官方 3.3× / 社区 5.4×，**不同 CPU 与输入尺寸，口径不同，量级参考**；在 1 fps 抽帧下无关紧要）和**AGPL 的合规成本**（与体积无关，且无法用工程手段摊薄）。

## 三、工程建议（针对本项目）

1. **face 通道锁定 YuNet，不因"多任务统一"而让位。** 前提先说清：**这不是"YOLO 做不到人脸"**——现成 YOLO-face 权重（含 ONNX）确实存在，下载即用。真正的理由是三条：
   - **参数与体积不划算**：现成 YOLOv8n-Face 为 **3,005,843 参数 / ONNX 11.7 MB**，YuNet 为 **75,856 参数 / 229,738 B**，约 **40 倍参数、51 倍体积**。而 `face` 区域在本管线里只用于「取框上部 → shot 级并集 → 外扩成安全区」，是**粗几何**用途，不是身份识别，也没有小脸极限场景的硬指标；这种情况下 40 倍参数没有可兑现的收益。
   - **许可面**：YOLO-face 是 Ultralytics 权重迁移学习的产物，按厂商立场仍属 AGPL 覆盖物（见 §二.5(e)），一旦分享即触发 §4–§6；而 YuNet / opencv_zoo 为 **MIT**，许可面干净。
   - **维护性与已验证性**：YuNet 是 opencv_zoo 官方条目（2023mar → 2026may 持续再导出，含动态输入版），本机已完成与 OpenCV 参照的**逐框对齐 <0.5px** 实测、载入 87 ms / 推理 12 ms 达标；YOLO-face 权重是第三方个人项目，无版本承诺，CPU 耗时本课题**未实测**。
   - **一处必须澄清**：「运行时纯 Node」**不是**任何 YOLO 路线的受阻点——ONNX 由 `onnxruntime-node` 直接加载，不触及 `02-perceive` 的运行时约束。
   - **如果将来 face 需求升级**（如需要身份比对 = 人脸识别，而非仅检测），那时才该重新选型：识别需要 embedding 模型（ArcFace / SFace 一类），检测器本身不提供该能力，换 YOLO 也解决不了。
2. **`handheld` / `broll` 是 YOLO26 在本项目里唯一可能的落点，值得先做一次性离线验证，但不宜直接进每日管线。**
   - **为什么是"唯一可能的落点"**：这两类在本项目里都是**物体检测**——`handheld` 是主持人手持的**讲解用物品**（产品/道具）的检测，`broll` 是 **B-roll 空镜中的主体**（产品特写与展示）的检测。COCO 80 类里的 `cup` / `bottle` / `cell phone` / `book` / `laptop` 等类目**有可能覆盖其中一部分品类**；但本项目的讲解物品、展示品是否落在 COCO 80 类之内，**本报告未核实**——这正是本条离线验证要回答的第一个问题。同时两者的遮挡额度分别是 **≤20% / ≤30%，允许 fail-soft**，不像 `face` 必须 fail-closed——也就是说检出率不完美是管线可以容忍的。
   - **收益**：开箱即用的通用物体检测；一次推理同时覆盖 handheld 与 broll 两类区域；无需自建标注（**前提是目标品类在 COCO 80 类内**）——这一点与 face 通道的处境不同：face 早已有合适的现成小模型，"有没有权重"不是问题，问题是"为粗几何用途付 40 倍参数是否划算"（见 §三.1）。
   - **成本**：① **AGPL 合规负担**（权重按厂商立场是 AGPL 覆盖物，见 §二.5(e)）；② **模型体积 20–35×**；③ **单帧耗时 3.3–5.4×**（口径不同，仅量级参考）。后两项在 **1 fps** 抽帧下可接受：1 小时素材 3600 帧，检测总耗时约从 43 s 增至 140–235 s（见 §一.6）。
   - **可执行建议**：**先用 `yolo26n` 对现有素材做一次性离线验证**（不接入每日管线、不把产物交给外部），第一个要回答的问题是"本项目的手持物品与展示品到底落在 COCO 80 类的哪几类里、有没有落空"，其次实测 handheld / broll 两个通道的**真实可检出率**与漏检模式（小目标产品特写、反光包装、手持遮挡是否造成漏检），拿到数据再决定是否进入每日管线。
   - **若验证后仍倾向否决**，理由必须换成真实成立的那两条：(a) **AGPL 成本 vs 收益不划算**——为两个可 fail-soft 的兜底任务背 AGPL 义务，换来的是"本来可以容忍误差"的通道精度小幅提升；(b) **产品特写/小目标精度未知**——YOLO26 在小目标上的分层数据来自第三方博客、非同行评议（§二.3），本课题**未找到可靠证据**证明它在产品特写这类小目标上够用。**注意：`handheld` / `broll` 是物体检测任务，不能用镜头/场景分类或运动估计（光流、相机抖动）替代。**
3. **如果未来确实需要"人物出现"信号**，`yolo26n-pose` 的 17 关键点是比 detect 更合适的中间产物（一次推理同时给人体框 + 姿态，可用于判断"人物是否在画面中/是否在说话"），但**仍须先解决 AGPL**：要么整条管线 AGPL + 分享时交付完整源码，要么改走 Apache/MIT 许可的姿态模型（如 RTMPose 系列，本报告未核实其许可，建议另开一条核查）。**注意：这条仅用于"人物是否在场/是否在说话"这类粗粒度信号，`face` 通道（遮挡额度 0、fail-closed）不可用它替代，理由见 §二.2。**
4. **v1.1 的三处需修订**：① "支持 5 类任务"→ 实为 7 类（新增 sem、depth）；② 40.3ms 需补注"pose 文档页未标 CPU 型号"；③ 43% 需补注"社区复现约 12%，不可作为迁移常数"。
5. **AGPL 的合规动作清单（若仍要用 YOLO）**：默认只自用 → 零义务；一旦分享产物给任何人 → 必须①保留 LICENSE 与版权声明、②标注修改、③整体以 AGPL-3.0 授权、④提供完整对应源码（含构建脚本）、⑤在文档中显式提示接收方其再分发权利。**最省事的做法是：从设计上就不 convey**（运行时下载、不打包、不随产物分发），但这条设计与"换机可移植性优先"存在张力，建议在产品文档里写死"本工具不随附任何 AGPL 组件，需用户自行下载"这一条。
