## 2. `npm run motion:accept -- <file>` 六道验收（Task 2，提案 §4）

实现全在 `src/core/motion-accept.ts`（Node 侧专用，不进浏览器 bundle）；
`tools/accept-motion-spec.mts` 只做 I/O 壳。创作期 spec 的**唯一入库通道**：

| 门 | 判据 |
|---|---|
| 1 structure | `validateMotionSpec`：JSON 可解析、颜色只认令牌、图元/属性/缓动白名单、≤16KB |
| 2 registration | `deriveDeclaration` 后 id/scope/layer/footprint 齐备；`custom/<语义名>@<semver>` 合法 |
| 3 frames | 注册后于帧 6/45/72（与画廊同帧位）`renderToStaticMarkup`：DOM 非空白、无 `data-template-missing` |
| 4 animates | **三帧 markup 两两不等**——「动效真在动」唯一可靠自动化判据；生成物须有贯穿 item 的动效，静态摆设在此被拦 |
| 5 lint | spec 原文零 `Date.now` / `Math.random` / `useFrame` / `animation:` |
| 6 签章 | 全过后产出 acceptance 块；🔴 **无时间戳**——同输入重跑逐字节一致（确定性红线 E2） |

失败逐条报因 + 退出码 1（渲染门前任何失败短路，绝不对未过结构校验的 spec 渲染）。
全部通过则把**带签章全文**写入 `templates/specs/custom-<语义名>.json` 并打印 specHash。

## 3. spec-loader 验签（Task 3，AC-7 / AC-8）

`src/core/spec-loader.ts` 装载循环内：`custom-*` 入库文件必须带吻合签章——

- 缺签章 → ConfigError，错误信息给可执行做法（重跑 `npm run motion:accept`）；
- `acceptance.specHash !== canonicalSpecHash(spec)`（文件被手改）→ ConfigError；
- **canonical spec hash** = sha256(spec 去 acceptance 键后 `JSON.stringify(..., null, 2)`)
  ——签发与验签两侧可复算（裁决演进：Task 2 初版按 raw bytes，Task 3 落地前统一为
  canonical hash，见 commit `3b25ff6`）。
- 非 `custom-*` 文件（8 份基线 spec）无签章照常装载——向后兼容（AC-8 回归保障）。
- **版本并存**：`custom/x@0.1` 与 `@0.2` 两文件同目录并存 → 双双注册、各自可达
  （layer 区分）；已出片 job 引用的旧版本永不失效（AC-8）。

## 两次裁决

### 裁决一：签章白名单扩展（commit `9be99de`）

Task 2 的 acceptance 块最初装不进来——spec 顶层键白名单没有 `acceptance`。
补：白名单收录 `acceptance` 并校验形状（`toolVersion` / `specHash` / `gates`），
否则「签章可装载」无从谈起。属结构修正，非校验项增补（不动 18 项清单与登记册）。

### 裁决二：验签判据 = 文件名 `custom-` 前缀，非 id 前缀（Task 3 交付时提出，本日追认）

`validateMotionSpec` 的 ID_RE 强制**所有** spec 的 id 以 `custom/` 开头——8 份基线
spec（fade-up 等）的 id 同为 `custom/`，按 id 判会把基线全部拒之门外。文件名前缀
（`custom-*.json`，`motion:accept` 产物恒此形）是「验收产物」与「基线手写 spec」
唯一可靠区分，故验签按文件名判。Task 3 报告的 5 条用例在该判据下全部满足。
