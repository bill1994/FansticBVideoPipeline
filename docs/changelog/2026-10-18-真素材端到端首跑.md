# 真素材端到端首跑 —— 两个渲染层阻塞 bug 与一条对齐假绿

> 日期：2026-10-18
> 触发：执行计划书 D1 的未达成项「用真素材产出 1 件可发布成片」
> job：`jobs/e2e-perceive`（kukini.mp4，1920×1080 / 59.94fps / 6667 帧 / 48 条 SRT cue）
> 结论：**流程首次全通**（align → perceive → storyboard → validate → render），
> 途中抓出 **2 个必须修的渲染 bug** 与 **1 条对齐假绿**；成片已产出但**未达可发布**（见 §4）。

---

## 0. 为什么要做这次跑

`jobs/` 下 4 个 job 全部停在 `01-align` 或 `02-perceive`，**没有任何一条跑过 03/04/05**。
demo job 是 `hasVideo: false`（走占位底分支）⇒ **「有真实视频」那条代码路径从未被执行过**。
本次是它第一次被跑，所以缺陷是「被隐藏」而非「不存在」。

---

## 1. 第一个 bug：`<OffthreadVideo>` 的 src 全路径不可用（已修）

**症状**：渲染 2836/6667 帧后崩，或全程黑帧但**不报错**。

**三种写法实测**（Remotion 4.0.534，静态服务器把 URL 映射到 **bundle 目录**）：

| props 里的 `video` | 结果 |
|---|---|
| `../00-input/kukini.mp4`（原实现） | ❌ 404 —— `bundle/00-input/kukini.mp4` |
| `kukini.mp4`（只传文件名） | ❌ 404 —— `bundle/kukini.mp4` |
| `public/kukini.mp4` + `--public-dir=<00-input>` | ✅ 命中 |

**修法**（`src/stages/render.ts`）：`video: 'public/' + basename`，并给 remotion 加 `--public-dir=<job>/00-input`。

**为什么难发现**：404 只在**视频真的被挂载**时才报；而挂载与否取决于第二个 bug（见 §2），
所以在多数帧上它是「静默黑屏」而不是报错。

**量测法**：`ffmpeg` 抽单像素比对。修复前中心像素 `0,0,0`（根容器背景），
修复后 `197,207,214`（素材墙面）——**用像素值而不是眼睛判断「视频在不在」**。

## 2. 第二个 bug：载体轨把视频裁在了自己的时间窗内（已修）

**症状**：只要 storyboard 里存在**一个**载体类 item（本例 `cinematic/punch-in`，footage-transform），
**该 item 区间之外的整段视频消失**，成片变成纯黑 + 只有叠加层。

**根因**：`CarrierTrack` 把**整条链**套在 `<Sequence from={start} durationInFrames={end-start}>` 里。
`carrier.tsx` 文件头写的意图是「视频必须全程可见」，实现却只覆盖了 `[trackStart, trackEnd)`。
`punch-in` 只占 150 帧 ⇒ 另外 6517 帧视频没有被挂载。

**证据链**：
- 帧 100/300/600（载体窗外）：中心像素 `0,0,0`，且**无任何加载错误**（children 未挂载）
- 帧 2860（载体窗内）：立刻报视频 404（children 被挂载）
- 移除 `bg-punch` 轨后同一帧：像素变成素材色

**修法**（`src/remotion/carrier.tsx` + `Overlay.tsx`）：`CarrierTrack` 新增 `durationInFrames`，
窗口前 `[0, start)` 与窗口后 `[end, duration)` 各补一段**无变换透传**，
把「任一时刻恰好渲染一份 children、零或一层变换」这条不变量扩展到**整条时间轴**。

**为什么这是第四层假绿**：`carrier.test.ts` 测的是 `splitCarrierSegments` 这个**纯函数**，
它算出的分段在轨道窗口内完全正确 —— 错的是**外层容器的作用域**。
组件单测与静态断言都不可能发现「窗口外没渲染」。

## 3. 一条对齐假绿：`alignedRatio = 1.000` 但有 7 秒空洞

**现象**：align 门控通过 —— 均值置信度 0.9113、低置信占比 3.19%、`alignedRatio = 1.000`。

**事实**：SRT 的 cue2 结束于 8.05s、cue3 起于 15.13s（7.08s 静音）。
`ffmpeg volumedetect` 实测该区间 **mean −58.2 dB / max −34.1 dB**（语音区是 −23 / −19 dB）⇒ **确实静音**。
但 `words.json` 把 cue3 的「它把 spirit Donkage 的中底和 cookie 的」整句词放在 **484–877 帧（8.07–14.63s）**，
即**塞进了静音里**，偏差 **−7.06s**。

**根因**：whisper 吐出一个 **8.08s–20.52s 的单一分段**，把 cue3+cue4 合并，横跨 7 秒静音；
DP 只能在这 12.4 秒里平摊词。`builtin-align.ts` 调 whisper 时**没有传 `-ml`（最大分段长度）与 `-sow`（按词切分）**。

**为什么门控没拦住**：`alignedRatio` 的定义是「SRT 词对上 **token** 的比例」——
它衡量**文本匹配**，结构上**看不见时间错位**。这次它必然报 1.0。
⇒ 与 MEMORY 里记的「曾出现 alignedRatio=1.0 却有 3240ms 空洞」是**同一个结构性盲区**，不是偶然。

**损伤范围**（`tools/probe-align-drift.mjs` 实测）：48 条 cue 中 **4 条**偏差 >1s：

| cue | SRT 起点 | 词落点 | 偏差 |
|---|---|---|---|
| 3 | 15.13s | 8.07s | **−7.06s** |
| 4 | 17.93s | 16.60s | −1.33s |
| 36 | 84.08s | 82.68s | −1.40s |
| 48 | 108.10s | 109.16s | +1.06s |

**未修**：这属于「门控指标选型」问题，按项目纪律**先改裁决册再动实现**。已在 MEMORY 记入待裁决。

## 4. 成片验收（`jobs/e2e-perceive/05-render/out.mp4`）

2160p→1080p，6667 帧，219 MB，墙钟 **21 分 06 秒**（Remotion 21m + 编码；F4 基准首条数据）。

**目视确认生效的模板**（`out/e2e/k*.png` 抽帧）：

| 帧 | 模板 | 观察 |
|---|---|---|
| 300 | `typography/lower-third` + `caption/karaoke-word` | 左下角 "Nike × Stussy / Spiridon Kukini II"；字幕「联名」高亮 |
| 2180 | `typography/tag-float` | 右上浮签 |
| 2450 | `typography/kinetic-line` | 左下「宽脚买大半码」 |
| 2650 | `cinematic/punch-in` | 画面明显放大（scale 1.12） |
| 5620 | `data/stat-card` | 右上「4 / 套穿搭」 |
| 6560 | `typography/center-emphasis` | 「值回票价？」落在**左侧中部** |

🔴 **帧 6560 是本次最重要的一格**：该 item 起草时 footprint 是 `[0.3, 0.34, 0.45, 0.12]`，
校验期 tier1 因遮挡人脸把它平移到 `[0.10, 0.54, 0.45, 0.12]`。
成片里文字**确实出现在左侧中部** ⇒ **通道方案 A（render 侧重算）在真实画面上成立**，
不是「报告说改了、画面没动」。

**未达「可发布」的原因（三条，均非渲染 bug）**：

1. **字幕跨 cue 挤成一行**：我用「大窗口」起草（一条 caption item 覆盖 8–31 秒），
   而 `caption/karaoke-word` 渲染的是 **item 窗口内全部词** ⇒ 出现 3–5 行文字墙。
   ⇒ 用法问题：**caption item 必须按 cue 切**（48 条 cue 就该有 48 个 item）。
   也说明 SKILL.md 缺一句明确约束：「caption 区间 = 单条 cue」。
2. **对齐偏差**（§3）：cue3 的 7 秒错位仍在，成片对应段落字幕会提前出现。
3. **模板打磨未做**：本轮验的是「有没有」，不是「好不好看」。

## 5. 顺带确认与遗留

**确认有效**：

- `storyboard` 烘焙：闸1 阈值 T=0.796、12 条锚点解析、7 轨
- `validate`：18 项 + 2 条原生约束；本 job 首次跑到 error=0（11 warning）
- tier1 遮挡消解：`W-D2-01` 平移 handheld 遮挡 25.1% → 9.3%
- tier2 载体档：**真的会启动**（人工补 `carrier` 后报 `carrier-insufficient`），
  且**第三层假绿护栏正确**——「已施加载体档但主体仍遮挡 52.5% > 预算 0%」如实报错，没有谎称成功

**遗留问题（按严重度）**：

1. 🔴 **tier2 写的 `window` 在渲染层没有消费者**。
   `validate` 把 `window` 写进**叠加 item** 的 `carrier.params`，
   但 `Overlay.tsx` 按 `item.motion` 的 scope 划载体轨，`MotionItem` 完全不读 `item.carrier`；
   唯一读 `carrierParamsOf` 的 `split-frame.tsx` 只在 **motion 本身是 `carrier/split-frame`** 时运行，
   而校验侧对非叠加类 item **不会写 window**（`occlusion.ts` 显式 `isOverlayScope` 门）。
   ⇒ 两条路径不相交，**自动载体退让目前改变不了画面**。需裁决：是让 `MotionItem` 对带 `carrier`
   的叠加 item 施加包围变换，还是要求载体档必须是独立 track。
2. ⚠️ **对齐门控选型**（§3）：需要一条能看见「时间空洞」的判据（如静音区间与词落点交叉核验）。
3. ⚠️ **caption 窗口契约**：SKILL.md 未写「一条 item 一条 cue」。
4. ⚠️ **回归测试未补**：`CarrierTrack` 的「窗口外透传」与 `render` 的 video 路径，
   两项修复都只有**像素级人工证据**，尚无自动化断言。
