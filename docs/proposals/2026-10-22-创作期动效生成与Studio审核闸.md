## 1. 需求原旨（用户两句话）

1. **没有可用模板时，按 prompt 生成新 motion**；接受每次生成结果不同（"每一次不一样这个我不抵抗"）
2. **渲染前在 Remotion Studio 人工审核**，看到 motion 没问题才进入渲染

## 2. 设计原则：随机性关进创作期

```
创作期（自由掷骰子，快反馈）
  prompt「玻璃质感的数字翻牌」→ 生成 MotionSpec → Studio 预览
      ↑ 不满意就重掷（秒级画廊级渲染）           │ 满意
      └──────────────────────────────────────────┘
                                          定稿冻结为库内模板（版本化）
                                                     │
渲染期（确定性红线一字不改）
  motionboard 引用已冻结模板 → validate → render（100 次渲染同一个东西）
```

**为什么不做"渲染时生成"**（即使接受结果不同也不做）：

| 痛点 | 说明 |
|---|---|
| 反馈环 20 分钟 | 真素材渲染墙钟 20 分钟（kukini 6667 帧）；生成物 bug 只能渲完才发现，改一次掷一次 |
| 校验全线失明 | 18 项构建期校验全是结构判定；prompt 产物渲染前无已知结构（footprint/时长/遮挡预算全未知），validate 对它瞎 |
| 静默截断放大 | E-C6-01（item 超出 Composition 被 Remotion 静默裁掉、全链路无报错）对未知结构的生成物无法预防 |
| 溯源断裂 | bind-report 的 intent→模板→候选序链要求产物是可指认的库内实体 |

**"每次不一样"被完整保留**：不同次生成结果不同（创作期自由）；同一次定稿渲染恒定（生产期可靠）。确定性红线约束的是渲染期，从未约束创作期——所有模板本来就是 AI 在会话里生成的，本提案只是把这条已验证的路径产品化。

## 3. 工作流：五阶段之间插入「06-review 审核环节」

```
00-input → 01-align → 02-perceive → 03-storyboard → 04-validate
                                                          │ ok:true
                                                          ▼
                              [06-review] review 命令：
                               · 映射 render-props（复用 render 的 C6 双栈映射）
                               · 启动 Remotion Studio（--props 挂载真实 storyboard）
                               · 用户逐条过 must_review 队列 + 全片抽查
                               · 无合适模板 → 按 §4.5 genPrompt 生成新 MotionSpec → 预览 → 定稿入库
                               · 确认 → 写 06-review/confirmed.json（已审核条目清单）
                                                          │
                                                          ▼
                                            05-render（启动闸读 confirmed，未确认拒绝启动）
```

- **Studio 审核是真实预览**：`remotion studio` 挂载该 job 的 render-props，时间轴可拖、逐帧可查、逐条 item 可定位——不是看截图
- **must_review 硬闸**：闸2/产路地板判为 must_review 的条目**必须**在 Studio 过目并确认；template/auto 条目默认放行，`--require-review` 可选全量审核
- **渲染启动闸扩展**：沿 D3-a 既有机制——render 读 `confirmed.json` 的 stage:"render" 记录，新增「已审核条目清单」字段；must_review 条目未全部覆盖 → 拒绝启动（与 fullscreen 确认同一条闸，不另立机制）

## 4. 生成物验收门槛（生成的新模板六道全过才准入库）

1. 注册检查：motion id 命名空间、scope/layer/footprint 声明齐备
2. paramsSchema 契约：键与类型可校验（#16 能管住它）
3. 画廊三帧渲染：`templates:gallery` 产出且不空白
4. 「不同帧产出不同 DOM」断言（"动效真在动"唯一可靠自动化判据）
5. 确定性 lint：零 `Date.now` / `Math.random` / CSS animation / `useFrame`
6. 版本化入库：旧 job 引用的旧版本永不失效

不合格 → 打回重掷，不入库、不可被 motionboard 引用。

## 4.5 prompt 来源契约：`motionboard.genPrompt`（2026-10-23 增补）

> 增补缘由：对照用户预期流程（「无匹配素材 ⇒ 由模型**根据 board 中产出的 motion prompt** 生成新 motion，并可选择保存至素材库」）逐项比对时发现——P1-b 原稿只规定「按 prompt 生成」，**未规定 prompt 从哪来**；而现行 motionboard 契约没有承载生成 prompt 的字段：`ALLOWED_MOTIONBOARD_ITEM_KEYS`（`src/core/motionboard.ts`）现允许 `_author` / `intent` / `motion` / `featuredText` / `note` / `confidence` / `params` / `footprint` / `exclusive` / `footprintAnimates` / `carrier` / `fromFrame` / `durationInFrames` / `sim_max` —— `intent` 是受控词表（`MOTIONBOARD_INTENTS`），`featuredText` 是显示文案，都不承担「描述期望动效形态」的职责。本条把「board 产 prompt」落入契约。

| 项 | 裁决 |
|---|---|
| 字段 | `MotionBoardItem`（`src/core/types.ts`）新增**可选** `genPrompt?: string` —— 自然语言，描述期望的动效形态 / 质感 / 节奏；**禁写**坐标、帧号、颜色、CSS（同 params 纪律） |
| 谁写 | 模型（motionboard 作者）。三种触发：① intent 绑不定（`bind-report.json` 的 `noFits`）的条目；② 安全阀整批转 custom 的条目；③ 人工增删改时主动指定 |
| 谁读 | **仅创作期生成器**（P1-b 的 prompt→MotionSpec 环节）与人审 |
| 谁不读 | binder / validate / render —— `genPrompt` **不进任何机器判定**（守住 P0：自由文本不进判定链）。`assertMotionboardKeys` 的键白名单放行该键（见连带改动），但绑定器与 18 项校验都不读它 |
| 缺省行为 | 无 `genPrompt` 的 no-fit 条目 ⇒ 维持 **B4/N-3 的 custom 人工逃生口** —— 生成是增强，不是替换 |
| 与 intent 的关系 | 并存时 `intent` 仍是绑定键；生成走 `genPrompt`；产物入库后该条目改 `motion` 钉死新模板（或 intent 指向它） |
| 连带改动 | ① `src/core/types.ts`（`MotionBoardItem` 契约）；② `src/core/motionboard.ts`（`ALLOWED_MOTIONBOARD_ITEM_KEYS` 放行）；③ SKILL.md（模型写 genPrompt 的纪律：写形态不写坐标/帧/颜色/CSS） |

🔴 **为什么不让绑定器读 genPrompt 猜模板**：那等于把自由文本拉回机器判定链，正是 P0 要禁的；且「猜」的失败模式是**静默错配**（看起来绑上了，其实不是要的效果，校验全绿）。genPrompt 的唯一机器消费者是创作期生成器，且生成结果须过 §4 六道验收才准入库——语义判断的出口被门槛看着，不会反噬判定链。

⚠️ **与 M-3 的关系**：M-3（pacing 语义判定，2026-10-23）把「分布判断」交给 LLM，本条把「缺料时的形态描述」也交给 LLM。共同原则：**自由文本只进创作期，不进渲染期判定**；渲染期拿到的永远是冻结后的结构化产物（motionboard / storyboard / MotionSpec JSON）。

## 5. 分期

| 期 | 内容 | 说明 |
|---|---|---|
| **P1-a 审核闸（最小可用）** | `review` 命令 + Studio 预览 + must_review 确认闸 | 不含生成；模板仍由会话手写（今日已可行：库里 17 个模板全为 AI 会话所写）。render-props 映射需从 render 阶段前移为 review/render 共用 |
| **P1-b 生成自动化** | prompt（取自 `motionboard.genPrompt`，见 §4.5）→ MotionSpec 生成器 + 自动验收 + 版本化入库 | 生成发生在创作期会话/工具内，**不在渲染管线内调 LLM**（不违反既有红线） |
| ⛔ 明确不做 | 渲染时按 prompt 即时生成 | 理由见 §2；红线不改 |

## 6. 待裁决问题

1. 审核闸默认档位：仅 must_review 硬闸（建议）vs 全量强制？
2. P1-b 生成器的宿主：独立 CLI 命令 vs 会话内 skill 流程？（后者零管线改动，先跑通再固化）
3. render-props 映射前移后，render 阶段是否复用同一份（建议：复用 + 校验 storyboard hash 防漂移）
4. 生成新模板的命名与版本策略（建议：`custom/<语义名>@0.1` 起步，定稿升 1.0）

## 7. 验收标准（P1-a）

- `npm run pipeline -- review --job <id>` 启动 Studio 并挂载该 job 真实 storyboard
- must_review 条目未确认时 `render` 退出码 1，错误信息列出缺失的条目 ref
- 确认后 render 正常启动；fullscreen 既有闸不受影响（同一条 confirmed 记录共存）
- Studio 里能逐条定位 must_review item 的帧区间（validate 报告已给出 `frames`）

## 8. 风险

| 风险 | 缓解 |
|---|---|
| Studio 对 `--props` 挂载的支持细节待实测 | P1-a 第一件事就是验证；不行则退化为"渲染静帧抽帧 + contact-sheet 审核"（media-qa 联系表机制复用） |
| 生成模板与现有 footprint/遮挡体系冲突 | 六道验收门槛含注册检查；生成物声明 footprint 才可能过 validate |
| 审核环节被当成可选步骤跳过 | 渲染启动闸硬拦，与 fullscreen 同级，不由自觉 |
