### 0.2 修改顺序铁律

本项目有明确的真源层级，**改动必须自顶向下**，否则会出现「正文改了、登记册没改」的新矛盾：

```
① 登记册 OPEN-DECISIONS.md   ← 裁决唯一真源，先在这里把「为什么」写死
        ↓
② 乐享 KB 正文                ← 给人读的进度与设计结论，跟着同步
        ↓
③ SPEC §1/§2/§5              ← 实现规格，跟着同步
        ↓
④ .workbuddy/skills/          ← 执行期行为契约，跟着同步
        ↓
⑤ src/ 代码 + tests/          ← 最后落实现
```

**反例警示**：§3 缺口 3 如果只改 KB 不改登记册，下次有人拿登记册当依据实现，会重新引入同一个 bug。

### 1.2 问题不只是「漏了一条校验」

真正的毛病藏在 L4/L7/L9：**D3 说「必须人工确认」，但 F3 定义的 `confirmed.json` 是给「对齐降级放行」设计的**（`stage` 枚举只有 `alignment | storyboard | validate`）。也就是说：

> D3 要求一个动作，而文档里**没有任何数据结构能记录这个动作**。

这比"漏了一条校验项"严重 —— 它是闭环断了。所以缺口 1 要补两样：**落点** + **载体**。

### 1.3 修改方案（推荐）

#### P1 · 登记册：新增裁决 D3-a（先把「为什么」写死）

#### P2 · 登记册 F3 行 + 结构块：补 `render` 与 `acknowledgedFullscreen`

`stage` 枚举改为 `alignment | storyboard | validate | render`，结构块加一个字段：

```jsonc
{
  "jobId": "...",
  "stage": "alignment | storyboard | validate | render",
  "reason": "...",
  "confirmedBy": "人工署名",
  "confirmedAt": "ISO 时间",
  "acknowledgedFullscreen": ["fs-track/000"],   // ← 新增：已确认的 fullscreen item ref
```

### 2.2 问题性质：**纯漏收，不是设计分歧**

§8.6 明明白白写了「校验期检查…→ error」。而这条规则：

- ✅ 输入在构建期可读（`noMotionRanges` 就在 storyboard 自己顶层）
- ✅ 是纯结构化判定（帧区间相交，和 footprint 相交同类）
- ✅ 在渲染前就该阻断（渲染它是白渲）

**三条判据全中**，与 §7.3 表下注要立的规矩完全一致。它当初没进表，只是因为 §7 的清单早于 §8.6 成型 —— 是时序问题，不是取舍。

| N10 | 样例/文档 | `examples/demo/03-storyboard/draft.json`（**8 处全为 `"+2f"`**）→ 连产物 `bake-report.json` 也照抄了 `+2f`；`README.md`「实现过程中发现的三处文档缺口」第 3 条 | 明确写着「demo 统一用 `+2f`」以规避本条 |

> N11 是关键旁证：**测试一直是对的，是 `checkTiming` 与 C2 不一致。** 两者从没在同一个用例里碰过面 —— 测试只验烘焙，校验器只吃烘焙结果，中间那条缝就是缺口。

### 3.2 矛盾的确切形态

把 N1/N2/N3 和 N4/N6 并排放：

- C2 说：模型这样写 → `{anchor:"word:37", offset:"-8f"}` → 落到 `帧 372`
- C2-5 说：`fromFrame` 必须落在 `[word.startFrame, word.endFrame]` 内，**「否则动效早于词出现」**

`-8f` 的作用就是把 `fromFrame` 推到词起点**之前** 8 帧。于是：

> **按 C2-5 判，C2 自己给的规范示例必然报错。** 文档里每一条 `-8f` 都是自己规则的反例。

### 3.3 先定「哪一条是笔误」

这不是文字游戏，选错方向会把设计带偏。证据：

| 证据 | 指向 |
|------|------|
| §4.1 示例带注「原示例中的 span 语法已被 C2 作废」—— 说明这个示例**已经被修订过一次**，`-8f` 是修订后**留存**的 | 偏「遗留」 |
| 但 N2/N3 位于 **C2 章节自身**（不是 C1 的旧示例），是 C2 封口时的表述 | 偏「意图」 |
| 抢拍（动效略先于台词）是 MG 常见且有效的手法；一刀切禁掉会让动效永远「追着声音跑」 | 偏「意图」 |

**关键的决定性论据**：如果走「禁负偏移」，那抢拍就只能靠 `abs:` 绝对帧实现。但 `abs:` 写死帧号后**就失去「跟着词走」的能力** —— 改一处文案，锚点全废。这等于把抢拍逼回手工定帧，**直接违反 C2 的核心铁律「不让模型手算帧」**。

> **所以「禁负偏移」这条路走不通。** 结论：`-8f` 是真实意图，**C2-5 的区间写窄了**。

### 3.4 修改方案

#### 改 C2-5 的判定区间：下界从「词起点」改为「锚定词所在 cue 的起点」

```
原：合法区间 = [word.startFrame, word.endFrame]
新：合法区间 = [cue.fromFrame, word.endFrame]
    其中 cue = 覆盖该锚定词的 cue；无 cue 覆盖时退化为 word.startFrame（保守）
```

**为什么下界取 cue 起点**：

1. **零新增常量。** cue 边界本来就有（`01-align` 的 cue 来自 SRT + 强制对齐），不需要拍一个「提前量上限」的数字 —— 而这个数字一旦拍出来，就是又一个待实测占位值。
2. **语义对。** cue = 一句话。动效在**同一句话内**提前进入可接受；跨到**上一句**里去才是真错位。这正是 C2-5 想拦的东西。
3. **与既有设计同源。** B3 的「停顿锚点」也是把停顿当语义边界用的 —— 这里复用了同一种直觉。

**代价（要如实写在文档里）**：放宽后，「动效在长 cue 的最开头就进入」不再被拦。若认为这不可接受，可**另加一条 warning**（不阻断）：提前量超过某阈值 → `W-C2-5-01`。但那个阈值同样是待实测数值，**建议留到 C2-2 一并校准，不要现在拍**。

#### 具体补丁

### 3.6 依赖与受影响段落

**上游依赖**
- `01-align` 必须产出 cue 边界，且 cue 与词能对应上。**这是本方案唯一的外部依赖** —— 若 cue 不可靠，整个下界就不可靠（退化为词起点）。当前 `words.json` 里 cue 由 SRT 文本 + 对齐词时间共同定界，来源是可靠的。
- 实现上不需要新字段：在 cue 列表里找 `fromFrame ≤ word.startFrame ≤ toFrame` 的那条即可。

**受影响的既成事实**
- **`examples/demo` 现在用 `+2f` 是在规避这个 bug**，改完应改回负偏移以证明修复有效 —— **这条要做，否则无法验证**。
- `src/core/bake.ts` 里关于时长的推导 `max(模板 minVisibleInFrames, 锚定词区间长度)` 不变，负偏移不影响它。
- C2-2 的阈值校准（待办）与本条无耦合，但**如果**采纳「提前量 warning」，阈值要与 C2-2 一起实测，不要分两次拍。

**容易被漏掉的一处**：`tests/bake.test.ts` 里有断言 `fromFrame === 840 - 8`（`word:37` + `-8f`）。这个测试**本来就是按 C2 语义写的**，是 `checkTiming` 与它不一致。改完 `checkTiming` 后它无需变动，但值得在提交信息里点明「测试一直是对的，是校验器错了」。
