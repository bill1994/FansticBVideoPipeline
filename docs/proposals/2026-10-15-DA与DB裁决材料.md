## 1. D-A：是否新增「会遮挡主体的叠加模板」

### 1.1 位置

`src/templates/builtin.ts`（10 个模板声明）+
`src/validate/occlusion.ts` 的 `collectHits()`（判定入口）。

### 1.2 问题的确切形态

补上 `occludesSubject` 消费后，实测 **10/10 模板无一能进入遮挡判定**：

| 路径 | 模板 | 为什么进不去 |
|---|---|---|
| 声明 `true` | `carrier/split-frame` | 载体类 → `isOverlayScope` 为false |
| 声明 `true` | `cinematic/punch-in` | 同上 |
| 声明 `true` | `transition/whip-pan` | fullscreen → D3 人工确认分支 |
| 声明 `false` | 其余 7 个 | 按字段过滤掉 |

⇒ **D2 这套「区域分级 + 令牌预算 + 三级退让」的机制，在真实素材上跑不起来。**

### 1.3 为什么这不是"补实现补错了"

三个理由，逐条都指向「模板集缺口」：

1. **声明语义是完备的** —— `occludesSubject` 能区分
   `whip-pan`(true) 与 `noise-grain`(false)，信息量真实存在；
2. **过滤规则是合理的** —— 载体类不该进遮挡预算、fullscreen 归 D3，都有依据；
3. **缺的只是「那类模板本身」** —— 规则没写错，是**没有对象符合规则**。

⚠️ 反过来说：如果现在把某个 `overlay-safe` 模板改标 `true`，
它**默认footprint 大概率不在主体区** ⇒
会出现「声明遮挡主体但默认摆位并不遮挡」的语义矛盾。
**这是为什么不能顺手改标，而要新增。**

### 1.4 方案对比

#### 方案 A：新增 1–2 个 `overlay-safe` + `occludesSubject: true` 模板

**推荐 A1（单模板，最小验证）**

| 项 | 内容 |
|---|---|
| 形态 | **居中大字强调**（压在主体胸腹区） |
| scope | `overlay-safe` |
| layer | 约 70（高于现有 overlay-safe的 40–60，压在主体上方） |
| footprint | 约 `[0.15, 0.38, 0.7, 0.22]`（画面中部，正是主体所在） |
| `occludesSubject` | **true** |
| paramsSchema | `{ text: string }`，`requiredParams: ['text']` |
| minVisibleInFrames | 30 |
| 渲染实现 | 与 `kinetic-line` 同结构（定位框 + 大字 + 竖条），但字号更大、无入场位移（因为它就是「压上去」的） |

**优点**：
- 形态与真实需求吻合（口播视频里「压在人身上的大字」是高频手法）；
- 让 D2 机制在真实素材上**第一次能被触发**；
- `footprint` 落在主体区 ⇒ 遮挡判定名副其实。

**代价**：
- 增加模板数（10 → 11），后续需维护手感表条目；
- **长文本风险**（与 D-B 相关）：大字号 + 宽框，阈值需实测。

**次选 A2（通栏条）**：横向通栏条（从左延伸到右侧的强调条）。
`footprint` 约 `[0, 0.45, 1, 0.1]`，**必然横跨主体** ⇒ 遮挡更显著。
但它与 `lower-third`（左下贴边条）形态相近，**需先确认两者在画面上的区分度**。

#### 方案 B：改标现有模板为 `true`

**不推荐。** 理由见§1.3 末段 —— 会产生「声明遮挡但默认摆位不遮挡」的矛盾。
若坚持此路，须**同时**调整该模板的默认 `footprint` 到主体区，
那实质上就是「改了形态」，与新增无异，却**丢失了原有的安全区用法**。

#### 方案 C：暂不新增，靠 perceive 落地后再说

**代价**：D2 机制继续只在测试夹具上被验证。
⇒ ⚠️ 风险：**夹具能证明代码逻辑对，但证不了真实素材上够用**。
两者差异恰恰在「真实主体框的形状与位置分布」上，
而那正是 D2 预算表（人脸 0% / 手持物 20% / B-roll 30%）要适配的对象。

### 1.5 三方案对比速查

| | A1 居中大字 | A2 通栏条 | B 改标现有 | C 暂不做 |
|---|---|---|---|---|
| 解D2 机制空转 | ✅ | ✅ | ⚠️ 部分 | ❌ |
| 形态与真实需求吻合 | ✅ 高频 | ⚠️ 与lower-third 近| ⚠️ | — |
| 新增维护成本 | 1 模板 | 1 模板 | 0 | 0 |
| 语义矛盾风险 | 无 | 无 | 🔴 有 | 无 |
| 需实测项| 长文本阈值 | 长文本 + 区分度 | — | — |

### 1.6 改完之后的衔接

若裁决 A：

1. `builtin.ts` 新增声明（`layer` 建议 70，避开现有 40–60）；
2. `src/remotion/templates/` 新增组件 + 加进 `IMPLEMENTED` 映射表；
3. 手感表补该模板条目（**必须**，否则违反「改实现必改表」纪律）；
4. **撤掉测试夹具**？ ⚠️ **不撤** —— 夹具仍用于测 tier2 等与具体模板无关的链路；
   但可把「必须有真实遮挡型模板」这条依赖去掉。
5. 真渲验证（Chrome 已就绪，单段约 40 秒）。

⚠️ **不需要改登记册的既有决策** —— 这是新增模板，不是改判D2。
但裁决本身要回写登记册（按纪律「裁决后必须回写」）。

## 2. D-B：长文本溢出的处置

### 2.1 位置

4 个模板组件（`kinetic-line` / `lower-third` / `tag-float` / `stat-card`）
的 `whiteSpace: nowrap` + 固定字号。

### 2.2 问题的确切形态（2026-10-15 真渲实测）

塞入 16 个中文字 + `123456789`，1920×1080 实测：

| 模板 | 测试值 | 实测结果 |
|---|---|---|
| `kinetic-line` | 16 中文字 | 铺满 806px 框并溢出 |
| `lower-third` | 16 中文字 + 副标题 | 文本长过条形背景 |
| `tag-float` | 16 中文字 | 撑破 240px 胶囊框 |
| `stat-card` | `123456789` | 🔴 **溢出画面边界** |

真实阈值约 **13–14 中文字**（比初稿估计宽 3 倍 —— 初稿是拍脑袋的，被实测纠正）。

### 2.3 为什么这条比 D-A 紧迫

三个理由：

1. **已经会坏**：5 个模板已实现、可用，模型一填长文本就出问题；
2. **无人能拦**：16 项校验全是结构判定，**不读渲染结果**
   ⇒ 校验报告照样 `ok: true`，成片已经坏了但没人知道；
3. **不会被"诚实留空"兜住**：项目对「未实现」有诚实降级机制，
   但**对「实现了但输出越界」没有任何机制**。

⚠️ 这正是本项目反复出现的同款病：
**「定义了没人用」的反面 —— 「出了错没人拦」。**
16 项校验覆盖了「结构对不对」，但覆盖不了「画出来好不好看」。

### 2.4 方案对比

#### 方案 A：渲染期自适应（按文本长度降字号 / 断行）

**做法**：组件内量测文本长度，超阈值则降字号或允许折行。

**优点**：治本，且对模型完全透明（模型不用管）。

**代价（🔴 三条，都不小）**：
1. **破坏「字号即层级」语义** —— 层级是设计的一部分，
   自动降字号等于让机器替用户做审美决策；
2. **各模板降法不同** —— 字幕宁可降字号，强调字宁可断行，
   数字卡可能该换单位 ⇒ 5 套策略要分别调；
3. **SSR 下量测不可靠** —— 量文本宽度需要浏览器度量，
   而单测走 `renderToStaticMarkup`（无布局）⇒ **测试覆盖不到这条路径**。

#### 方案 B：构建期校验（新增校验项 #17）

**做法**：校验 `文本长度 × 字号 ≤ footprint 宽`。

**优点**：**早发现早阻断**，与项目「渲染前就该拦」的判据一致；
测试走纯字符串计算，**可完整单测**。

**代价（🔴 两条）**：
1. **必须先改登记册**（项目纪律：增补校验项须先改登记册）；
2. **引入字体度量估算** —— 需定规则（如 CJK 按 1.0em、拉丁按 0.5em、
   标点按 0.5em）。⚠️ **估算不准就会误伤合法创作**
   —— 这正是计划书风险登记 R6「审美断言设计过度 ⇒ 误伤」的具体化。

⚠️ 但 B 的风险是「偶尔误伤」，A 的风险是「成片一直坏」
—— **后者严重得多**。这个不对称是推荐 B 的主要理由。

#### 方案 C：不做，靠 SKILL.md 纪律约束

**做法**：起草规范里写明字数上限（当前 ≤6 字）。

**优点**：零改动、零风险。

**代价**：
- **纪律不是强制**。项目已有铁律「增补校验项须先改登记册，
  当天就抓到过两次漏同步」⇒ 靠纪律的失败率**有实测证据**；
- 用户没有编辑 UI，只能手改 JSON ⇒ 无提示、无兜底。

### 2.5 三方案对比速查

| | A 渲染期自适应 | B 构建期校验 | C 靠纪律 |
|---|---|---|---|
| 治本程度 | ✅ | ✅（在构建期） | ❌ |
| 误伤风险 | 低 | ⚠️ 中（度量估算） | 无 |
| 测试可覆盖 | ❌ SSR 量不到 | ✅ 纯函数 | — |
| 破坏既有语义 | 🔴 字号即层级 | 无 | 无 |
| 需改登记册 | 否 | **是** | 否 |
| 成片仍会坏 | 不会 | 不会（被拦住） | 🔴 **会** |

### 2.6 若选 B，估算规则需要先定的三件事

⚠️ 这三项**必须一起定**，分次拍必然留坑（同 `alignedRatioMin` 的教训）：

1. **宽度估算系数**：CJK / 拉丁 / 数字 / 标点各按多少 em？
2. **阈值松紧**：估算值 × 多少算超？**建议留 10%–20% 余量**，
   因为字体实际度量可能略宽于估算；
3. **超了之后报什么**：`error`（阻断，需人工改）还是 `warning`（仅提示）？
   ⚠️ 倾向 `warning` 起步 —— 与 `DENSITY.maxItemsPerCue`
   那个「未校准的占位值当 error 用，伤害真实用户」的教训一致。

## 3. 建议的裁决方式

### 3.1 若你只想拍一件事

**先拍 D-B，选方案 B（构建期校验，warning 档起步）**。
理由：它影响**已可用**的5 个模板，且当前「校验全绿但成片已坏」；
D-A 影响的是**尚不存在**的模板，暂无实际损失。

### 3.2 若你同意两项都做

建议顺序：**D-B（先）→ D-A（后）**。
理由：D-B 会让"新增一个大字模板"这件事更安全
（新增模板必然带来新的溢出阈值需要实测）。

### 3.3 若你想先都不做

那么请明确记录「已知风险，不做」——
当前状态下，模型起草时填长文本会产出明显坏的成片，
**且没有任何机制会提示**。这个风险需要被显式接受，而不是被遗忘。
